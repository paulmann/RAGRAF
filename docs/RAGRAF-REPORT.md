# RAGRAF: подключение языков разработки и пометка документации

Отчёт о сессии. Все числа получены замером в этой сессии; где число взято
из более раннего замера, это указано. Утверждения, которые не удалось
проверить, помечены прямо.

## 1. Что было не так

Постановка задачи: «просканируй `<полигон>` и `1st_RdpMON\Service` на мой
стек разработки; нужно добавить в сканирование и индексацию RAGRAF ps1, bat, sh
и другие найденные коды; подумать о добавлении md-файлов с пометкой роли».

Фактическое состояние до правок:

1. **`catalog` не знал о проекте** — это исходная жалоба, и она подтвердилась.
2. **`.ps1`, `.sh`, `.bat` не попадали в индекс.** Причина установлена
   и совпадает с названной: их расширений нет в карте языков
   `RAGRAF\src\ragraf\config.py`, а разбор деревом шёл только для трёх языков
   (`PARSE_LANGS = {"php", "css", "html"}`).
3. **Дополнительная находка, которой в жалобе не было.** Не попадали не только
   скрипты: в `1st_RdpMON\Service` **1217 файлов `.cs`** — основной язык
   проекта — и RAGRAF не мог ответить ни на один вопрос о его коде. Операции
   `symbol`, `callers`, `code` возвращали пусто. То есть RAGRAF был бесполезен
   ровно там, где нужен больше всего. Это оказалось дороже отсутствия скриптов.

Замер по каталогам (`tools/scan_scripts.py`):

## 2. Что сделано

### 2.1 Карта языков: 10 расширений → 55

`src/ragraf/config.py`, `LANG_BY_EXT`. Было 10 расширений, стало 55.
Языков: 27. Из них **16 разбираются деревом**, 11 — только текстом.

**Разбираются деревом** (узлы, рёбра, вызовы):
`php, css, html, javascript, typescript, python, csharp, perl, bash,
powershell, ruby, lua, go, java, c, cpp`

**Только текстом** (поиск и чтение, без структуры):
`markdown, sql, batch, yaml, json, toml, ini, xml, text, rst, rust`

Выбор сделан замером, а не по названию. Грамматики проверены на реальных
файлах (`tools/check_parse_real.py`):

| язык | разобрано/проверено | вывод |
|---|---|---|
| json, php, markdown, html, javascript | 12/12 | деревом |
| yaml, perl, python, csharp | 12/12 | деревом |
| typescript | 10/12 | деревом |
| bash | 11/12 | деревом |
| css | 9/12 | деревом (частичные ошибки не мешают) |
| powershell | 6/12 | деревом, с оговоркой |
| c, cpp | 4–5/12 | деревом, с оговоркой |
| **sql** | **0/12** | только текстом |
| **batch** | **0/7** | только текстом |
| **ini** | **3/12** | только текстом |

**PowerShell разбирается частично, и это нормально.** Из 96 файлов
`.ps1`/`.psm1` 53 разбираются без ошибок, а 43 — с неполным разбором
(`tools/check_powershell_parse.py`). Грамматика спотыкается на специфическом
синтаксисе: `1KB`/`1GB` в арифметике, `[math]::Round`, атрибутах параметров.
Файл при этом попадает в поиск текстовыми чанками, а признак неполноты виден
в `index_status` (`files_partial`). Утверждать, что файл разобран целиком,
нельзя.

**Почему SQL и batch — текстом.** Разбор дал ошибку на всех проверенных
файлах. Строить по ним узлы значило бы выдумывать структуру. Текстом они
попадают в поиск, но узлов не дают — и это честнее мнимых функций.
Практический эффект всё равно есть: **именно так в корпусе z обнаружились
25 файлов миграций и 44 таблицы схемы**, которых раньше не было видно.

### 2.2 Обобщённый извлекатель вместо жёсткого PHP

Создан `src/ragraf/extract/generic.py`. До него `PhpExtractor` был написан под
грамматику PHP и жёстко зашит. Теперь для каждого языка с грамматикой описан
набор имён узлов (`LangProfile`), а обход и построение фактов общие.

Выдаются те же виды узлов и рёбер, что у PHP-извлекателя: иначе операции
фасада (`callers`, `impact`, `slice`) не увидели бы новые языки, потому что
обход графа фильтрует рёбра по известным видам.

### 2.3 Индексатор: сняты жёсткие списки языков

`src/ragraf/indexer.py`. Было два ручных набора — `PARSE_LANGS` и `TEXT_LANGS`,
и всё, чего в них не было, отбрасывалось со статусом `skipped`. Теперь решение
принимается по факту: есть ли у языка извлекатель.

**Причина, по которой это было хрупко.** Наборы дублировали карту расширений
и разошлись с ней — именно поэтому `.js`, `.cs`, `.ps1` числились
«неизвестными». При первой же попытке сделать второй ручной список
(`PARSE_LANGS_EXT`) тест сразу поймал расхождение: семь расширений
(`.psd1`, `.zsh`, `.t`, `.pyi`, `.mts`, `.cc`, `.cxx`) были в карте, но
забыты в нём. Поэтому набор языков с разбором теперь **производный** от карты,
а не второй список.

### 2.4 Пометка роли документации

Создан `src/ragraf/docrole.py`. Роль определяется по имени файла, и только
для технического задания — по заголовку первых строк.

Одиннадцать ролей:

| `doc_role` | название |
|---|---|
| `tech_spec` | техническое задание |
| `agent_rules` | правила агента |
| `acceptance` | критерии приёмки |
| `architecture` | описание устройства |
| `plan` | план работ |
| `report` | отчёт |
| `changelog` | история изменений |
| `readme` | описание проекта |
| `reference` | справочный материал |
| `documentation` | прочая документация в каталоге документов |
| `other_md` | markdown без опознанной роли |

Роль хранится в новой колонке `chunk_map.doc_role` и **доходит до ответа
поиска**:

```json
{
  "path": "docs/ТЗ-Документооборот-agreements.md",
  "start_line": 1,
  "doc_role": "tech_spec",
  "doc_role_title": "техническое задание"
}
```

У чанков кода поля нет — и это тоже сигнал: нет метки, значит не документ.

**Почему имя файла, а не содержимое.** Разведка по двум каталогам дала:
`README*` — 122 файла, `AGENTS.md` — 21, `CHANGELOG*` — 20, `*_REPORT` — 38.
Признак роли лежит в имени, и читать содержимое для его определения незачем.
Исключение одно — ТЗ: файлов с именем `TZ.md`/`ТЗ-*.md` всего **2** на 1550
документов, а с заголовком «Техническое задание» — **4**. Без проверки
заголовка три задания из четырёх остались бы без метки.

**Единой конвенции ТЗ в проектах НЕТ** — это результат разведки, а не
предположение. Четыре найденных технических задания лежат в четырёх разных
схемах: `docs/02_architecture/TZ.md`, `docs/ТЗ-*.md`, `BSL/*.md`,
`.zwork/attachments`. Придумать единый шаблон имени было бы выдумкой.

### 2.5 Учёт узлов и рёбер исправлен

Побочная, но важная находка. Журнал ревизии показывал **2227 узлов**, а в
таблице лежало **1290** — расхождение 42%, выглядевшее как потеря данных.

Разбор (`tools/measure_node_dupes.py`, `measure_node_dupes2.py`):

| вид узла | строк | различных id | схлопнуто |
|---|---|---|---|
| **css_class** | 1441 | 521 | **920** |
| function | 365 | 365 | 0 |
| file | 112 | 112 | 0 |
| method | 37 | 37 | 0 |
| class, constant, namespace, property | 17 | 17 | 0 |

**По узлам кода схлопываний НОЛЬ.** Все 920 схлопываний — классы CSS,
и это намеренное решение, записанное в журнале ранее: имя класса — общий ключ
без пути (`class_node_id(name)`), иначе определение в стилях и использование
в разметке не сопоставлялись бы. Именно так были найдены 32 класса `z-agr-*`
без правил в CSS.

То есть **потери данных не было** — была неточность учёта. Исправлено:

- число узлов берётся из таблицы (`count_nodes`), а не из длины списка строк;
- число рёбер тоже берётся из таблицы (`count_edges`): между подсчётом
  и запечатыванием работают стадии, которые **добавляют** рёбра — разрешение
  внешних имён и перенос графа свойств кода. На z журнал показывал 12499
  при 12956 фактических.

### 2.6 Ошибка в разборе C#: `record` определялся как `struct`

Найдена на реальном корпусе. В индексе `public sealed record AlertRule(...)`
оказался **структурой**, хотя это ссылочный тип.

Причина: грамматика C# даёт один и тот же тип узла `record_declaration`
и для `record class` (ссылочный тип), и для `record struct` (значимый).
Различить их по имени узла невозможно. Проверено отдельным файлом
(`tools/diag_csharp_record.py`).

Исправлено: в профиль добавлено правило, зависящее от ключевого слова
внутри узла. Проверка `tests/test_csharp_records.py` — **12/12**:

```
AlertRule   record class  → class     (было struct)
Person      record class  → class
Point       record struct → struct
Pair        record struct → struct
Vector      struct        → struct
```

Разница существенная: по ней судят о копировании и передаче по ссылке.

### 2.7 Исключения: `publish` и `obj` — проверены, а не угаданы

При подключении RdpMON `init` сначала насчитал 2415 файлов и 93 МБ. После
разбора — 1268 файлов и 11,7 МБ.

Проверка исключений сделана по содержимому (`tools/check_excluded_dirs.py`,
`check_publish_sources.py`), потому что исключение каталога необратимо:

- `publish` (406 файлов, 389,5 МБ) — сборка. Внутри нашлись и файлы кода
  (`.html`, `.css`, `.js`), и по имени решать было рискованно. Проверка
  по имени и содержимому: у всех трёх есть источник в `src/RdpAudit.Web/wwwroot`,
  содержимое отличается → это копия, а не единственный экземпляр. Исключение
  безопасно.
- `obj` (168 файлов `.cs`) — по имени похоже на исходники. Проверка: все
  сгенерированы сборкой (`AssemblyInfo.cs`, `GlobalUsings.g.cs`,
  `.NETCoreApp,Version=v8.0.AssemblyAttributes.cs`).
- `.dev_agent` (2376 файлов, из них 1911 = 80% резервные копии `.bak`).
- **`.staging` намеренно НЕ исключён.** Там лежит **единственный** файл `.sh`
  проекта (`.staging/port-diff/reference.sh`, 23 176 б) и портированные
  скрипты `.ps1`. Исключить его — значит прямо саботировать задачу
  «индексировать ps1, sh, bat».
- Резервные копии исключаются **по имени файла**, а не по каталогу: в C#
  проекте 1911 файлов `.bak` разбросаны по дереву, и выборочное исключение
  каталогов не помогает.

## Разбор Python: что заработало и что нет

Корпус sagaai (Python/Streamlit) стал первым корпусом этого языка.
Разбор потребовал правок, и часть ограничений сохраняется — они указаны
прямо, чтобы ими не пользовались вслепую.

### Что заработало

| Возможность | Состояние | Замер |
|---|---|---|
| Разбор исходников деревом | работает | 378 файлов, 5751 узел |
| Дерево символов (функции, классы) | работает | 3362 функции, 730 методов, 192 класса |
| Поиск по коду и смыслу | работает | возвращает пути и строки |
| Роли документов | работает | правила агента опознаются |
| Рёбра вызовов разбором дерева | работает | 22 886 (`calls_heuristic`) |
| Рёбра вызовов из графа Joern | работает | 4299 (`calls`) |

### Правки, которые для этого понадобились

1. **Выбор языка.** В сборке графа было жёстко зашито `--language PHP`.
   Для Python используется отдельный парсер Joern `pysrc2cpg`, который
   нашёлся в установке (`.bat`-обёртка) и умеет `--ignore-dir-names`.
2. **Исключения служебных каталогов.** Передача списка в `--ignore-dir-names`
   требует **кавычек** вокруг значения: без них cmd.exe разбирает запятую
   как разделитель аргументов, и Joern отвечает «Unknown argument».
   Ошибка была неочевидной: код возврата 1 без указания на кавычки.
3. **Нормализация имён.** Правило приведения имён было написано под PHP
   (`->` → `::`). Для Python оно портило имя: `core\api_errors.py:__init__`
   не совпадало ни с одним полным именем индекса. Добавлено отдельное
   правило: разделители пути приводятся к прямым слешам, форма `путь:имя`
   сохраняется.
4. **Обозначение глобальной области.** У PHP это `<global>`, у Python —
   `<module>`. Проверялось только первое, поэтому вызовы уровня модуля
   не отсеивались и одновременно не привязывались.

### Сохраняющиеся ограничения

1. **Экспорт графа Python падает.** `joern-export` завершается ошибкой
   `SchemaViolationException: OUT edge with label REF to an adjacent METHOD
   is mandatory, but not defined for this METHOD_REF node`. Падение
   происходит при расчёте оверлея потока данных, а не при выгрузке:
   сам граф пригоден. Проверено на всех сочетаниях `--repr` и `--format` —
   не работает ни одно.
2. **Серверный путь недоступен.** Оба способа получить граф через сервер
   Joern для Python падают:
   * `importCode` ищет исполняемый генератор `pysrc2cpg` и не находит его
     (в установке только `.bat`-обёртка);
   * `importCpg` падает с `NullPointerException` в `XTypeRecoveryPassGenerator`.
3. **Вызовы уровня модуля не привязываются.** Joern для Python помечает
   владельцем `<module>` даже внутри функций (замер: все 172 184 записи),
   поэтому привязка идёт в основном по разбору деревом.
4. **Операции `slice` и полный `impact` недоступны** для этого корпуса:
   они требуют графа свойств кода. `impact` отвечает, но по неполным данным.

### Как это влияет на работу

Для поиска по коду, навигации по символам и понимания структуры корпуса
sagaai пригоден: эти операции опираются на разбор деревом и работают.
Для анализа потока данных и точной оценки последствий правки — нет:
там нужен настоящий CPG, а он для Python не выгружается.


## 4. Проверено и опровергнуто: cuGraph

В отчёте прошлой сессии вывод «cuGraph невыполним» стоял как **непроверенный**:
сравнение делалось на `torch.sparse`, а не на самом cuGraph, и WSL не установлен.

Проверено фактом через API PyPI (`tools/check_cugraph_windows.py`):

| пакет | версия | платформы сборок |
|---|---|---|
| `cugraph-cu12` | 26.8.0 | `manylinux_2_26_aarch64`, `manylinux_2_27_x86_64` |
| `cugraph-cu13` | 26.8.0 | только `manylinux` |
| `pylibcugraph-cu12` | 26.8.0 | только `manylinux` |
| `cudf-cu12` | 26.8.1 | только `manylinux_2_24` |

**Сборок под Windows нет ни у одного пакета RAPIDS.** На этой машине
(Windows, WSL не установлен) поставить cuGraph нельзя. Вывод прошлой сессии
подтверждён — теперь не мнением, а фактом.

**Оговорка, которую нужно сохранить.** Отсутствие сборки НЕ означает, что
cuGraph плох. В WSL он поставится, и там может оказаться быстрее процессора.
Наш вывод был про другое: на графе 1059 вершин даже готовый GPU-обход
проигрывал процессору, потому что в первый вызов входит подготовка карты; на

## 5. Дубликаты документации — **реализовано**

Разведка дала числа, которые повлияли на реализацию:

- **669 побайтово одинаковых копий** документов найдено в подключённых
  корпусах и их окружении.
- Из **120 файлов `readme.md`** — **103 с разным содержанием**.
- Худший случай: один ADR в **104 копиях**, размноженный вложением каталогов
  (`old/revoap.com/www/www/www/www/docs/`).
- Полный замер по `<полигон>`: **5559 документов, 513 групп копий,
  3856 лишних файлов** — 44,7 МБ против 2,3 МБ полезного текста.

**Ключевой вывод подтверждён и реализован: схлопывание идёт по хэшу
содержимого, а не по имени.** Схлопывание по имени слило бы 103 разных
`README.md` в один.

### Как устроено

Создан `src/ragraf/dedupe.py`. Файлы группируются по `sha256` (он уже
считается при сканировании), из каждой группы остаётся одна «главная» копия.

**Файлы на диске НЕ удаляются.** В модуле нет ни одного удаляющего вызова
(проверяется тестом). Инструмент только перестаёт считать копии отдельными
сущностями индекса — удаление необратимо, и решать его должен владелец.

Встроено в `corpus.scan()` — единственную точку, откуда файлы берут
и индексатор, и сторож свежести. Это критично: `corpus_hash` считается по
полю `files`, и если бы схлопывание шло _после_ подсчёта суммы, она не
совпала бы с содержимым индекса и сторож зациклил бы переиндексацию.

### Правило выбора главной копии — замерено, а не выбрано на глаз

Проверены четыре правила на 513 реальных группах
(`tools/measure_dedupe_rules.py`). Считалось, сколько групп получило
«главным» путь из каталога-копии:

| правило | групп с мусорным путём |
|---|---|
| **без мусорных сегментов (`cleanest`)** | **38** |
| самый свежий | 65 |
| самый короткий | 76 |
| самый длинный | 242 |

Выбор детерминирован: при полном равенстве берётся лексикографически первый
путь. Это обязательное условие: иначе главным каждый раз станет разный файл,
сумма корпуса изменится, и сторож зациклится.

### Настройки (панель администратора)

| настройка | значения | по умолчанию |
|---|---|---|
| `dedupe_enabled` | да/нет | **выключено** |
| `dedupe_scope` | `docs` \| `all` | `docs` |
| `dedupe_mode` | `keep_one` \| `skip_all` | `keep_one` |
| `dedupe_keep` | `cleanest` \| `shortest` \| `longest` \| `newest` | `cleanest` |
| `dedupe_report` | да/нет | включено |

По умолчанию **выключено** осознанно: включение меняет состав индекса,
то есть требует переиндексации и сдвигает все числа в отчётах.

Опечатка вида `dedupe_scope: doc` отклоняется в интерфейсе с указанием
допустимых значений, а не превращается в ошибку через час индексации.
Интерфейс рисует эти настройки списками, а не полями ввода числа.

### Результат на корпусе revoap.com

| до | после |
|---|---|
| 699 файлов | **592 файла** |
| — | отброшено **107 копий** в 86 группах |
| — | все отброшенные — документы; файлов кода 0 |

Проверено (тесты `test_dedupe_effect.py`, `test_dedupe_stability.py`):

- ни одна отброшенная копия не попала в индекс (0);
- все оставленные файлы попали в индекс (0 потерь);
- уникальных файлов не потеряно ни одного (проверка по хэшам);
- чанков от отброшенных документов в индексе нет (0);
- в выдаче поиска путей-копий нет;
- **сторож свежести не зацикливается:** хэш в ревизии совпал с хэшем скана,
  `changed=False`, `stale=False`.

Числа схлопывания видны в `index_status`: `files_found` 699, `files_total` 592,
`dup_dropped` 107, `dup_groups` 86, `dup_bytes` 17440.

### Что важно понимать

Если `dup_dropped` больше нуля, разница между `files_found` и `files_total`
объясняется схлопыванием, а не потерей файлов. В корпусах
z.batteryservice.ru, RdpMON и MD.Viewer дублей **нет вовсе** — там включать
нечего, и это тоже проверено.

## Учёт агента в статистике

Статистика использования разделена на две независимые оси. Раньше они были
смешаны в одном поле, и отфильтровать данные по агенту было невозможно.

| Ось | Поле | Значения | Отвечает на вопрос |
|---|---|---|---|
| Канал | `tool` | mcp, cli, admin, dev, selftest | откуда пришёл вызов |
| Агент | `agent` | AutoClaw, SagaAI, MD.Viewer, RAGRAF-Admin | кто именно вызвал |
| Семейство | `agent_kind` | autoclaw, external, internal | свои или сторонние |

### Почему это понадобилось

Замер до правки: в корпусе z.batteryservice.ru поле `tool` принимало
значения admin/cli/dev/selftest/unknown, и **113 вызовов из 138** числились
как `unknown`. Причина: MCP-сервер создавал фасад, не сообщая о себе,
а клиент `clientInfo` в запросе `initialize` не читался.

После правки имя агента берётся из двух источников:
  1. параметр запуска `--agent` (приоритетный: задаёт владелец);
  2. поле `clientInfo.name` запроса `initialize` (по протоколу MCP
     клиент обязан себя назвать).

Для консольного вызова имя передаётся переменными окружения
`RAGRAF_AGENT` и `RAGRAF_AGENT_KIND` — это единственный способ узнать
агента, не меняя синтаксис командной строки.

### Три режима статистики

```
ragraf -p <конфиг> usage                   # общая по всем агентам
ragraf -p <конфиг> usage --agent AutoClaw  # только этот агент
ragraf -p <конфиг> usage --agent-kind autoclaw  # все агенты AutoClaw
```

В ответе есть разбивка `by_agent` (по каждому агенту) и `by_agent_kind`
(по семействам). Сессии и вызовы считаются раздельно: один процесс MCP
может обслужить несколько задач, поэтому числа могут расходиться.

### Старые записи не потеряны

Добавление полей идёт догоняющей миграцией: прежние журналы не требуют
удаления, а записи без агента видны как `unknown`. Проверено на живом
журнале: 190 сессий и 138 вызовов сохранены полностью.

Особенность: фильтр `--agent unknown` ищет не строку `unknown`, а записи
с пустым полем (NULL). Без этого фильтр возвращал 0 вызовов, хотя в разбивке
их было 138 — владелец видел строку и, выбрав её, получал пусто.

### Кто представлен в панели администратора

Панель обращается к RAGRAF ради чтения состояния и статистики. Её
собственные обращения помечены агентом `RAGRAF-Admin` с семейством
`internal`, поэтому они не смешиваются с работой агентов.


## 9. Служебные каталоги в исключениях

**Запрос владельца:** «добавить в исключения для индекса служебные папки `.ragraf`».

**Проверка показала: `.ragraf` уже был исключён везде** — и это проверено
четырьмя способами, а не по одному месту:

| слой | состояние |
|---|---|
| базовый список `DEFAULT_EXCLUDES` (config.py) | `**/.ragraf/**` есть |
| список `init` (`init_corpus.py`) | `.ragraf` есть |
| конфиги всех шести корпусов | правило есть в каждом |
| фактический скан | `.ragraf` обрезается, **0 файлов** в индексах |

Отдельно подтверждено механизмом: базовые исключения применяются
АВТОМАТИЧЕСКИ (`config.py:654`: `exclude = list(DEFAULT_EXCLUDES) + из файла`),
поэтому корпус без правила в своём конфиге всё равно защищён.

### Настоящий пробел, который нашёлся вместо этого

Два списка одного и того же расходились:

| список | каталогов | где действует |
|---|---|---|
| `EXCLUDE_DIRS` (init_corpus.py) | 28 | только при создании корпуса командой `init` |
| `DEFAULT_EXCLUDES` (config.py) | 13 → **28** | всегда |

**Последствие:** корпус, подключённый вручную, начинал индексировать
`__pycache__`, `.venv`, `target`, `node_modules` и прочее — сотни и тысячи
файлов вида `site-packages/*.py` и `*.pyc` попадали в поиск.

### Что сделано

Базовый список расширен с 13 шаблонов до **28** (24 каталога + 4 образца имён).
Внесены только те, безопасность которых подтверждена замером: при их
включении **выпадает 0 файлов во всех пяти корпусах**
(`tools/measure_safe_excludes.py`).

Список `init` синхронизирован с базовым: расхождение устранено (было 2
недостающих каталога — `.agents` и `var`).

### Чего НЕ внесено и почему — это важнее того, что внесено

Замер по содержанию, а не по именам, нашёл ловушку:

| каталог | что внутри | вывод |
|---|---|---|
| `bin` | revoap.com: **6 рабочих PHP-скриптов** (`cache-purge.php`, `revoap-worker.php`); Clean_BOM_Senior: `bom.js`. В RdpMON тот же `bin` — сборка .NET | нельзя глобально |
| `cache` | revoap.com: 15 файлов кеша | безвредно, но не глобально |
| `obj` | RdpMON: 168 сгенерированных `.cs` | шум, но имя неоднозначно |
| `publish` | RdpMON: 406 файлов сборки, среди них `.html`/`.css`/`.js` | копии исходников |

При внесении `**/bin/**` в базовый список выпало бы **8 файлов**, включая
рабочие скрипты. Поэтому эти каталоги исключаются **в конфиге конкретного
корпуса** (в `rdpmon.yaml` это сделано) — там видно назначение.

### Неочевидная находка: сопоставление шаблонов регистрозависимо

```
**/cache/**   ловит  src/cache/X.php   но НЕ ловит  src/Cache/X.php
**/bin/**     ловит  bin/cache-purge.php            ← и это рабочий скрипт
```

Именно поэтому `src/Cache/CacheStatistics.php`, `src/Logs/LogsService.php`
и `src/Storage/*.php` в revoap.com **остаются в индексе**: их каталоги
написаны с заглавной буквы. Это случайное спасение, а не расчёт — и ещё одна
причина не вносить `cache`, `logs`, `bin` в базовый список.

### Проверка безопасности правки

Главный риск при расширении списка исключений — молча выбросить рабочий код.
Проверено:

- число файлов в каждом корпусе **не изменилось** (162 / 592 / 15 / 1266 / 6);
- все 7 проверяемых файлов кода из каталогов с «служебными» именами на месте;
- `init` на тестовом проекте исключил `.venv`, `__pycache__`, `target`,
  но сохранил `src/Cache/CacheStats.php`;
- базовые правила действуют во всех шести конфигах (28 из 28).

## 10. Что НЕ сделано и почему

- **`graph_gpu`: настройка включена, исполнителя в библиотеке нет.** Настройка
  есть в коде, панели и конфигах корпусов; решение владельца (9 октября 2026) —
  считать на карте, порог 5000 вершин. Но графовых алгоритмов (PageRank, обходы)
  в библиотеке не реализовано: измерительный код живёт только в проверочных
  скриптах каталога инструментов (`tools/analyze_gpu_graph.py`,
  `tools/check_graph_gpu_alt.py`), которые библиотека не использует. Поэтому
  включение настройки меняет только её значение: чтобы карта действительно
  считала граф, нужна реализация, а не переключатель.
- **CPG depth.** Слиты только рёбра `calls`; CFG/DFG/REACHING_DEF извлечены,
  но не слиты; `slice` использует собственный BFS, не настоящий PDG-слайсинг.
- **`batch` и `sql` — не деревом.** Это осознанное решение по замеру,
  а не недоделка. Если понадобится структура по SQL, потребуется отдельный
  разборщик: пакетная грамматика на реальных файлах не работает.
- **Кэш эмбеддингов запроса.** Поиск ~1 с против 0,5–3 мс у остальных
  операций. Осталось с прошлой сессии.
- **`obj` и `publish` исключены по имени каталога.** Проверено на этом
  проекте; в другом проекте содержимое может отличаться. Это допущение,
  а не универсальное правило — проверять при подключении.
- **Схлопывание не включено в остальных корпусах.** В z.batteryservice.ru,
  RdpMON и MD.Viewer дублей нет вовсе (замерено), поэтому настройка там
  не включалась: при нуле дублей она только изменила бы сумму корпуса.
  Включено в revoap.com, где дубли реально есть.

## 11. Ответ на вопрос «где смотреть ТЗ и правила»

Практический итог для агента: запрос в RAGRAF теперь возвращает роль
документа вместе с результатом.

- Технические задания: `doc_role = tech_spec`. В z.batteryservice.ru — 22 чанка,
  основной файл `docs/ТЗ-Документооборот-agreements.md`.
- Правила агента: `doc_role = agent_rules`. В каждом корпусе это `AGENTS.md`
  плюс контекстные документы (`docs/93-agent-context.md` в RdpMON).
- Планы: `doc_role = plan`. Отчёты: `doc_role = report`. Описания устройства:
  `doc_role = architecture`.

Рекомендация, вытекающая из разведки: если создаёте новое ТЗ, кладите его
в `docs/` и начинайте имя с `ТЗ-` или `TZ-` — тогда метка проставится
автоматически. Сейчас в четырёх проектах четыре разные схемы, и это
единственное, что мешает автоматическому распознаванию.
