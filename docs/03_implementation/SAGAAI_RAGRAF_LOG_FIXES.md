## 6. Интерпретатор RAGRAF: настоящая причина отказа

**Симптом.** Владелец повторил проверку и получил тот же отказ:
`operation=index_status` → код 2, «ошибка конфигурации: не установлен PyYAML».

**Первая версия диагноза была неполной.** Я проверял `import yaml` в своей
сессии и видел `6.0.3` — и решил, что зависимости на месте, а виноват только
испорченный маркер. Это было верно для сессии агента и неверно для приложения.

**Что показал замер.** PyYAML лежит не в самом vendor-Python AutoClaw, а в
пользовательском каталоге платформы:

```
C:\Users\<user>\AppData\Roaming\AutoClaw-oversea-official\toolchain\python\Python313\site-packages
```

Он подключается переменной `PYTHONUSERBASE`, и эта переменная задана **только в
сессии, которую создаёт AutoClaw** (`Process`-уровень). В реестре `User` и
`Machine` её нет. Приложение SagaAI, запущенное из проводника, работает без неё:

| Проверка | Результат |
|---|---|
| `PYTHONUSERBASE` — User | не задан |
| `PYTHONUSERBASE` — Machine | не задан |
| `PYTHONUSERBASE` — моя сессия | `...\AutoClaw-oversea-official\toolchain\python` |
| `import yaml` с переменной | `6.0.3` |
| `import yaml` без переменной | `ModuleNotFoundError` |
| RAGRAF без переменной (как приложение) | **rc=2, «не установлен PyYAML»** |

**Почему это было невидимо.** Маркеру `.interpreter` доверяли молча: ни один
кандидат не проверялся. Поэтому инструмент отвечал отказом конфигурации, хотя
рядом лежало рабочее окружение.

**Правка — две части.**

1. **Собственное окружение RAGRAF.** Создано `C:\AutoClaw\RAGRAF\.venv`
   (Python 3.14.7), установлены все зависимости из `requirements.txt`. Окружение
   автономно: `user site` отключён, поэтому оно не зависит ни от
   `PYTHONUSERBASE`, ни от настроек AutoClaw. Маркер `.interpreter` переключён на
   него. Замер `selftest`: все компоненты `[OK]` кроме `joern` (не установлен,
   для базового слоя не требуется).

2. **Проверка интерпретатора запуском** (`_has_yaml`) в функции RAGRAF SagaAI:
   берётся первый кандидат, который действительно может импортировать PyYAML.
   Маркер остаётся приоритетным, но перестаёт быть единственным источником
   истины. Проверено в четырёх условиях — выбор всегда верный.

**Проверка из окружения приложения** (без `PYTHONUSERBASE`, как запускается
сервис):

## 1. RAGRAF: операции `policy_trace` и `class_usage` не работали через CLI

**Симптом.** `python tools/ragraf.py query policy_trace --name X` завершался
кодом 2 «неверный аргумент», хотя операция есть в списке допустимых.

**Причина.** Обе операции объявлены в `OPS` (поэтому argparse их принимал),
реализованы в фасаде и доступны через MCP, но в диспетчере `dispatch_op` ветвей
для них не было — вызов доходил до конца функции и падал в
`raise SystemExit(EXIT_USAGE)`.

**Доказательство.** До правки: `query policy_trace --name can_act` → rc=2,
`query class_usage --mode missing` → rc=2. После правки: обе → rc=0.

**Правка.** `src/ragraf/cli.py:481` и `src/ragraf/cli.py:485` — добавлены ветви
диспетчера.

**Почему это не поймали раньше.** Существующий тест `tests/test_class_usage.py`
проверял наличие имени в исходнике (`"class_usage" in cli_src`) и доступность
через MCP — то есть декларацию, а не исполнение. Такая проверка проходит на
сломанном диспетчере.

## 2. RAGRAF: `--help` и русский вывод падали при не-UTF8 локали

**Симптом (из лога, дословно).**

```
UnicodeEncodeError: 'charmap' codec can't encode characters in position 174-188
  File "encodings\cp1252.py", line 19, in encode
```

**Причина.** RAGRAF выводит русский текст, но кодировку потоков не задавал.
Дочерний процесс, запущенный из Python без явной кодировки, получает на этой
машине cp1252, и справка не кодируется.

**Доказательство.** До правки: `PYTHONIOENCODING=cp1252` + `--help` → rc=1, та
же трассировка. После правки: rc=0, справка читается.

**Правка.** `src/ragraf/cli.py:988` — `_force_utf8_output()`, вызывается первым
действием `main` (до разбора аргументов, иначе справка всё равно падала бы).

## 3. RAGRAF: маркер интерпретатора «отравлялся» неудачным запуском

**Симптом (из лога).** Уже установленный PyYAML не находился: инструмент
постоянно отвечал «ошибка конфигурации: не установлен PyYAML».

**Причина.** `_remember_interpreter()` вызывался **первым действием** `main`, до
разбора аргументов и загрузки конфига. Любой запуск чужим интерпретатором
(например `.venv` SagaAI без PyYAML) записывал в `.interpreter` путь, который не
работает, и он оставался таким навсегда — а внешний инструмент SagaAI берёт
интерпретатор именно оттуда.

**Доказательство.** Воспроизведено: запуск `.venv` SagaAI → маркер изменён на
нерабочий путь. После правки: тот же запуск → маркер не изменился; успешный
запуск → маркер пишется.

**Правка.** `src/ragraf/cli.py:1012` — маркер пишется только после успешного
выполнения; лишняя запись не делается, если путь уже тот же.

## 4. SagaAI: `'NoneType' object is not subscriptable` в `run_code` / `run_test`

**Симптом (из лога).** Три вызова `run_code` вернули
`{"ok": false, "error": "'NoneType' object is not subscriptable"}`. Агент
прочитал это как поломку инструмента и ушёл на другой путь.

**Причина (найдена и воспроизведена точно).** В `subprocess.run(...)` указан
`text=True`, но не указан `encoding`. Вывод дочернего процесса декодировался
кодировкой, предпочитаемой **родителем**. Для piped-процесса на Windows это
ANSI-кодовая страница (cp1252), тогда как ребёнок мог писать UTF-8 или cp1251.
При несовпадении падал поток чтения, `proc.stdout` оставался `None`, и
следующая строка `proc.stdout[-4000:]` давала ровно это сообщение.

**Доказательство.** Воспроизведено дословно: дочерний процесс, печатающий
не-ASCII текст, возвращал `{'ok': False, 'error': "'NoneType' object is not
subscriptable"}`. После правки — структурированный результат.

**Правка.** `dev_agent/tool_executor.py`:
* `decode_child_output` (строка 469) — вывод читается **байтами** и
  декодируется цепочкой, уже принятой в проекте (`core.fs.decode_bytes`:
  utf-8 → cp1251 → latin-1; та же цепочка в `core/threads_devagent.py:456`).
  Одного `encoding="utf-8"` было мало: падение уходит, но вывод cp1251
  превращается в символы замены;
* `_run_child` (строка 496) — общий помощник для обоих инструментов;
* `run_test` (строка 1430) и `run_code` (строка 1527) переведены на него.

## Что осталось и требует решения владельца

1. **`slice` на корпусе SagaAI отдаёт код 3** — это правильное поведение, а не
   дефект: срез требует графа свойств кода (`capability=full`), а корпус
   `sagaai` в состоянии `degraded`, потому что Joern не смог экспортировать CPG
   (`ava.util.NoSuchElementException: next on empty iterator`). Экспорт CPG —
   отдельная задача.

2. **777 ошибок в полном прогоне `pytest` SagaAI** — это среда, не код: setup
   `tmp_path` падает с `PermissionError: [WinError 5]` при обходе каталога
   временных файлов. Проверено сравнением: с исходной и с исправленной версией
   `tool_executor.py` результат одинаковый. Рекомендация: задать pytest
   собственный `--basetemp`.

3. **Индекс корпуса `ragraf` (сам RAGRAF) не построен** — в его `.ragraf` нет
   каталога `index`, поэтому операции на этом корпусе отвечают «индекс не
   создан» (теперь кодом 3, как отказ слоя). Если нужен самоиндекс — отдельная
   задача: полная индексация каталога с JDK и GPU-библиотеками занимает время.

4. **«Мохнатый» русский текст в логе** (`R|# RAGRAF ? ????????????? ??????
   ????????????`) — артефакт самого диагностического скрипта SagaAI, который
   печатал результат через `encode('ascii', errors='replace')`
   (`Errors.html`, строки 561-590). Это не дефект продукта, поэтому не
   исправлялось.
