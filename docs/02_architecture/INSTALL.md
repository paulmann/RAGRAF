# Установка RAGRAF

Документ описывает установку Community-поставки на Windows 10/11 и Linux. Написано по
измерениям 23.11.2026: каждый шаг, названный здесь, был выполнен на этой машине
(Windows) или на `192.168.31.31` (Debian 12). Где прогона не было — сказано прямо.

## 1. Что нужно до установки

| Требование | Почему | Чем проверяется |
|---|---|---|
| Python 3.13+ **с модулем venv** | `pyproject.toml` требует `>=3.13`; окружение ставится в `venv` | `python -c "import sys,venv; print(sys.version_info[:2])"` |
| PowerShell 7.6 Core (Windows) | установщик — скрипт 7.6, Windows PowerShell 5.1 не поддерживается | `pwsh -v` |
| bash, python3-venv (Linux) | системная установка и `venv` | `bash --version`, `python3 -c 'import venv'` |
| 3 ГБ свободного места | venv с зависимостями (fastembed, torch-подобные колёса) | `scripts/install.ps1` проверяет сам |

**Ловушка, измеренная на этой машине.** `python` в PATH может оказаться интерпретатором,
встроенным в другое приложение: он проходит проверку версии (3.13.15), но **не имеет
модуля venv**, и установка падает уже после распаковки. Установщик поэтому перебирает
кандидатов (`PATH`, `%LOCALAPPDATA%\Python\bin`, `C:\Program Files\Python3*`) и берёт
первого с venv; остальных называет в шаге «Прочие Python».

**Ловушка Linux.** На Debian 12 системный Python — 3.11, пакета `python3.13` в
репозитории нет. Установщик отказывает с кодом 3 и называет причину. Для проверки на
хосте `192.168.31.31` Python 3.13.7 собран из исходников в домашний каталог
(`~/.local/python313`, `./configure --prefix=… && make && make install`) — это
тестовая мера, а не рекомендуемая: на боевой машине нужен пакет из backports или
собранный интерпретатор с сопровождением.

## 2. Windows 10/11

```powershell
# из распакованного архива: обёртка для Проводника — ragraf-setup.cmd
pwsh -NoLogo -NoProfile -File .\scripts\ragraf-setup.ps1 -DryRun          # план
pwsh -NoLogo -NoProfile -File .\scripts\ragraf-setup.ps1                  # установка в %LOCALAPPDATA%\RAGRAF
pwsh -NoLogo -NoProfile -File .\scripts\ragraf-setup.ps1 -Prefix D:\RAGRAF
pwsh -NoLogo -NoProfile -File .\scripts\ragraf-setup.ps1 -Uninstall       # программа уйдёт, состояние останется
```

Что делает установщик (порядок и отказы — часть поведения):

1. `pwsh` ≥ 7.6 Core, иначе код 3.
2. Каталог: умолчание `%LOCALAPPDATA%\RAGRAF`. Отвергаются: корень диска, домашний
   каталог целиком, `C:\Windows`, `Program Files`, каталог внутри индексируемого проекта
   (признак — `.ragraf` в каталоге или у родителя), чужой каталог с `.ragraf`, где нет
   пакета RAGRAF.
3. Python 3.13+ с venv; список отвергнутых кандидатов печатается.
4. Та же версия уже стоит → «уже установлено», установка пропускается, проверки
   ограничиваются `--version`, реестр не пишется (иначе `catalog/` менялся бы на каждом
   запуске — измерено).
5. Другая версия стоит → переносится в `<каталог>.bak-<yyyyMMdd-HHmmss>`.
6. Распаковка, затем `scripts\install.ps1` (зависимости; единственное место их установки),
   затем PATH пользователя (`<каталог>\.venv\Scripts`), чтение PATH после записи.
7. Проверки: `ragraf --version`, `ragraf ensure` на пробном проекте (нужны маркер проекта
   и ≥3 файла с кодом — иначе `ensure` честно отвечает `not_a_project`), `ragraf -p <конфиг
   пробы> check`, `ragraf edition --fingerprint`.

Итог печатается как: версия, каталог, отпечаток установки, что осталось настроить.

## 3. Linux (Debian 12)

```bash
# без sudo — в ~/.local/share/ragraf, симлинк в ~/.local/bin
bash scripts/ragraf-install.sh --dry-run
bash scripts/ragraf-install.sh
bash scripts/ragraf-install.sh --prefix ~/ragraf-test

# системная установка (root) — в /opt/ragraf
sudo bash scripts/ragraf-install.sh --system
sudo bash scripts/ragraf-install.sh --system --service   # плюс unit ragraf-watch.service

bash scripts/ragraf-install.sh --uninstall               # состояние сохраняется
bash scripts/ragraf-install.sh --uninstall --purge       # вместе с состоянием
```

Отличия от Windows-версии, названные явно:

- окружение ставится напрямую: `python3 -m venv` + `pip install -e ".[secrets]"`;
- PyNaCl обязателен: без него хранилище секретов и лицензия помечаются `unverifiable`,
  и издание **молча понижается до community** — поэтому `[secrets]` в установке не
  опционален;
- каталоги под `/opt` разрешены только с `--system`, `/var/www*` отвергается всегда;
- удаление и отказы по каталогу выполняются до проверки интерпретатора (измерено:
  `--uninstall` отказывал «нужен Python 3.13», хотя удалению он не нужен).

## 4. Обновление при живом состоянии

Обновление — это повторный запуск установщика с `-Upgrade` (Windows) или `--upgrade` (Linux).
Новый каталог собирается **рядом** (`<каталог>.new-<pid>`), в него переезжают состояние,
окружение и конфиги корпусов, затем два переименования — окно недоступности измеряется
миллисекундами, а не секундами.

| Что | Windows | Debian 12 |
|---|---|---|
| `catalog/`, `edition.license`, `.ragraf` | на месте, sha256 совпал | на месте |
| `config/` корпусов, созданных `ensure` | перенесён | перенесён |
| окружение | переезжает после подмены | переезжает после подмены |
| время | **7 291 мс** | **4 108 мс** |
| параллельные обращения к `--version` во время обновления | 55 обращений, **0 отказов** | 22 обращения, 5 отказов в полосе 58 мс |

**Четыре дефекта, найденные этими прогонами (все закрыты):**

1. Схема «унести в `.bak` → распаковать» держала каталог недоступным **2 678 мс**, и все
   пять параллельных обращений падали. Теперь — сборка рядом и подмена переименованием.
2. `config/` корпусов не переносился: после обновления реестр ссылался на конфиг, которого
   уже нет (`конфигурация не найдена`). Теперь конфиги переносятся — новые имена выигрывают,
   остальные копируются.
3. Editable-установка запоминает путь к `src/`: после переезда `ragraf --version` показывал
   **прежнюю** версию, и установщик падал на собственной проверке. Сначала лечилось так:
   `pip install -e . --no-deps` в промежуточном каталоге `<каталог>.new-<pid>`.
4. **Слово «окно в миллисекунды» было неправдой, пока окружение уносили в начале сборки.**
   Замер 23.11.2026 (Debian, 95 обращений за 9 с): 88 отказов — установка была сломана всё
   время сборки, а не на двух переименованиях. Теперь `.venv` остаётся на месте до подмены и
   переезжает из `.bak` третьим переименованием; пути внутри него не меняются, поэтому и
   `pip install -e` больше не нужен (он больше не попадает в окно). Тот же правка на Windows:
   перенос `.venv` из блока сборки убран, после подмены он делается мгновенно.

Замер после правки: Debian — 22 обращения, 5 отказов в полосе 58 мс (`529 → 587 мс` от начала
обновления), то есть окно ≈ 60 мс; Windows — 55 обращений за 7,3 с, **ни одного отказа**
(разрешение петли ≈ 130 мс на вызов, поэтому «ноль отказов» значит «окно короче 130 мс»).
Свойство «обновление не теряет состояние» закреплено проверкой №6 в
`tools/installer/selftest.ps1`, диагностика сбоя — №7, чужое состояние — №8.

**Маркер установки и отказ на чужое состояние.** Установщик пишет
`<каталог>/.ragraf/install.json`: `installer`, `install_path`, `version`, `written_at`.
Следующий запуск в каталоге, где маркер называет ДРУГОЙ путь, отказывает кодом 2
(«состояние принадлежит установке …»), а не перезаписывает чужую лицензию и чужой реестр.
Догадаться об этом по данным `.ragraf` нельзя: поля «чей индекс» в них нет — `meta.registry_owner`
называет каталог реестра, а `catalog_snapshot.json` — его кэш. Проверено на обеих платформах:
Debian — `ОТКАЗ: состояние в /home/cbs-test/rg-b/.ragraf принадлежит установке /home/cbs-test/rg-a`,
код 2; Windows — порча №8 самопроверки, код 2.

## 5. Служба: таймер проверки, а не демон сторожа

`--service` ставит не демон, а **таймер**: подкоманды `watch` в CLI нет, свежесть
сверяется внутри каждого вызова фасада. Поэтому юниты называются по делу:

- `ragraf-refresh.service` (`Type=oneshot`, `ExecStart=<bin> -p <конфиг> check`);
- `ragraf-refresh.timer` (`OnBootSec=5min`, `OnUnitActiveSec=<--refresh-minutes>min`, по умолчанию 15).

Запуск: `systemctl enable --now ragraf-refresh.timer`. Файл конфигурации обязателен:
без него установщик отказывает с кодом 2 и не пишет юнит (иначе systemd даёт `203/EXEC`).

Проверено на `192.168.31.31` 23.11.2026: таймер `active`, `list-timers` показывает
следующий запуск, ручной `systemctl start ragraf-refresh.service` даёт `Result: success`,
а в журнале — честный отчёт проверки («индекс устарел» с названной причиной).

**Три дефекта, которые вылезли только на живой службе:**

1. `User=nobody` + venv под `/opt` → `status=203/EXEC Permission denied`. Лечение: свой
   системный пользователь `ragraf` (создаётся установщиком), `chown` установки, `chmod a+rX`.
2. Интерпретатор из домашнего каталога служебному пользователю недоступен: shebang venv
   указывает в `/home/<кто-то>`. Теперь это отказ с кодом 3 и подсказкой
   «нужен системный Python 3.13 или `--service-user <владелец>`».
3. Юнит запускал `ragraf watch` — такой подкоманды нет вовсе. Отсюда таймер вместо демона.

## 6. Без сети

Установка без сети для pip не притворяется успешной. Замер 23.11.2026
(`PIP_INDEX_URL=https://invalid.invalid/simple`): `scripts/install.ps1` возвращает код 1,
установщик завершается кодом 1 и называет журнал зависимостей — никакого «готово».

Рабочий путь без сети — **обновление**, а не установка: окружение переносится из прежней
установки вместе с состоянием, pip не запускается вовсе. Тот же замер с недостижимым
индексом дал код 0 и сохранил реестр (sha256 `catalog/catalog.json` совпал).

## 7. Диагностика и первый запуск

`-Diagnose` (Windows) и `--diagnose` (Linux) печатают один блок для письма в поддержку:
версия ОС и оболочки, **все** найденные интерпретаторы с вердиктом по `venv`, состояние
установки (версия, `ragraf --version`, первые строки `status`), свободное место. Ничего
не меняется на диске; секретоносные пути не читаются.

**На сломанном окружении блок обязан назвать причину** — это проверено порчей №7 в
`tools/installer/selftest.ps1`: у установки удаляется `.venv`, и диагностика говорит
`«.venv\Scripts\ragraf.exe нет — зависимости не встали»`, а не «всё хорошо».

Заглушка Microsoft Store отвечает текстом вместо версии — в блоке она названа
«НЕ ЗАПУСКАЕТСЯ» с обрезкой до 70 символов, чтобы письмо оставалось читаемым.

**Без Python в PATH установщик всё равно находит интерпретатор** (`%LOCALAPPDATA%\Python`,
`C:\Program Files\Python3*`) и честно печатает отвергнутые. Отказ с кодом 3 остаётся только
когда подходящего нет вовсе — замер: `-PythonPath` на несуществующий путь → код 3 и
названная причина.

`-FirstRun <каталог>` / `--first-run <каталог>` — мастер первого запуска: `ensure` на
каталоге владельца, затем `status` с честным `capability`, затем первая выдача `search`.
Замеры на обеих платформах (23.11.2026): `ensure → created`, `capability=degraded` названо
предупреждением с причиной, `search` вернул **три адреса `файл:строка`**.

Три страховки на живом проекте (введены 23.11.2026, проверяются порчей №9 и №10):

| Что видит мастер | Что делает | Почему |
|---|---|---|
| в проекте `.ragraf/install.json` другой установки | отказ, называет путь установки-хозяина | чужой индекс нельзя перезаписать «мастером» |
| файлов больше 2 000 | отказ с указанием на `ragraf ensure <каталог>` | замер 23.11.2026: 500 файлов — 48 с, 2 000 — 501 с; кривая ≈ n^1,7, значит 20 000 это ≈10 часов. Предел = 10-минутный бюджет |
| проект под git без правила `.ragraf/` | предупреждение | иначе 300 МБ индекса попадут в `git status` |

Проверки данных идут ДО проверки окружения: чужий индекс и размер каталога — факты о
файлах, и они не должны зависеть от того, встали ли зависимости (замер: в песочнице без
`.venv` прежний порядок давал «без окружения первый запуск невозможен», и обе находки
оставались незамеченными).

## 9. Чего установщик не делает

Границы названы, чтобы их не искали в коде:

- **не ставит Joern и модель эмбеддингов** — без них издание честно `degraded`, с причиной;
  установка внешнего слоя — `scripts/install-joern.ps1`;
- **не подписывает код и не собирает MSI/MSIX** — нужен сертификат, это решение владельца;
- **не включает платное издание** — только кладёт рядом `catalog/` место для лицензии;
  лицензия выдаётся отдельно, отпечатком установки;
- **не переносит данные из чужой установки**: маркер называет другой путь → отказ кодом 2;
- **не трогает чужой корпус**: каталог с `.ragraf` и без `src/ragraf/__init__.py` отвергается
  кодом 2 (правило «чужое состояние»);
- **не правит PATH системно** без права: `--system` без root → код 3;
- **не проверяет сайт и не лезет в сеть** при `--skip-deps` и без сети; обновление без сети
  работает (реестр и лицензия остаются на месте).

## 10. Если установка отказала

Коды возврата одинаковы на обеих платформах: `0` — установлено, `1` — ошибка шага,
`2` — аргументы или опасный каталог, `3` — окружение (нет PowerShell 7.6, нет Python
3.13+ с venv, `--system` без root). Отказ всегда называет шаг и причину; строка с `FAIL`
— последняя перед «ОТКАЗ».

**Почему нужна именно граница Python 3.13 и что делать на Debian 12.** Граница
объявлена в `pyproject.toml` (`requires-python = ">=3.13"`) и ОДНИМ значением в каждом
установщике (`$script:MinPython = [version]'3.13'`, `MIN_PYTHON="3.13"`); согласие
трёх мест проверяет `python tools/check_python_floor.py`. Барьеров два, и оба честные:

* установщик отказывает кодом 3: «нужен Python 3.13+, найден 3.11 (`/usr/bin/python3`);
  на Debian 12 системный 3.11 — нужен 3.13 из backports или собранный» (замер 23.11.2026);
* если обойти установщик и собрать venv руками, откажет `pip`: `Package 'ragraf' requires
  a different Python: 3.11.2 not in '>=3.13'` — то же ограничение, второй раз и в другом
  месте, чтобы «почти поставилось» не вышло.

На Debian 12 есть два пути: `python3.13` из backports (если включён) либо собранный
интерпретатор — установщик принимает его через `RAGRAF_PYTHON` и сам проверяет модуль
`venv`. Проверено, что без этого не работает ни один путь; проверено ли, что работает
служба под 3.13 из backports на чистой Debian 12 — нет, и это названо в разделе 8.

Секретоносные пути установщик не читает и не печатает: ни ключ подписи
(`catalog/audit-signing.key`), ни файл лицензии. Он называет только отпечаток установки —
по нему выпускается офлайн-лицензия.
