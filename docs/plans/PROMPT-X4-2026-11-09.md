## 2. Задача этапа

1. **Один формат кейса на двух потребителей.** Не заводить два формата.
   Кейс: `id`, `kind` (`index` | `trace` | `bench`), `expected` (факты: файлы,
   имена, адреса), `required_steps` (например `[ensure, search_multi]`),
   `forbidden` (`[file_search, raw_read_of_code]`), `rev` (пин, может быть пуст),
   `note`. Хранение — файл на диске корпуса (например `quality-cases.yaml`)
   плюс разбор в `quality.py`; второго SQLite не заводить (C1 из плана).
2. **Журнал решений гейта.** `event_log` (или существующий журнал телеметрии)
   получает вид `gate_decision`: вердикт, причина, инструмент, `session_id`,
   `rev_id`. Без этого трассу нельзя восстановить по фактам — она останется
   пересказом.
3. **Трасса кейса.** Источник шагов — `usage_call` плюс `gate_decision`.
   Кейс падает, если обязательный шаг отсутствует ИЛИ был обход, даже когда
   текст ответа верный. Сбой сохраняется воспроизводимо: `rev`, `session_id`,
   отсутствующий/лишний шаг.
4. **Парный прогон `quality_pair(from_run, to_run)`.** Отдельная операция,
   `quality_diff` не трогать (C6).
   - per-case `better | worse | not_sure`;
   - агрегат НЕ имеет права сказать «не хуже», если хотя бы один ранее
     проходивший кейс упал: блокирующая находка `regression`;
   - одинаковые ревизии/состояния → все `not_sure` (честно, а не «улучшение»);
   - `pair_basis: "fixed_cases"` и обе ревизии — в ответе, а не только в
     документации.
5. **Бенчмарк без модели.** `quality_pair` умеет брать задачи `bench/tasks.yaml`;
   ожидаемые файлы/имена превращаются в машинную проверку (есть/нет в ответе
   операции), без LLM и без оценок «на глаз». Если задача не поддаётся машинной
   проверке — она помечается `not_machine_checkable`, а не выбрасывается молча.
6. **`digest` индекса от кейсов не меняется** (C7): ни кейсы, ни прогоны не
   входят в отпечаток индекса. Это проверяется свойством, а не обещанием.

## 3. Чего НЕ делать

- Не менять `quality_diff`: его отказ выносить вердикт между ревизиями —
  сознательное решение, а не дефект.
- Не заводить вторую базу/второй формат кейсов.
- Не вводить новых возможностей издания: `quality_pair` — расширение
  существующей `quality-loop` (Pro).
- Не ходить в LLM и сеть; наборы герметичны.
- Не коммитить: в дереве нет `.git`.
- Не переписывать историю в документах вне маркеров `surface:*` — числа
  меняются только через `surface_gen --write`.

## 4. Приёмка (`tests/test_quality_cases.py`, группа core, песочница %TEMP%)

1. Верный ответ без обязательного `ensure` → провал кейса с названным
   пропущенным шагом.
2. Обход через файловый поиск при наличии `forbidden` → провал с записью
   решения гейта (в трассе видно `deny`/`ask` и причину).
3. Один перевёрнутый кейс → агрегат не говорит «не хуже»: находка `regression`.
4. Одинаковые прогоны → все `not_sure`.
5. `digest` индекса до и после прогона кейсов совпадает (C7).
6. Детерминизм: два прогона на неизменном состоянии дают одинаковый отчёт.
7. Кейс с пустым `rev` не считается «свежим»: ответ называет, что пин не задан.
8. Без лицензии Pro операция отказывает, называя возможность `quality-loop`.

Дополнительно, в том же прогоне: `tests/test_quality_loop.py` — 158/0 (прежние
свойства не должны пострадать); `tests/test_provenance.py` — 42/0;
`tests/test_contracts_anchors.py` — 35/0; `tests/test_contracts.py` — 44/0.
