# Литература: что проверено и что из этого следует

**Метод:** поиск по arXiv API и официальным страницам; для каждой работы указан идентификатор, извлечённый в этом прогоне. Выдуманных ID нет: там, где ID подтвердить не удалось, стоит «ID не подтверждён», а не догадка.
**Статус:** обе волны выполнены. Незакрытые направления перечислены в §7 как **лакуны**, а не замаскированы пересказом.

**Ключевой вывод для §4 плана.** Ни одна из найденных работ **не измеряет деградацию агентской памяти со временем** (закрепление устаревшего вывода). То есть требование заказчика «накапливать различия, чтобы не делать неправильных выводов» соответствует признанной проблеме, для которой в литературе **нет готового измерения** — значит мерить придётся самим (метрика M5).

## 5. Инкрементальный анализ и устаревание

| Работа | ID | Суть | Числа | Что берём |
|---|---|---|---|---|
| **Incrementalizing Production CodeQL Analyses** | `arXiv:2308.09660` | Можно ли инкрементализировать продовый анализ кода; эмпирика + прототип инкрементального решателя | «update times **proportional to the size of the code change**» — множитель ускорения в аннотации не приведён | **Гранулярность дельты — размер изменения, а не «весь репозиторий».** И признание авторов: интерпроцедурность и context-sensitivity инкрементальность ломают |
| **FiD-Light** | `arXiv:2209.14290` | RAG возвращает не только ответ, но и **provenance items** из обновляемой базы знаний | SOTA на 6 задачах KILT | Минимальный стандарт: ответ обязан нести источник |
| **Crucible / Q&A Nuggets** | `arXiv:2601.13222` | Явный citation-provenance через банк «самородков» | TREC NeuCLIR 2024 | Провенанс через весь конвейер, а не только в ответе |

**Лакуна (честно):** прямых работ по «устареванию индекса для RAG» (index staleness / stale retrieval / temporal validity) **не найдено** — поиск по arXiv пуст. Ближайшая область, где формализуют интервалы валидности, — **битемпоральные графы и «as-of» запросы в БД**, но это не проверялось (вне бюджета). Классика инкрементального анализа (Vivien & Rinard PLDI 2001, IncA, Salsa, Incremental Datalog/DDlog, Soufflé) существует, но живёт вне arXiv и **по первоисточникам не верифицирована**.

**Вывод:** механизм «иммутабельный INDEX_REV + append-only ledger» мы проектируем сами, опираясь на: гранулярность по размеру изменения (CodeQL), обязательный провенанс (FiD-Light), версионирование контекста (Git Context Controller) и ключ инвалидации `files_touched` (Structured Distillation).

## 6. Противоречия, которые нельзя замалчивать

| Противоречие | Позиция A | Позиция B | Решение для нас |
|---|---|---|---|
| Давать ли исходник вместе с графом | RepBench: **graph-only > source+graph**; граф-онли 74,4%, а добавление исходника разбавляет контекст | Сам RepBench: на части memory-lifecycle кейсов source+graph не хуже; LLMxCPG вообще показывает исходник **в узлах среза** | Не фиксировать догму. `repo_map`/`impact` отдают структуру; `slice` отдаёт структуру **плюс** минимальные тела символов — и это проверяется метрикой M4 |
| Графовый индекс против просто большого контекста | RepBench: меньше кода, больше структуры | Длинноконтекстные модели тянут больше контекста; прямого сравнения граф-индекса с long-context-индексом нет | Решается только замером на нашем корпусе (M3) |
| Полнота против шума | Классический SAST жертвует точностью ради полноты | LLM даёт точность, но теряет полноту | Каждое ребро/факт несёт достоверность → агент сам решает, где перепроверить |
| Устойчивость к обфускации | Граф устойчив к переименованию | Границы среза ломает **вынос кода в функцию** (extract-method) | Отдельная категория записи в ledger + пересборка срезов после `reindex --commit` |

## 7. Чего не нашлось (лакуны, без маскировки)

1. **Дрейф/устаревание индекса для RAG** — прямых работ с arXiv-ID нет. Область закрыта частично битемпоральными БД и инкрементальным поддержанием представлений, но это не проверено.
2. **Деградация памяти агента со временем** (закрепление устаревшего вывода) — ни одной измерительной работы не найдено.
3. **Инкрементальный статический анализ для PHP/Python/JS** — не найден ни одной работы; единственная релевантная (CodeQL) про Java/JS-стек CodeQL.
4. **Измерений на прикладном (не memory-safety) коде** для задач «доработать/отрефакторить» — практически нет: подтверждённые числа статьи получены на C/C++ и поиске уязвимостей.
5. **ID для Risse & Böhme** — работа есть (USENIX Security 2024), arXiv-версия не найдена.
6. **LeanGuard** — не существует по этому названию (два независимых поиска).

## 8. Что из литературы входит в требования RAGRAF

| Источник | Требование |
|---|---|
| RepBench (`2606.25356`) | Отдавать **структурный контекст**, а не «файл целиком»; замерять сжатие (M4) |
| LLMxCPG (USENIX '25) | **Никакого свободного языка запросов** агенту — только фиксированные операции; пороги калибруются на ~20 примерах |
| ALIBI (`2607.24964`), Words Speak… (`2606.30587`) | Свободный текст — отдельный слой; ответы нейтральны по формулировке и всегда с провенансом |
| CLEAR (`2608.03134`) | Разделение ролей при проверке вывода: собрать → утверждать → критиковать → судить |
| RepoHyper (`2403.06095`), GraphRAG (`2404.16130`) | Операция `repo_map` с обобщениями по подсистемам |
| Repoformer (`2403.10059`), CODEFILTER (`2508.05970`) | Право не искать; выбраковка **вредных** чанков |
| LCIP (`1512.07435`) | Baseline M2: 69%/79%/55%; учиться на истории изменений |
| CodeQL incremental (`2308.09660`) | Гранулярность дельты — размер изменения; интерпроцедурность ограничивать явно |
| FiD-Light (`2209.14290`), Crucible (`2601.13222`) | Провенанс (`path:line` + ревизия) обязателен в каждом факте |
| Structured Distillation (`2603.13017`) | Ключ инвалидации — `files_touched`; эмбеддинг-поиск, а не только BM25 |
| Git Context Controller (`2508.00031`) | Версионирование контекста = иммутабельный `INDEX_REV` |
| Správa архитектурных знаний (`2601.19548`) | Ledger расхождений — признанное направление, проектируем явно |
| AdaRepair-Mem (`2609.20130`) | Накопление без фильтра **вредит** → обязательная дедупликация и арихивация ledger |
