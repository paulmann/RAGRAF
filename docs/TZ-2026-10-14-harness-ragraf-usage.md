## 2. ТЗ: требования к RAGRAF

Формат: **P0** — без этого использование невозможно, **P1** — снимает основные затраты,
**P2** — удобство и метрики. У каждого пункта критерий приёмки.

### P0-1. Регистрация корпуса и автоподхват проекта по рабочему каталогу

Сейчас: `config/bwo.yaml` есть, но `catalog.json` корпуса BWO не содержит; `use_project`
отвечает `found=False`; сервер продолжает отдавать `rdpmon`.

Требуется:
1. `ensure` (без аргументов и с `root`) обязан: найти существующий конфиг по корню,
   **зарегистрировать проект в реестре**, выбрать его текущим и указать это в ответе
   (`corpus.project`, `selected_by: root|config|registry`).
2. `use_project` обязан принимать путь и подхватывать уже существующий конфиг, а не только имя
   из реестра.
3. При нескольких корпусах — явный признак «корпус не тот» в каждом ответе, если проект
   текущего каталога отличается от активного (сейчас это молчаливая подмена — источник ложных
   фактов).

Приёмка: `ensure(root="C:/AutoClaw/BWO")` → `status=created|reindexed`, `project=BWO`;
повторный вызов → `actual`; `use_project("C:/AutoClaw/BWO")` → `found=True`.

### P0-2. `ensure` не должен висеть: исключения, лимиты, инкремент, прогресс

Факт: дерево 38 675 файлов / 2,3 ГБ, из них 27 254 `.FBO` (833 МБ) и 580 `.MOL` (220 МБ);
два вызова `ensure` не ответили за ~11 минут.

Требуется:
1. **Exclude по умолчанию** для «тяжёлых и не-кодовых» каталогов и расширений, с явным списком
   в конфиге: `uploads/**`, `*.FBO`, `*.MOL`, `*.CBT`, `*.gz`, `*.br`, `*.webp`, `*.svg`,
   `*.docx`, `*.exe`, `*.zip`, `Editor-PHP-*/**`, `full/**`, `img/**`, `vendor/**`,
   `node_modules/**`, `.git/**`, `*.min.js`, `*.min.css`.
   Для BWO это даёт ≈ 2 000–2 500 файлов вместо 38 675.
2. **Предварительная оценка объёма**: до индексации вернуть число файлов/байт и, если больше
   лимита, отказать с причиной и предложением exclude-правил (а не таймаут).
3. **Инкрементальная индексация** по (mtime, size), чтобы повторный `ensure` был ≤ 3 с.
4. **Никогда не отвечать таймаутом без деталей**: при превышении бюджета — ответ
   `status=timeout` с этапом, числом обработанных файлов и подсказкой.

Приёмка: холодный индекс BWO ≤ 60 с; тёплый `ensure` ≤ 3 с; на дереве с `uploads` индексация
не касается бинарных выгрузок; при превышении лимита ответ приходит ≤ 5 с и содержит причину.

### P0-3. `write_check` обязан видеть GENERATED/VIRTUAL и структуру ключей

Факт: два `INSERT` упали в MySQL («The value specified for generated column 'String Nominal
Voltage'…» и «Column count doesn't match»), ошибки нашлись только по ответу СУБД.

Требуется, чтобы `write_check(table, columns, operation)` возвращал:
* `missing` — колонок нет в таблице, с ближайшими существующими именами;
* `generated` — **отдельным списком**: колонки GENERATED/VIRTUAL, писать нельзя;
* `required` — NOT NULL без DEFAULT;
* `keys` — PK/UNIQUE (нужно для `ON DUPLICATE KEY UPDATE`);
* `check` — предупреждение, если число значений в плане не совпадает с числом колонок.
Дополнительно: `write_check_sql(sql)` — разбор готового INSERT/UPDATE по тексту.

Приёмка: для `TestConfig` с колонками `String Nominal Voltage`, `Duration Seconds` →
`generated` содержит их; для `TestData` — `Time Seconds`, `Real Time`, `Cell Voltage Middle`;
для `StringData` — `Power`, `Watt-hours`; при 17 значениях и 16 колонках приходит
предупреждение о несовпадении.

### P0-4. Атрибуция обращений к задаче

Факт: `by_task = "(без задачи)"` — по журналу нельзя понять, на какой вопрос ушёл индекс.

Требуется: `ragraf_task(name)` (или авто-метка из первой фразы хода) + группировка `usage` по
задачам с полями: обращений, фактов, ошибок, `misses` (запросов без фактов), оценка
«заменённого чтения» (`est_lines_not_read` уже есть).

Приёмка: `usage(scope=session)` показывает задачи с осмысленными именами; по каждой видно
число обращений и найденных фактов.

### P1-1. Поиск «одним ответом»: `search_multi` с учётом копий и кодировок

Факт: «Allowed formats» и списки расширений живут в 10 файлах (8 копий `Files*.php`,
`upload.php`, `templates/Files.html`), причём часть файлов — в cp1251 (`upload.php`,
`mysql_stdin.pl`, `import*.pl`), часть — в UTF-8.

Требуется: один вызов с массивом запросов (literal + regex), поиск с учётом кодировок
UTF-8/CP1251/UTF-16, группировка результатов по семействам файлов, пометка «активный файл /
копия / не подключён», приоритет точек входа.

Приёмка: запрос `["Allowed formats", "fileExtensions", "'MCH', 'MOL'"]` возвращает все
вхождения, сгруппированные, с указанием, что активен `php/Wizard/Files7.php` (подключён из
`templates/Files.html`), ≤ 2 с.

### P1-2. Копии, «мёртвый» код и точки входа

Факт: в BWO рядом живут `import.pl`, `import1.pl`, `import2.pl`, `import_stdin.pl`, `index.pl`,
`mysql_stdin.pl`, `mysql_least.pl`, `Files.php`…`Files7.php`; я определял активные вручную по
ссылкам в JS и шаблонах.

Требуется:
* `duplicates` — группы почти-дубликатов (по структуре, не только по хешу) с оценкой различий;
* `dead_code` — файлы/подпрограммы без входящих ссылок (ни из кода, ни из шаблонов, ни из роутов);
* `entrypoints` — роуты, endpoint'ы, `action=`, `source`, подключения скриптов; для каждого
  файла — «достижим ли из точки входа».

Приёмка: `duplicates(scope="php/Wizard")` → группа {Files.php…Files7.php} с пометкой, что
`Files7.php` используется (`BWO_FILES_ENDPOINT` в `templates/Files.html`), остальные —
кандидаты на удаление; `dead_code` по `cgi-bin` → список с обоснованием.

### P1-3. Полиглот: PHP + Perl + JS + HTML-шаблоны + SQL

Факт: корпус BWO — смесь языков, включая Perl (`import.pl` 113 КБ, 1 900 строк) и шаблоны с
плейсхолдерами `%{Key}`, `@{Key}`, `<!--#include virtual-->`.

Требуется:
* разбор Perl: подпрограммы, пакетные переменные (`$FORMAT`, `%hFORMAT`, `%dFORMAT`), вызовы;
* разбор HTML-шаблонов: плейсхолдеры как «литеральные якоря» (поиск «где ожидается ключ»);
* связь «шаблон ↔ ключи переводов» (например, какие ключи `Translate` реально используются);
* SQL внутри PHP/Perl (heredoc, `$dbh->do`) — как обращения к таблицам для `table_usage`.

Приёмка: `search("hFORMAT")` в Perl даёт `cgi-bin/import.pl:438`; `search("reg.months")`
находит и таблицу переводов, и использование; `table_usage("StringData", mode=write)` находит
`BCTC_Import.php`, `BWO_Import.php`, `BSL_o3_Pro_5.php`.

### P1-4. БД: живая схема, сверка с миграциями, write-path

Требуется:
* `schema` — пометки `generated`, `pk`, `unique`, `auto_increment`, типы;
* `db_drift` — сверка живой схемы с миграциями проекта (в BWO это реально: таблицы `BWO_*`
  и `bct_c_1000_Header` появляются миграциями, а база может их ещё не иметь);
* `table_usage` — не только имя таблицы в SQL, но и «кто пишет» с учётом подготовленных
  выражений.

Приёмка: `db_drift` показывает отсутствующие в базе таблицы из `db/migrations`; `schema("TestConfig")`
помечает пять генерируемых колонок; `table_usage("cellvoltagedata", mode=write)` находит новый
загрузчик.

### P2-1. Диффы между ревизиями

`ragraf_diff(since=rev)` — что изменилось: файлы, символы, схема. Нужно, чтобы после серии моих
правок видеть регрессии («эта функция больше нигде не вызывается», «таблица перестала
заполняться»).

### P2-2. Ответы, а не сырые хиты

Режим `answer=true`: сформулированный ответ + ссылки `файл:строка`, без служебных полей
(`brief` уже есть — расширить до «ответа»). Цель — ≤ 1–2 КБ на типовой вопрос.

### P2-3. Память о решениях

`ragraf_note(task, text)` / `ragraf_notes(task)` — короткие записи вроде «в MySQL часть колонок
генерируемые — писать нельзя», чтобы не переоткрывать найденное в следующей сессии.

### P2-4. Метрики эффекта

В `usage` добавить: `saved_calls` (сколько grep/read заменено), `hit_rate`, `avg_ms`,
`stale_served` (ответов со `stale=true`, должно быть 0), `misses`. Без этого нельзя доказать,
что индекс окупается.

## 3. Что нужно сделать, чтобы HARNESS использовал RAGRAF **всегда**

Правило в AGENTS уже есть, но оно не работает: в последнем ходе я не сделал даже `ensure`.
Нужны три вещи — триггеры, принуждение и дешевизна.

### 3.1. Триггерная таблица вместо общего правила (в AGENTS)

| Перед чем | Обязательный вызов |
|---|---|
| Первое обращение к коду проекта в ходе | `ensure` (с `root` текущего проекта) |
| Поиск строки, файла, символа | `search` / `search_multi` / `symbol` |
| Правка файла, функции, класса | `impact` (что затронет) |
| Любой `INSERT`/`UPDATE` | `write_check` |
| Правка прав/доступа | `policy_trace` |
| Создание таблицы/колонки | `schema` / `db_schema` (не дублировать существующее) |
| Конец хода | строка отчёта: сколько обращений, что дали, почему 0 (если 0) |

Отдельно: **если корпуса нет** — не делать вид, что индекс проверен, а прямо писать
«корпуса проекта в реестре нет, факты из чтения файлов» (так было в ходе про FBO — и это
правильно), и **сразу предлагать зарегистрировать корпус**.

### 3.2. Технический гейт в HARNESS (принуждение)

Предлагаю добавить в DSH middleware на инструменты `pwsh` и `read`:
* если аргументы содержат `Select-String|rg|findstr|Get-ChildItem -Recurse` и путь внутри
  корпуса проекта, а в сессии **не было** `ensure` для этого корпуса — вернуть предупреждение
  с готовой подсказкой (`ragraf_search(query)`), а при повторном нарушении в том же ходе —
  отказать один раз с текстом «сначала индекс, потом grep»;
* если корпус есть, а grep всё же вызван, — писать в журнал `usage` событие `bypass_grep`
  (чтобы это было измеримо).

Это не «запрет на grep»: при отсутствии корпуса или при поиске вне проекта (логи, временные
файлы, чужие каталоги) grep остаётся законным и нужным.

### 3.3. Сделать индексный путь дешевле grep'а

Чтобы я выбирал индекс не по принуждению, а по выгоде:
1. `ensure` ≤ 3 с (P0-2);
2. компактные ответы по умолчанию (P2-2);
3. готовые «рецепты» в навыке `ragraf-core`: 10 типовых запросов
   («где выводится строка», «все списки расширений», «кто пишет в таблицу», «какие ключи
   перевода есть», «что затронет правка кнопки», «какие файлы — копии», «генерируемые колонки
   таблицы», «поиск в cp1251», «точки входа», «дифф после правок»);
4. `search` должен выигрывать у grep'а не только точностью, но и форматом: сразу
   сгруппированные места + пометка активного файла.

### 3.4. Метрика приёмки для «использует всегда»

* ≥ 80 % задач по BWO — хотя бы одно обращение к индексу;
* 0 случаев «grep по коду проекта при наличии корпуса без `ensure`»;
* доля задач, где индекс дал хотя бы один подтверждённый факт со ссылкой, ≥ 50 %;
* `stale_served = 0`;
* в отчёте каждой задачи по коду — строка про использование RAGRAF.

## 4. Порядок работ (предложение)

1. **P0-1 + P0-2** (регистрация и быстрый `ensure`): после этого корпус BWO появляется в
   реестре и индекс начинает работать — это разблокирует всё остальное.
2. **P0-3 + P0-4** (write_check и задачи в журнале): снимает реальные падения при записи в
   базу и делает эффект измеримым.
3. **P1-1…P1-4** (поиск, копии, полиглот, БД): основной выигрыш по шагам.
4. **3.2** (гейт в HARNESS) — после того, как индекс станет быстрым и полезным; иначе гейт
   будет мешать.
5. **P2** — по мере надобности.

Ожидаемый эффект по этому проекту: 25–35 сэкономленных шагов на каждой крупной задаче
(добавление формата, починка импорта, правка отчёта) и отсутствие ошибок вида
«писать в генерируемую колонку», каждая из которых сейчас стоит 2–3 прогона.

# Статус P0: что сделано 2026-10-14 (HARNESS)

## P0-1. Регистрация корпуса и автоподхват проекта — сделано в основном

* `ensure(root)` сам нашёл конфиг `config/bwo.yaml`, **зарегистрировал** корпус и вернул
  `category: BWO`, `config`, `rev_id` — раньше `use_project` по этому пути отвечал `found=False`.
  В `catalog/catalog.json` появилась запись: `category=BWO`, `root=C:/AutoClaw/BWO`,
  `config=…/bwo.yaml`, `project=BWO`.
* Замечание из прогона: у записи после `ensure` счётчики `file_count/node_count/edge_count`
  остались нулями, хотя прямой `index` построил 162 381 узел и 701 120 рёбер. То есть
  `ensure` для **уже известного** корпуса не переносит результат прогона в реестр так же
  надёжно, как для нового, и не сообщает, что прогон вышел пустым. Это следующий шаг.

## P0-2. Бюджет времени и предел объёма — сделано, проверено на BWO

Реализовано:
* `config.py`: `index.budget_seconds` (по умолчанию 120) и `index.max_files` (20000);
* `ensure(..., budget_seconds=..., max_files=...)`: отказ при превышении `max_files`
  с числами и подсказкой про exclude; бюджет прокидывается в прогон;
* `indexer.run(..., budget_seconds=...)`: дедлайн, проверки после стадий (ast, schema, lexvec),
  быстрый режим (без CPG) при остатке меньше 45 с, поле `budget_exceeded` в отчёте;
* `watch.check(..., budget_seconds=...)` и `run_reindex(...)` — авто-реиндексация тоже
  ограничена бюджетом;
* `EnsureOutcome` получил статус `partial` (прогон прерван по бюджету: ревизия не закреплена,
  прежний индекс рабочий).

Проверено на BWO:
* до правок `ensure` дважды не отвечал (~11 минут таймаута на стороне клиента);
* после правок `ensure` **отвечает**: сверка и регистрация корпуса — 6,7 с (4645 файлов);
* прямой `index` собрал корпус полностью: rev-0003, файлов 4645, узлов 162 381,
  рёбер 701 120, чанков 102 433, capability=full, 655 с;
* поиск по собранному корпусу работает: запрос «Allowed formats» вернул все копии
  `php/Wizard/Files.php`, `Files1…Files6.php` с диапазонами строк (то, что я раньше искал
  грепом руками).

Замечание: бюджет соблюдается не строго — проверки стоят **между** стадиями, поэтому
длинная стадия (ast 325 с, lexvec 146 с) может его превысить. Нужны проверки внутри стадий
или перед ними.

## P0-3. `write_check` и генерируемые колонки — код готов, проверка не завершена

Реализовано в `facade.op_write_check`:
* читается **живая** схема (`db_live_column`, `db_live_table`), а не только миграции;
* в ответе: `generated_columns`, `generated_requested`, `live_only_columns`, `keys_live`
  (primary/unique), `values`, `values_mismatch`;
* проблема формулируется явно: «нельзя писать в генерируемые колонки (значение считает СУБД)»
  и «число значений (N) не равно числу колонок (M)»;
* параметр `values` добавлен в MCP-схему инструмента и в CLI (`--values`).

Проверка на BWO **не выполнена**: слой схемы корпуса пуст (`schema: 0 таблиц — SQL-миграции
не найдены`), потому что в `bwo.yaml` стоит `db: enabled: false`. Нужно либо включить слой баз
(и дать доступ к локальной копии `wizard_online`), либо убедиться, что миграции проекта
разбираются без слоя баз. До этого подтверждения пункт считается незакрытым.

## P0-4. Атрибуция обращений к задаче — частично

* В RAGRAF уже есть поддержка `RAGRAF_TASK` (`cli.py: _task_from_env`), она используется
  командами CLI. В прогоне переменная выставлялась, но подтверждения из журнала я не
  получил: вывод `usage` в CLI не показал строк по задачам.
* MCP-сервер `RAGRAF_TASK` не читает: `Facade` создаётся без `task=` (`mcp_server.py`,
  создание фасада), поэтому в журнале остаётся `by_task = "(без задачи)"`.
* Что нужно: либо читать переменную при создании фасада в MCP-сервере, либо добавить
  инструмент `ragraf_task`, который выставляет метку на текущий ход, и вызывать его
  из HARNESS перед работой. Со стороны HARNESS — выставлять метку задачи на каждый ход.
