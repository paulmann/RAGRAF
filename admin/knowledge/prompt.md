## 0. Роль и режим работы

Ты — старший инженер-владелец сквозного контура знаний LLM-агентов. Твоя работа — не «добавить поиск по истории», а построить **производный слой знаний**: по вопросу находить агента, который уже решал похожую задачу, нужный навык и накопленный опыт, а агенту-руководителю давать возможность передать задачу подходящему агенту вместе с полным контекстом.

Порядок работы обязателен:

1. **Сначала факты.** Прочитай существующие пакеты DSH (`dsh-session-query*`, `dsh-skill*`, `dsh-settings`, `dsh-schedule`, `dsh-experimental-agent-team`, `dsh-subagent`) и подтверди допущения по коду. Не проектируй заново то, что уже реализовано.
2. **Потом ADR.** Согласуй архитектуру, модель данных, ранжирование, приватность и границы интеграции до написания кода. Один короткий ADR лучше тысячи строк преждевременного кода.
3. **Потом реализация по этапам.** P0 — индекс и поиск, P1 — карточки навыков и диспетчеризация, P2 — семантика и обратная связь.
4. **На каждом шаге — доказательства.** Ссылки `файл:строка`, замеры, тесты. Факт без ссылки — гипотеза; гипотезу помечай явно.

Не задавай вопросов, ответ на которые есть в репозитории. Спрашивай только о продуктовых развилках, перечисленных в разделе 14.

## 1. Продуктовая цель

Сделать так, чтобы человек и агент-руководитель за один запрос получали ответы на четыре вопроса:

1. **Кто?** — какой агент (или сессионный актор) уже занимался этой задачей и с каким результатом.
2. **Что?** — какие навыки, знания, артефакты и решения по теме уже накоплены.
3. **Насколько это применимо?** — чем именно этот опыт релевантен новой задаче, какие ограничения и риски.
4. **Как передать?** — как поставить задачу выбранному агенту (или его реплике) с контекстом, критериями приёмки и ссылками на доказательства.

Ключевой результат: **сократить путь от вопроса до компетентного исполнителя** и не заставлять агента-руководителя вручную перечитывать историю сессий.

## 5. Функциональные требования

### FR-1. Настройки и включение

1. В Settings появляется секция **«Знания агентов»** (`agent-knowledge`).
2. Главный переключатель **включён по умолчанию**; отключение:
   - останавливает индексацию и таймеры;
   - скрывает/деактивирует инструменты (`KNOWLEDGE_DISABLED`);
   - показывает в UI честное состояние «выключено»;
   - по выбору пользователя сохраняет или удаляет индекс.
3. Настройки хранятся через `dsh-settings` (волатильные поля + профильный patch), применяются без перезапуска, где это возможно.
4. Секция содержит: статус, расписание, источники, приватность, действия, ссылку на поиск.

### FR-2. Индексация

1. По умолчанию — **2 раза в сутки**, локальное время `03:00` и `15:00`; список времён и таймзона настраиваются.
2. Инкрементальный режим: индексируются только изменившиеся сессии/навыки/строки AutoClaw.
3. Пропущенный запуск: догоняется **только последний**; одновременно два запуска не выполняются (lock).
4. Запуск при старте, если индекс устарел больше чем на `stale_after_hours` (по умолчанию 24).
5. Ручной запуск:
   - инструмент `knowledge_reindex` (агентом),
   - кнопка в UI,
   - CLI-команда для ops.
   Режимы: `incremental` (по умолчанию), `full`, `verify`; прогресс, отмена, идемпотентность.
6. Каждый прогон пишется в `ak_index_run`: время, режим, источники, counts, длительность, ошибки, `index_rev`.
7. Полная пересборка — в отдельную БД/поколение с атомарной заменой; старая версия доступна до успешного завершения.

### FR-3. Источники и адаптеры

1. **DSH**: сессии (live + persisted) через `ctx.sessionQuery`, проекции, реестр workspace'ов, каталог навыков.
2. **AutoClaw 2**: read-only адаптер; обнаруживает аккаунты и БД, читает `work_sessions`, `work_runs`, `work_events`, `neutral_session_entries`, `memory_assets`, `agents`, `collaboration_run_agent_*`, навыки и ledger.
3. **Навыки**: frontmatter + тело + список ресурсов (пути, без встраивания бинарников), хэш/версия.
4. Для каждого источника: `source_state` (ревизия, последняя индексация, counts, schema version, ошибка), деградация без падения.
5. Запрещено писать в исходные БД и логи. AutoClaw открывается только `mode=ro` с таймаутом и retry/backoff.
6. Схема AutoClaw может дрейфовать: адаптер проверяет наличие таблиц/колонок и честно сообщает `SOURCE_SCHEMA_UNSUPPORTED`.

### FR-4. Модель знаний

Обязательные сущности (имена с префиксом `ak_`):

- `ak_actor` — актор, его вид, источник, имя, workspace, первый/последний запуск, модель, статистика.
- `ak_episode` — эпизод: заголовок, цель, ограничения, итог, статус, время, длительность, токены, workspace, `actor_id`, `session_id`, диапазон событий.
- `ak_event` — нормализованное событие (роль/тип, текст, инструмент, путь, время, ссылка на исходный seq).
- `ak_skill` — навык: имя, описание, `whenToUse`, путь, хэш, версия, источник, ресурсы.
- `ak_skill_use` — факт применения навыка актором в эпизоде (из `tool/call name=skill`, `/name`, ledger/истории).
- `ak_artifact` — артефакт: файл, отчёт, презентация, коммит, ссылка; provenance.
- `ak_memory` — память (AutoClaw `memory_assets`; в DSH — извлечённые решения, если включено).
- `ak_relation` — рёбра: `actor—did→episode`, `episode—used→skill`, `episode—produced→artifact`, `episode—about→topic`, `skill—related→skill`.
- `ak_assignment` — выданная задача: кому, кем, когда, статус, `dispatch_id`, provenance.
- `ak_index_run`, `ak_source_state` — служебные.
- `ak_document` + `ak_fts` (FTS5) — поисковые документы; `ak_vector` — опционально.

Требования к извлечению эпизода:

- цель — первый содержательный запрос пользователя (не системный промпт);
- ограничения и критерии — из сообщений, `todos`, `plan`, `goal`;
- действия — инструменты, файлы, команды;
- результат — финальный ответ, `deliverables/presented`, `workspace/changes`, статус;
- ошибки/повторы — `run.failed`, `tool/result` с ошибкой, compaction;
- навыки — `tool/call` с именем `skill` и аргументом `name`;
- участники — `agentTeam`, `subagent`, `collaboration_run_agent_participations`;
- доказательства — исходные `session_id` + `event_seq` / `entry_id`, чтобы результат можно было проверить.

Детерминированное извлечение обязательно. LLM-суммаризация — **опция**, по умолчанию выключена; при включении явно предупреждать о передаче текста провайдеру.

### FR-5. Поиск

Режимы:

| Режим | Что возвращает |
|---|---|
| `find_agent` | Ранжированные акторы + доказательства + пригодность к диспетчеризации. |
| `find_skill` | Ранжированные навыки + доказательства применения + пригодность к задаче. |
| `find_knowledge` | Эпизоды/решения/артефакты/память. |
| `get_agent` / `get_skill` / `get_episode` | Полная карточка по id. |

Требования:

1. Гибридный поиск: лексика FTS5 (BM25) + опционально вектор; слияние RRF; фильтры.
2. Фильтры: источник, workspace, вид актора, дата, статус/итог, навык, модель, «только успешные».
3. Ранжирование актора: агрегация по эпизодам, а не «один лучший документ»:
   `score = max(rel) + 0.3·mean(top3) + 0.2·recency + 0.2·success + 0.1·same_workspace + 0.1·skill_overlap`.
4. Диверсификация (MMR), чтобы один актор не занимал всю выдачу.
5. Каждый результат обязан содержать сниппет-доказательство и ссылку на источник.
6. Детерминизм: при равных score — порядок по времени и стабильному id; одинаковый `index_rev` даёт одинаковый результат.
7. Пустой результат — валидный ответ с причиной, подсказками (расширить фильтры, переиндексировать) и без выдуманных агентов.
8. Поддержка русского и английского: триграммы/префиксы, нормализация регистра, точный boost для идентификаторов, опциональные синонимы.
9. Пагинация курсором; лимиты и бюджеты токенов; полные тела — только в `get_*`.

### FR-6. Карточка навыка («все данные о навыке»)

`knowledge_get_skill({name, task?})` возвращает:

- frontmatter и полное тело `SKILL.md`;
- `whenToUse` и признаки `disable-model-invocation` / `user-invocable`;
- ресурсы: пути/URL/описания (не содержимое бинарников);
- версия/хэш/источник/дата, история версий (если есть ledger);
- статистика использования: сколько раз, кем, когда, в каких эпизодах, с каким итогом;
- связанные навыки, дубликаты/конфликты;
- «пригодность для задачи»: 3–5 тезисов, ограничения, типовые ошибки, чек-лист применения;
- provenance: откуда взято, как проверить.

Если передан `task`, карточка должна быть **ответом на задачу**, а не просто энциклопедией: что применить, чего избежать, какие шаги и доказательства.

### FR-7. Диспетчеризация задач агентом-руководителем

Инструмент `knowledge_dispatch`:

Вход:

```json
{
  "task": {
    "title": "Короткое имя задачи",
    "description": "Что сделать",
    "acceptance_criteria": ["..."],
    "constraints": ["..."],
    "deadline": "2026-10-30T18:00:00+03:00"
  },
  "target": {"mode": "auto", "actor_id": null, "count": 1},
  "strategy": "best_fit",
  "dry_run": true,
  "commit": false,
  "context": {"include_episodes": 3, "include_skills": true, "include_artifacts": true}
}
```

Поведение:

1. При `dry_run`/`commit=false` — только план: выбранные акторы, обоснование, пакет контекста, риски. Ничего не запускается.
2. При `commit=true` и явном намерении пользователя/руководителя:
   - **актор текущей команды** → `team_task_create` + `send_message`;
   - **исторический актор DSH** → `spawn_teammate` с ролью-репликой (имя, описание, brief) + задача + сообщение; либо рекомендация возобновить сессию, если это поддерживается;
   - **сохранённый агент AutoClaw** → сформировать handoff-пакет (задача + контекст + критерии + ссылки) и пометить `dispatch_mode: external_handoff`; **не писать** в БД AutoClaw без отдельного одобренного интеграционного контракта;
   - **нет подходящего актора** → вернуть честный отказ и предложить создать нового.
3. Пакет контекста: цель, ограничения, критерии приёмки, топ-доказательства, инструкции навыков, прошлые артефакты, известные ошибки, ссылки.
4. `dispatch_id` идемпотентен: повтор с тем же id не создаёт дубль.
5. Запись в `ak_assignment`: кто, кому, когда, почему, какие доказательства, статус.
6. Запрещено автономно запускать внешних агентов, тратить деньги или писать в чужие системы без явного подтверждения.

### FR-8. Забывание, исключения, retention

- Исключения: workspace, путь, сессия, актор, шаблон файла.
- «Забудь сессию/актора/навык»: удаление документов, FTS, векторов, связей; проверка отсутствия остатков.
- Retention по умолчанию 180 дней (настраивается); очистка по расписанию.
- Удаление индекса целиком; при выключении — выбор «оставить/удалить».
- Секреты и персональные данные вычищаются **до** записи в индекс.

### FR-9. Статус, наблюдаемость, обратная связь

- `knowledge_status`: включено/выключено, `index_rev`, последний/следующий запуск, длительность, counts по источникам, размер БД, покрытие, ошибки, деградации.
- Обратная связь: «полезно/не полезно», выбранный актор/навык; хранится без содержимого, влияет на ранжирование.
- Логи без содержимого; метрики: документы, попадания, пустые выдачи, latency, ошибки.
- UI показывает честные состояния: `not_ready`, `stale`, `degraded`, `disabled`, `error`.

### FR-10. Паритет поверхностей

Одна и та же операция доступна:

- агенту — через инструменты;
- человеку — через UI;
- ops — через CLI.

## 6. Нефункциональные требования

| Категория | Требование |
|---|---|
| **Локальность** | По умолчанию никакой передачи содержимого за пределы машины. Семантика/LLM-суммаризация — только opt-in с предупреждением. |
| **Безопасность** | Редакция секретов и PII до записи; файлы индекса `0600`, каталоги `0700`; untrusted-контент не исполняется; защита от prompt injection. |
| **Источники** | Read-only; AutoClaw БД не изменяется; исходные сессии не переписываются. |
| **Производительность** | Incremental ≤ 60 с на 200 сессий/100k событий; поиск P95 ≤ 300 мс на 100k документов; RAM ≤ 500 МБ; БД ≤ 2 ГБ. |
| **Надёжность** | Crash-safe: WAL, транзакции, resumable cursor, атомарная замена поколения; повторный запуск идемпотентен; нет частично видимого индекса. |
| **Конкурентность** | Один владелец индекса (lock); второй процесс — read-only или ждёт; таймеры не дублируются. |
| **Детерминизм** | Стабильные id, сортировки, сериализация; одинаковый вход → одинаковый `index_rev`. |
| **Масштаб** | 1M документов, пагинация, инкрементальность, retention. |
| **Приватность** | Исключения, забывание, retention, отсутствие телеметрии содержимого. |
| **Локализация** | RU/EN интерфейс и описания инструментов; корректная работа с кириллицей. |
| **Совместимость** | Не ломать существующие `session-query`, `skill`, `settings`, `schedule`, agent-team; учитывать schema drift. |

## 7. Архитектура и ограничения

1. **Производная БД, не источник истины.** Отдельная `~/.dsh/storages/agent-knowledge/knowledge.sqlite` (WAL). Индекс можно удалить и пересобрать.
2. **Максимально переиспользовать существующее:**
   - включить персистентный `dsh-session-query-sqlite` (`path` вне `sessions`, `openAt: startup` или `first-search`);
   - читать историю через `ctx.sessionQuery`, а не парсить zstd вручную;
   - каталог навыков — через `ctx.skills`; тело — по требованию;
   - настройки — `dsh-settings`; расписание — `dsh-schedule`/timer; фоновые задачи — `dsh-jobs-local`;
   - диспетчеризация — agent-team tools, не собственный мессенджер.
3. **Если API не хватает** — узкий адаптер, а не форк пакета.
4. **Один владелец индекса.** Lock-файл; при втором экземпляре — read-only или ожидание.
5. **Схема и миграции.** `schema_version`, идемпотентные миграции, проверка целостности, `verify`-режим.
6. **Источники разделены.** DSH и AutoClaw индексируются независимо; падение одного не ломает другой.
7. **Никакой записи в AutoClaw** без отдельного утверждённого контракта. Сейчас — только чтение.
8. **Не дублировать session-query БД.** Если возможно, хранить ссылки (`session_id`, `event_seq`), а не копии событий; дублирование допускается только для нормализованных документов с обоснованием.

## 9. UX

### 9.1. Settings → «Знания агентов»

1. **Верхняя карточка:** toggle, статус (`Активен`, `Индексируется`, `Устарел`, `Ошибка`), `index_rev`, последний/следующий запуск.
2. **Расписание:** «2 раза в сутки» по умолчанию; время, таймзона, «догонять пропущенный», «при старте, если устарел».
3. **Источники:** HARNESS (сессии/навыки), AutoClaw 2 (БД/навыки, read-only), счётчики и статус.
4. **Действия:** «Переиндексировать», «Полная пересборка», «Проверить целостность», «Очистить индекс»; прогресс и отмена.
5. **Приватность:** локальный режим (badge), retention, исключения, «забыть», «удалить всё».
6. **Поиск:** кнопка «Найти агента/навык/знание» → страница поиска.

### 9.2. Страница поиска

- Поле запроса + режимы `Агенты | Навыки | Знания`.
- Фильтры: источник, workspace, дата, итог, навык.
- Карточки результатов: имя, вид, источник, уверенность, «почему», 2–3 доказательства, навыки, кнопка «Передать задачу».
- Пустое состояние: «Ничего не найдено», причины, что сделать.
- Карточка навыка: тело, `whenToUse`, ресурсы, применение, история, агенты.
- Диспетчеризация: диалог с планом, критериями, пакетом контекста; `dry_run` по умолчанию.

### 9.3. Честные состояния

`disabled` — функция выключена и почему; `not_ready` — индекс ещё не построен; `stale` — данные устарели; `degraded` — источник недоступен; `error` — что именно и как починить.

## 10. Критерии приёмки

| ID | Критерий | Как проверить |
|---|---|---|
| AC-1 | Свежая установка: функция включена по умолчанию; выключение останавливает индексацию, инструменты отвечают `KNOWLEDGE_DISABLED`, UI честен. | Ручной сценарий + тест. |
| AC-2 | Индексация запускается в настроенное время (2 раза в сутки по умолчанию), настраивается, не пересекается, догоняет последний пропуск. | Тест таймера/фейковые часы. |
| AC-3 | Ручной reindex в трёх режимах работает; прогресс, отмена, идемпотентность. | Тест + CLI. |
| AC-4 | Покрытие: 100% доступных DSH-сессий/навыков и выбранных таблиц AutoClaw; дублей нет; отчёт покрытия. | Сверка counts с источниками. |
| AC-5 | Golden set ≥ 30 запросов: top-3 recall ≥ 0.80, MRR ≥ 0.60, zero-result ≤ 10% на известных темах. | Замер + отчёт. |
| AC-6 | Карточка навыка содержит тело, `whenToUse`, ресурсы, версию/хэш, ≥1 доказательство использования (если было), применимость к задаче. | Fixture-тест. |
| AC-7 | `knowledge_dispatch` в `dry_run` ничего не запускает; в `commit` создаёт задачу/сообщение/реплику с пакетом контекста и provenance; повтор идемпотентен; без подтверждения внешних действий нет. | Интеграционный тест. |
| AC-8 | Инкрементальный прогон после изменения одной сессии индексирует только её; повторный прогон — no-op. | Тест. |
| AC-9 | Kill -9 во время индексации: предыдущий индекс цел, следующий запуск продолжает/пересобирает. | Crash-тест. |
| AC-10 | Секрет-канарейка не попадает в БД, FTS, векторы, логи и выдачу; исключения и «забудь» удаляют без остатка. | Тест + grep. |
| AC-11 | AutoClaw БД после прогона не изменилась (mtime/размер/хэш); исходные сессии не переписаны. | Хэш до/после. |
| AC-12 | P95 поиска ≤ 300 мс, incremental ≤ 60 с на целевом объёме; отчёт с числами. | Бенчмарк. |
| AC-13 | Одинаковый `index_rev` + запрос → одинаковый порядок; tie-break стабилен. | Тест. |
| AC-14 | Документация обновлена: каталог инструментов, настройки, приватность, troubleshooting, changelog. | Ревью. |
