   запись `building`/`failed` с бо́льшим номером называлась активной и показывала нули.

### Б.9 Этап 9 — закрыт 30.10.2026

**Что было.** `.ragraf` занимал **26 829 МБ** при **8 808 МБ** собственно индекса:
`cpg/` — 17 831 МБ, `index/` — 8 954 МБ. В лексике лежали **7 729 196 строк**

называли ни объёма `cpg`, ни хвоста ротации: объём был виден только обходом диска.

**Причина, а не симптом.** Правило «удаляется вместе с ревизией» жило рукописным
списком таблиц в `Revisions._purge_rev_data` — списком, который надо было не
забыть дополнить. Документный слой появился позже списка и в него не попал.
Слой живых баз (`db_live_column` и родственные, ещё **3 594 860 строк**) не попал
туда же. Поэтому список таблиц теперь ВЫЧИСЛЯЕТСЯ по схеме (у какой таблицы есть
колонка `rev_id`), и новая таблица попадает под политику в тот день, когда
появилась.

**Что сделано.**

1. `src/ragraf/storage.py` — модуль политики: объёмы трёх хранилищ и `cpg`,
   разбор артефактов по ревизиям, план, выполнение, `VACUUM`, защита активной
   ревизии по строкам таблиц.
2. Пять настроек в `settings.DEFAULTS` с границами и объяснением каждого
   умолчания замером: `storage_keep_cpg_revs`, `storage_tmp_max_mb`,
   `storage_tmp_age_hours`, `storage_vacuum_free_percent`, `storage_auto_compact`.
3. Ротация (`revisions._purge_rev_data`) удаляет строки по вычисленному списку и
   артефакты CPG ревизии; индексатор после ротации зовёт автоочистку (по
   умолчанию выключена — см. ниже).
4. `ragraf compact` (`--plan` по умолчанию, `--apply --yes`, `--vacuum`,
   `--retain`), операция фасада `op_compact`, инструмент MCP `ragraf_compact`.
5. `index_status` показывает три хранилища (`graph`, `lexvec`, `control`),
   свободные страницы, объём `cpg`, временные каталоги, число ревизий и остаток
   хвоста — «сколько занимает» видно без обхода диска.

## 0. Что требуется (формулировка заказчика)

1. Разобрать статью <https://habr.com/ru/companies/pt/articles/1084780/> и подобные работы на arXiv.
2. Спроектировать вспомогательные RAG- и графовые базы, которые **облегчают работу LLM по доработке и разработке ПО**.
3. Перед началом доработки некий софт **проводит индексацию кода** в эти базы.
4. Агенты при доработке **активно используют базы вместо изучения кода** (`rg`/чтение файлов вслепую).
5. По мере разработки — **накопление различий базы и кода** в отдельной БД или в md-файле, чтобы **не делать неправильных выводов** в процессе накопления.
6. После окончания разработки/доработки — **запуск переиндексации**, приводящей базы в соответствие с кодом.
7. Работа ведётся в три этапа: **(1) исследование → (2) архитектура и ТЗ → (3) реализация ТЗ**, с подведением итогов и запросом уточнений перед и после каждого этапа.

### 1.2 Ключевой разрыв: наш кейс ≠ аудит безопасности

|---|---|---|
| Вопрос агента | «есть ли путь источник→сток?» | «где это лежит, кто это вызывает, что сломается, как сделать одинаково с существующим?» |
| Что нужно от графа | taint-путь с формальной гарантией полноты | **impact analysis**, контракты символов, связи с БД/маршрутами/формами/тестами |
| Языки | преимущественно C/C++ | PHP без фреймворка, Python, JS/TS, C#, PowerShell, SQL |
| Размер кода | сотни тысяч — миллионы строк | десятки — сотни тысяч строк на проект; несколько проектов |
| Жизненный цикл | разовый аудит зафиксированного коммита | **непрерывная разработка**; индекс живёт месяцами и неизбежно устаревает |
| Второй корпус данных | только код | код **+ схема MySQL + документация (md) + история git + конфиги** |
| Риск | пропустить уязвимость | **сломать работающее** и потратить токены на переоткрытие уже известного |

Отсюда два требования, которых в статье нет вовсе, но без которых заказ невозможен: **дрейф индекса** (§4) и **измеримость пользы на нашем корпусе** (§2.3).

### 1.3 Что в статье не рассматривается, а нам критично

1. **Дрейф индекса и различия «база vs код»** — в статье аудит одноразовый. Наша задача — живой индекс + журнал расхождений.
2. **Порядок обновления.** Инкрементальная переиндексация «по ходу» смешивает частичные выводы агента с фактами кода — это и есть механизм «неправильных выводов», которого заказчик просит избежать.
3. **Git-история как источник истины о прошлых изменениях** — даёт готовый оценочный набор (gold set) для проверки impact-анализа: по коммиту известно, какие файлы реально были затронуты.
4. **Динамические языки.** PHP без фреймворка: `include`/`require`, переменные-функции, `eval`-подобные конструкции, SQL в строках. Часть рёбер графа неизбежно эвристическая → каждое ребро обязано нести **достоверность и доказательство** (файл:строка), иначе агент будет опираться на выдуманные связи.
5. **Цена обновления.** Если переиндексация проекта занимает часы, её не будут запускать. Это нефункциональное требование первого порядка.

## 2. Постановка задачи RAGRAF

### 2.1 Целевой цикл (то, что заказчик описал словами)

```
┌──────────────────────────────────────────────────────────────────────┐
│ ФАЗА A — ИНДЕКСАЦИЯ (до начала доработки)                            │
│   scan → parse → extract → normalize → load → verify                 │
│   выход: INDEX_REV (снимок кода), отчёт покрытия, список пропусков   │
├──────────────────────────────────────────────────────────────────────┤
│ ФАЗА B — РАБОТА АГЕНТА С ИНДЕКСОМ                                    │
│   агент спрашивает: где лежит · кто вызывает · что сломается ·       │
│   срез функции · карта репозитория · кто читает таблицу · маршруты   │
│   НЕ сканирует репозиторий вслепую                                   │
├──────────────────────────────────────────────────────────────────────┤
│ ФАЗА C — НАКОПЛЕНИЕ РАЗЛИЧИЙ (drift ledger)                          │
│   каждая правка регистрируется как дельта: путь, хэши, символы,       │
│   затронутые рёбра, кто/когда/чем обнаружено                         │
│   ИНДЕКС ПРИ ЭТОМ НЕ МЕНЯЕТСЯ (заморожен на INDEX_REV)               │
├──────────────────────────────────────────────────────────────────────┤
│ ФАЗА D — ПЕРЕИНДЕКСАЦИЯ (после завершения доработки)                 │
│   reindex --commit → новый INDEX_REV, ledger архивируется и          │
│   превращается в человекочитаемый отчёт «что изменилось в знаниях»   │
└──────────────────────────────────────────────────────────────────────┘
```

### 2.2 Черновик требований

**Функциональные**

- **FR-1** Индексатор строит по репозиторию граф кода: узлы и типизированные рёбра с языковой разметкой.
- **FR-2** Индексатор строит векторный и лексический индекс для «поиска похожего» и навигации по тексту.
- **FR-3** В графе представлены не только символы, но и **внешние контракты**: таблицы/колонки/внешние ключи MySQL, HTTP-маршруты и их обработчики, формы и JS-обработчики, CLI/cron-точки входа, файлы документации.
- **FR-4** Фасад предоставляет фиксированный набор операций (не свободный язык запросов): `search`, `symbol`, `references`, `callers`, `callees`, `impact`, `slice`, `repo_map`, `schema`, `table_usage`, `routes`, `index_status`, `drift_report`, `drift_ack`.
- **FR-5** **Каждый факт в ответе несёт провенанс**: источник (парсер+версия), `path:line`, достоверность, `index_rev`.
- **FR-6** Журнал различий (ledger) ведётся как машиночитаемая БД **и** как человекочитаемый md-журнал; запись append-only.
- **FR-7** Любой ответ фасада при непустом ledger помечает затронутые факты как `stale` и предлагает живое чтение файла.
- **FR-8** Переиндексация запускается явной командой, синхронно или в фоне, с сохранением истории ревизий; результат — новый `INDEX_REV`.
- **FR-9** Операции чтения фасада доступны агенту как инструменты (MCP-сервер) и как CLI.
- **FR-10** Отчёт покрытия: сколько файлов разобрано, сколько не разобрано, где потеряны связи (важно для честности выводов).

**Нефункциональные**

- **NFR-1** Работает на текущей машине **без прав администратора**.
- **NFR-2** Полная переиндексация проекта до ~300 тыс. строк — не более ~15 минут на CPU; инкрементальная по дельте — секунды-минуты.
- **NFR-3** Никаких секретов в индексе: значения паролей/токенов/DSN из кода и конфигов **не индексируются**, только факт ссылки.
- **NFR-4** Индекс воспроизводим: одинаковый вход → одинаковый `INDEX_REV` (детерминированные id узлов).
- **NFR-5** Индекс можно удалить и пересобрать с нуля одной командой; артефакты не «размазаны» по репозиторию проекта.
- **NFR-6** Вся обвязка — PowerShell 7.6+/Python 3.13 по правилам `AGENTS.md` (кодировки utf8NoBOM, без CRLF/BOM в поставляемых файлах, без WinPS-compat).

### 2.3 Метрики успеха (измеримые, а не «стало лучше»)

| Метрика | Как считается | Базовая линия |
|---|---|---|
| **M1. Точность навигации** | Доля задач, где корректный файл найден с первого запроса к фасаду | Агент без индекса (`rg`/чтение) — снимается прогоном |
| **M2. Полнота impact-анализа** | Для N исторических коммитов: доля реально затронутых файлов, предсказанных `impact` **до** внесения правки | Gold set из git-истории; предсказание «только правильный файл» = 0,3–0,5 по опыту |
| **M3. Экономия контекста** | Токены и число tool-вызовов на задачу «внести правку» с индексом / без | Прямое сравнение на одинаковых задачах |
| **M4. Сжатие среза** | `тokens(срез) / tokens(подграф окружения)` по нашей кодовой базе | В статье: −68…70% и −90,93% на чужих наборах |
| **M5. Свежесть** | Доля ответов, помеченных `stale`; число инцидентов «агент опирался на устаревший факт» | Цель: инцидентов ноль, т.к. факт помечен |
| **M6. Проверяемость** | Доля утверждений агента со валидной ссылкой `path:line`, подтверждённой автоматически | Автопроверка существования файла и попадания в диапазон строк |
| **M7. Стоимость обновления** | Время полной и инкрементальной переиндексации | NFR-2 |

**Важно:** M2 измерим **задним числом** на реальной истории проектов заказчика — это отличает проверяемый результат от демонстрации. Точное значение baseline требует согласования (см. §7, вопрос 2).

## 3. Эскиз архитектуры (уточняется на Этапе 2)

```
L0  ИСТОЧНИКИ      код (git) · схема MySQL · документация (md) · история git · конфиги
                     │
L1  ЭКСТРАКТОРЫ    tree-sitter (синтаксис всех языков)
                   + типовые анализаторы: phpstan/psalm (PHP) · pyright/jedi (Python)
                     · TS compiler API (TS/JS) · Roslyn (C#) · AST-разбор PS (PowerShell)
                     · introspection MySQL (information_schema) · git log/diff
                     │  выход: единый поток фактов (узлы/рёбра/фрагменты текста)
L2  МОДЕЛЬ         каноническая схема: узлы, типизированные рёбра, свойства, провенанс
                     │
L3  ХРАНИЛИЩА      граф (узлы/рёбра) · векторный индекс · лексический индекс (BM25/FTS)

                     │
L4  ФАСАД          MCP-сервер (основной) + CLI (отладка и CI)
                     │
L5  ИНТЕГРАЦИЯ     AGENTS.md проекта + skill: «сначала индекс, потом чтение файлов»
```

### 3.1 Схема модели (черновик, уточняется на Этапе 2)

**Типы узлов:**

- Структура: `repo`, `package`, `module`, `file`, `namespace`, `class`, `trait`, `interface`, `enum`
- Код: `function`, `method`, `property`, `constant`, `parameter`, `sql_literal`
- База данных: `db_table`, `db_column`, `db_index`, `db_fk`, `db_view`
- Веб/точки входа: `web_route`, `http_endpoint`, `form`, `js_handler`, `cli_command`, `cron_job`
- Знания: `doc`, `doc_section`, `commit` (в т.ч. `config_key`, `env_var` — **без значений**)

**Типы рёбер:**

- Структура: `contains`, `defines`, `imports`, `uses`, `extends`, `implements`, `overrides`, `instantiates`
- Вызовы: `calls` (с числом мест вызова), `calls_heuristic` (динамический вызов, пониженная достоверность)
- Данные: `reads`, `writes`, `queries`, `returns`, `param_of`, `type_of`, `flows_to` (внутрипроцедурно)
- СУБД: `fk_to`, `references_table`
- Маршруты: `handles`, `renders`, `submits`, `posts_to`
- Проверка/знания: `tested_by`, `documented_by`, `changed_in`, `mentions`, `similar_to`

**Обязательные свойства каждого ребра:** `evidence` (`path:line`), `confidence` (1.0 статика / ~0.6 эвристика / ~0.4 вывод из истории или эмбеддинга), `extractor` (имя+версия), `index_rev`.

> Правило, вытекающее из разбора статьи: **ребро без доказательства не живёт в графе как факт** — иначе агент начнёт «галлюцинировать связями» уже из индекса, что хуже, чем галлюцинация из контекста, потому что выглядит авторитетно.

### 3.2 Что сознательно НЕ делаем (ограничение объёма)

- Не строим полноценный taint-анализ и не ищем уязвимости — это задача статьи, не наша.
- Не пишем CPGQL/DSL для агента: только фиксированные операции (тезис 7 статьи).
- Не индексируем бинарники, вендорные каталоги и сгенерированный код (список исключений — на Этапе 2).
- Не даём агенту модифицировать граф: он пишет только в ledger.

## 4. Ключевой механизм: накопление различий (drift ledger)

Это ядро требования заказчика «чтобы не делать неправильных выводов в процессе их накопления».

### 4.1 Три состояния и главный инвариант

| Состояние | Что это | Меняется когда |
|---|---|---|
| **Код** | фактическое содержимое репозитория | в любой момент |
| **Индекс** | снимок фактов на `INDEX_REV` | **только** командой `reindex --commit` |
| **Ledger** | append-only список дельт между индексом и кодом | каждая правка, обнаруженная хуком/сравнением |

> **Инвариант I1.** В пределах одного `INDEX_REV` индекс **иммутабелен**. Никакая частичная инкрементальная переиндексация в ходе доработки не выполняется.

Почему это принципиально: если индекс обновлять «по ходу», то выводы агента, сделанные 10 минут назад на старом срезе, и факты, попавшие в индекс 5 минут назад, оказываются в одном ответе без различия — ровно тот случай, когда «накопление» портит вывод вместо того, чтобы его улучшать.

### 4.2 Схема записи ledger

Машиночитаемая часть (SQLite, таблица `drift_entry`):

| Поле | Смысл |
|---|---|
| `id` | монотонный номер |
| `ts` | время обнаружения |
| `index_rev` | против какой ревизии зафиксирована дельта |
| `path` | файл (или `db://schema` для схемы БД) |
| `kind` | `add` / `modify` / `delete` / `rename` / `schema_change` |
| `old_hash`, `new_hash` | контентные хэши (не mtime) |
| `symbols_added`, `symbols_removed`, `symbols_changed` | символы, если удалось определить парсером на месте |
| `edges_invalidated` | какие рёбра графа заведомо устарели |
| `detected_by` | `hook:session-start` / `watcher` / `git-diff` / `manual` / `db-schema-diff` |
| `commit` | коммит, если есть |
| `ack` | признание дельты агентом: кто и когда её учёл |
| `note` | свободный комментарий (например: «вынес метод, границы среза изменились») |

Человекочитаемая часть — `drift/LEDGER.md`, дописывается теми же событиями, понятными формулировками:

```markdown
## 2026-10-04 14:32 · rev idx-0007 · detected_by git-diff
- `src/Wizard/OutgoingLetters.php` — modify
  - изменено символов: 3 (`listAction`, `$filterMap`, `applyFilters`)
  - устарели рёбра: `handles(OutgoingLetters#listAction → /wizard/outgoing/list)` — под вопросом
  - примечание: добавлен новый фильтр; контракт ответа не менялся
```

### 4.3 Жизненный цикл и защита от неверных выводов

1. **Старт доработки.** Хук сравнивает `INDEX_REV` с рабочим деревом → агент получает `drift_report`. Пустой отчёт = «можно опираться на индекс без оговорок».
2. **Ход доработки.** Каждый агентский ответ фасада содержит шапку:
   `index_rev=idx-0007 · drift=3 файла / 7 символов · provenance=index|live|mixed`.
   Факты, затронутые непустым ledger, помечаются `stale` → фасад предлагает живое чтение.
3. **Регистрация правки.** После каждой правки (или пачки) запись в ledger. Отдельно фиксируются правки, меняющие **границы срезов** (extract-method) — самое слабое место подхода по статье (тезис 12).
4. **Завершение доработки.** `reindex --commit` → новый `INDEX_REV`; ledger архивируется в `drift/archive/<rev>_<ts>.md` с ответом на вопрос «что изменилось в знаниях», и обнуляется.
5. **Дедупликация.** Ключ `(path, old_hash, new_hash)` — повторное обнаружение той же дельты не задваивает журнал.
6. **Ручные правки запрещены.** Ledger append-only; ошибка исправляется новой записью, а не перезаписью (иначе теряется история и «неправильный вывод» становится неотличим от верного).

**Определение «доработка завершена»** (выносится на уточнение, §7): явная команда `reindex` · коммит в git · завершение сессии агента · порог (N правок или M минут).

| Риск | Проявление | Как снижаем |
|---|---|---|
| Динамика PHP | связи выдуманы или потеряны (`include`, переменные-функции) | каждое ребро несёт достоверность и `evidence`; эвристика помечена как эвристика |

| Лицензии инструментов | CodeQL/Joern ограничения | лицензии проверяются на Этапе 1 и попадают в ТЗ как ограничение |
| **JVM/Docker нет** | Joern (единственный из проверенных инструментов, дающий полный CPG) требует JDK; Neo4j требует JVM; codebadger требует Docker + JVM | `php2cpg` в Joern **есть** (проверено в официальной таблице фронтендов) — вопрос не в поддержке языка, а в JVM. Решение — за заказчиком (§7, вопрос 1) |

| Расхождение ожиданий по метрикам | «стало удобнее» вместо измеренного | baseline M1–M3 фиксируется до реализации, в ТЗ |

**Что было.** Быстрая переиндексация корпуса занимала **35,6 с** (замер первым
`ensure` этой сессии; в отчёте предыдущей сессии — 34,1 с), причём сумма стадий
давала 29,3 с: запечатывание, ротация и открытие хранилищ в профиль не попадали
вовсе. Стадия `lexvec` одна стоила **16,18 с**.

**Находка 1 — 17 секунд в плане запроса.** `reusable_vectors` соединял обычную
таблицу `vec_meta` с виртуальной `vec_chunk`. Ограничение по `chunk_id` в
виртуальную таблицу не передаётся, поэтому SQLite сканировал `vec_chunk` на
КАЖДУЮ строку `vec_meta` (план `SCAN v VIRTUAL TABLE INDEX 1:2!___`). Замер на
живом хранилище: соединение **16,98 с**, `EXISTS` с тем же смыслом — те же 16,98 с,
два скана и пересечение в Python — **0,17 с**. Форма заменена
(`LexVecStore.reuse_index`), возврат прежней запрещён свойством
`tests/test_vector_reuse.py`.

**Находка 2 — переписывались все векторы, не меняя ни одного.** Из 21 272 чанков
активной ревизии **все 21 272** уже имели вектор в vec0: `chunk_id` адресует
содержимое, и неизменившийся чанк получает тот же идентификатор. Прежний код
делал `DELETE` + `INSERT` на 21 тыс. строк на каждом прогоне. Теперь пишется
только отсутствующее, а для сдвинутых чанков (текст тот же, идентификатор новый)
вектор переносится запросом `INSERT … SELECT` — vec0 его поддерживает (проба на
песочнице: 5 строк из 5).

**Находка 3 — уборка векторов не работала вовсе.** `_purge_rev_data` удалял
строки vec0, но расширение на этом соединении не загружалось: `table_exists`
отвечал `True`, `DELETE` падал с `no such module: vec0`, ошибка глушилась
`break`. Замер: **19 709 строк из 41 356 (48 %)** недостижимы для поиска и никем
не убраны. Заодно исправлен смысл: удалялись векторы, нужные ОСТАЛЬНЫМ
ревизиям. Теперь убираются только те, на которые не ссылается ни одна ревизия;
после правки строк vec0 21 703, сирот 0.

**Находка 4 — текст токенизировался дважды.** 42 556 вызовов на 21 тыс. чанков,
4,68 с в профиле; половина работы была лишней (в `symbol_tokens` и `code_tokens`
попадало одно и то же значение). Теперь один вызов на чанк.

**Находка 5 — проверка модели платилась всегда.** `embedder.status()` грузит ONNX
(замер в чистом процессе: 1,57 с) и вызывался даже когда кодировать было нечего.

**Решение по ротации — пакет не экономит.** Удаление данных одной ревизии стоит
**4,45 с** (29 запросов `DELETE` по ~100 тыс. строк: 81 тыс. рёбер и 21 тыс.
чанков с FTS-строками). Пачка из трёх ревизий стоит **18,0 с**, то есть
N × 4,45 с — амортизации нет, зато появляется прогон на 34 с (замер: 33,9 с
против 26,2 с на том же корпусе). Поэтому умолчание `rotate_batch: 1` — удалять
сразу, ровный график; значение больше единицы осталось настройкой. Цена
удержания названа объёмом: **≈0,6 ГБ на ревизию** (lexvec 443 МБ + graph 170 МБ),
`retain_revs: 3` = 1,8 ГБ при пороге предупреждения 6 ГБ.

**Решение по GPU — замером.** Процессор: 1,83 мс/текст (512 текстов за 0,94 с),
карта: 0,23–0,27 мс/текст, но подготовка 17,8–29,9 с в двух прогонах. Точка
равенства — **11 113** текстов при подготовке 17,8 с и **19 185** при 29,9 с.
Быстрая переиндексация кодирует 0 текстов, полная — около 14,5 тыс., то есть
ниже порога: на этой машине карта проигрывает по времени. `gpu_min_texts` этого
корпуса поднят с 1800 до **18 000**; глобальное умолчание не тронуто — оно
относится к машинам без замера.

**Находка 6 (была находкой 2 прошлой сессии) — брошенные ревизии.**
В журнале было **9** записей `state=building` (rev-0519 от 28.10 … rev-1112) без
событий в `event_log`. Закрывать «все `building` старше суток» нельзя: рядом
может идти живой прогон, и второй закрыл бы чужую работу. Поэтому в записи
появился признак живости `heartbeat_at` (обновляется на каждой стадии), а
закрытие требует, чтобы он устарел (`index.stale_revision_seconds`, умолчание
900 с) — при этом `UPDATE` условный, по `state='building'`, поэтому одна запись
не закрывается дважды. Замер на живом журнале: 9 записей закрыты, событий
`rev_closed_stale` — 9, `building` — 0. Свойства: `tests/test_stale_revision.py`
(12 проверок, подсадка «убрать проверку простоя» даёт 5 провалов).

**Находка 7 (была находкой 7 прошлой сессии) — набор не печатал числа.**
`tests/test_drift_e2e.py` не сообщал, сколько проверок выполнил, поэтому 14
проверок и три выглядели одинаково. Теперь печатает итог (**27 проверок,
0 провалов**) и сверяет байты живого `catalog/catalog.json` до и после прогона:
изменение живого реестра — провал набора, а не наблюдение.

**Итог замера.**

| стадия `lexvec` | 16,18 с | **5,84 с** |

Критерий «≤ 30 с» выполнен по числу прогона (25,4 с). Настенное время

**Границы, названные честно.** Соединение с `vec_chunk` запрещено свойством
только в `lexvec.py`: другие модули (`quality.py`, `storage.py`) читают vec0

Механизм закрытия брошенных ревизий опирается на время, а не на живость
процесса: прогон, который молчит дольше 900 с (например, завис в Joern), будет
закрыт — поэтому порог и вынесен в настройку.

**Кластеризация детерминированная.** Граф со-встречаемости (ребро — совместное
упоминание в одном чанке, вес — число чанков), порог `min_weight` (2), компоненты
связности, разрез крупной компоненты по порядку силы. `theme_id` считается той же
функцией, что при записи, — `sha1(seed + отсортированные участники)`: одинаковый
слой даёт одинаковые темы на любой машине и в любой ревизии. Leiden не берём: он

пустые цитаты и цитата вне списка участников — отказ разбора, запись не делается.

разбора, не показывается.
