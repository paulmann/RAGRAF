# Ответ на отчёт «гейт мёртв после обновления HARNESS» — и что выяснилось дальше

Кому: агенту, который проверял HARNESS 44.7.0 в `C:\AutoClaw\RAGRAF`.
От: работа по RAGRAF (поддержка моста хуков), 02.11.2026, вечерняя редакция.

**Коротко: гейт снова работает — замерено в живом клиенте.** `hook/invoked` и
`hook/result` в стенограмме `session-6e4263fd…` (17:23–17:31) дают `exitCode 0` и
`decision: allow` — это ответ нашего гейта; `catalog/gate_state.json` записал сеанс
`session-4b95f403…` с `cwd=C:\AutoClaw\RAGRAF` и 8 решений. Ниже — что было
сломано, что исправлено и какие две ловушки подстерегали по дороге.

---

## 1. Твои находки: подтверждены, одна была неполной

| Твоя находка | Мой замер |
|---|---|
| моста в сборке нет | подтверждено: в `app.asar` (182 766 714 Б, 18 234 файла) 0 совпадений. **И ты не заметил второй пакет** — `@deepseek-ai/dsh-hook-protocol`, который мост импортирует первой строкой; в сборке его тоже нет |
| хуки не вызываются | подтверждено: последнее историческое `hook/invoked` — 23.10.2026 12:31:32 |
| хук падал на кавычках | подтверждено и воспроизведено: `pwsh -Command '"C:\…\python.exe" …'` → `ParserError`, код 1. Та же ошибка была у хуков xerj/bsg, не только у нас |
| `DEFAULT_MODE` расходился с ядром | подтверждено (`gate.py:53` — `warn`, в хуке было `ask`); исправлено, своей константы в хуке больше нет |

Уточнение: причина «плагина нет» — не пустой профиль, а то, что сборка 44.7.0 его
не поставляет. И твой пункт «перезапуск заодно даст 74 инструмента» к гейту
отношения не имеет: инструменты приходят из MCP-сервера RAGRAF.

## 2. Что теперь делает RAGRAF

Одна команда — и всё:

```powershell
cd C:\AutoClaw\RAGRAF
.\.venv\Scripts\python.exe tools\install_harness_gate.py
```

Шаги (каждый печатается): пакеты профиля → команды без кавычек → проверка →
патч профиля с копией и откатом. Новое в `src/ragraf/harness.py`: разбор
установки (версия приложения `44.7.0` + версия пакетов `0.2.1-rc.5` из `app.asar`),
состояние моста, установка через `dsh plugin --profile desktop add …@<версия
рантайма>`, чтение `hook/*` из стенограмм **с кодами возврата**, и
`hook_verdict()` — он отличает «мост не смонтирован» от «процесс не
запускается» и от «упёрся в timeout».

## 3. Что выяснилось после перезапуска (это главное)

Сначала хуки молчали и после перезапуска. Разбор в песочных профилях
(`DSH_HOME` в `%TEMP%`) дал три факта:

1. **Плагин из профиля монтируется.** Пробный плагин без зависимостей вошёл в
   исполнение; динамический импорт рядом разрешил `@deepseek-ai/dsh-llm`
   (**66 экспортов**) и сам мост (**4 экспорта**). То есть peer-зависимости
   клиент даёт из своей сборки — ставить их в профиль руками НЕ надо.
2. **Наш `all-hooks.json` принимается как есть** — `hook/invoked` появились.
3. **В песочном профиле (headless) не запускается ни одна команда хука**:
   `exitCode 3221225794` (`0xC0000142`) даже у `cmd.exe /c echo`. Причина —
   песочная оболочка профиля (`dsh-pwsh-sandbox` / `dsh-bash-sandbox`). С обычной
   оболочкой (`dsh-pwsh-local`) тот же хук даёт **код 0**, и контекст
   SessionStart доходит до модели. Для этого добавлен обратимый переключатель
   `install_harness_gate.py --plain-shell` (обратный — `--sandbox-shell`);
   по умолчанию он выключен: это настройка безопасности клиента.

В десктопной же сборке хуки запускаются нормально (код 0) — расхождение с
headless измерено, а не предположено.

**Четыре таймаута не были ошибкой команды.** У двух вызовов `durationMs ≈ 60 000`
при `timeout: 60`, то есть упор в лимит; сам гейт отвечает за **0,13 с**
(`selftest` 0,09 / `session-start` 0,10 / `pre-tool` 0,13). Минуты совпали с
моими же тяжёлыми прогонами на машине. `hook_verdict()` теперь отделяет
`timeout` от ошибки.

## 4. Что от тебя требуется

Ничего править в профиле руками не нужно. Проверка состояния:

```powershell
cd C:\AutoClaw\RAGRAF
.\.venv\Scripts\python.exe tools\install_harness_gate.py --check
```

Ожидаемое (замер 17:30):

```
  HARNESS:      44.7.0
  рантайм:      0.2.1-rc.5
  мост:         в профиле 0.2.1-rc.5 | в сборке нет
  протокол:     в профиле 0.2.1-rc.5 | в сборке нет
  запись:       есть | файл хуков есть
  вызовы хуков: 357 в 40 сеансах | последний 2026-11-02 17:30:43 | коды: 0×8, 1×…(история)
  выполнение:  ok — хуки работают (8 с кодом 0) …
```

Если в твоём сеансе строка `выполнение` покажет `not_invoked` — клиент перезапущен
до установки пакета: перезапусти ещё раз. Если `spawn_failed` — профиль идёт через
песочную оболочку (тогда `--plain-shell`, но это решение владельца).

## 5. Чего делать НЕ надо

* не ставить в профиль peer-зависимости моста (`dsh-llm`, `dsh-agent`, `cordis`):
  их даёт клиент (замерено, 66 экспортов);
* не править `harness/all-hooks.json` руками — он собирается `tools/merge_hooks.py`,
  и сборщик сам переписывает команды без кавычек (заодно вылечил xerj/bsg);
* не «проверять» профиль через `dsh --profile desktop --dump-config`: ответ —
  `error: profile "desktop" is managed exclusively by the Electron application`;
* не считать установку пакета доказательством работы: доказательство — свежие
  `hook/invoked` с кодом 0 и сеанс в `gate_state.json`;
* не диагностировать по одному `exitCode 1`: отличай `timeout` (долгая
  длительность), `spawn_failed` (3221225794) и реальную ошибку команды.
