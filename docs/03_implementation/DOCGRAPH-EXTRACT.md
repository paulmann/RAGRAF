# Документный граф: извлечение фактов (этап 2)

Дата: 1 ноября 2026 г. Область: RAGRAF (`C:/AutoClaw/RAGRAF`), этап 2 плана
`docs/00_plan/PLAN-AGENT-INTEGRATIONS.md` (§3.2, §3.3, §3.9).

## 1. Что входит в этап

`src/ragraf/docgraph_extract.py` — проход по документным чанкам активной ревизии
через единственный клиент LLM (`src/ragraf/llm.py`), проверка адресов и запись слоя.
Включается флагом `--doc-graph` у `index`/`reindex` либо командой
`python tools/ragraf.py -p <config> docgraph build`.

Не входит: операции чтения фасада и MCP (`entity_neighbors`, `doc_relations`), гейт
изданий, dual-level поиск, темы и сводки. Это этапы 3–5.

## 2. Три правила прохода

| Правило | Что значит | Чем держится |
|---|---|---|
| Цитата из текста | модель называет фразу, проход ищет её в чанке и сам считает смещения | `quote_not_in_chunk` при отсутствии; `quote_too_short` при длине ниже `docgraph_min_quote_chars` |
| Связь опирается на упоминание | оба конца отношения обязаны иметь упоминание в ЭТОМ чанке | `unknown_entity` для имени, которого в чанке нет |
| Сначала ответ, потом запись | факты копятся в памяти, пишутся одной транзакцией | `commit=False`, `with_schema=False`; при отказе провайдера слой не меняется |

Поиск цитаты не строго символьный: если точного совпадения нет, текст сравнивается
со схлопнутыми пробелами (модель часто меняет перевод строки на пробел), и найденное
место переводится обратно в смещения ИСХОДНОГО текста. Это терпимость к
оформлению, а не к смыслу: цитата всё равно обязана присутствовать в чанке.

## 3. Почему `with_schema`

`docgraph.ensure_schema` вызывает `executescript`, а `sqlite3` перед ним фиксирует
текущую транзакцию. Пока писатели слоя вызывали схему сами, запись прохода
разваливалась на куски: подсадка M4 показала 9 сущностей, записанных до отказа
провайдера. Поэтому схема создаётся один раз вызывающим, а
`add_entity`/`add_relation`/`add_theme` принимают `with_schema=False`.

## 4. Повторный прогон

* Отпечаток совпал и слой не пуст → `skipped=true`, `calls=0`, слой не трогается.
* `force` (или смена модели/версии промпта) → проход идёт по чанкам, но каждый ответ
  берётся из `llm_cache`: `calls=0`, `cache_hits` равно числу чанков.
* Запись идёт теми же идентификаторами (`INSERT OR REPLACE`), поэтому содержимое
  слоя остаётся побайтово тем же.

## 5. Команды

```
python tools/ragraf.py -p config/ragraf.yaml index --doc-graph
python tools/ragraf.py --json -p config/ragraf.yaml docgraph build
python tools/ragraf.py -p config/ragraf.yaml docgraph build --dry-run --limit 50
python tools/ragraf.py -p config/ragraf.yaml docgraph status
```

`docgraph build` возвращает код 0, только если слой собран; при отказе провайдера —
код 1 и названный код отказа (`not_configured`, `auth`, `timeout`, …). `--dry-run`
считает вход без сети и возвращает 0 всегда: это отчёт, а не работа.

## 6. Стоимость и пределы

* Один вызов на чанк; чанк длиннее `docgraph_max_chars` обрезается (число обрезанных
  попадает в ответ и в примечание стадии).
* Не больше `docgraph_max_entities` сущностей из чанка.
* Отказы разбора считаются по кодам в `stats.rejected`, а не глотаются.
* Ответ провайдера не повторяется: повторы делает `llm.py` только на временных
  отказах (`llm_max_attempts`).

## 8. Границы этапа

* Операций чтения нет: слой только пишется; читать его будут `entity_neighbors` и
  `doc_relations` этапа 3.
* Гейт изданий `doc-graph` не введён: он появится вместе с операциями чтения.
* Слой пишется в АКТИВНУЮ ревизию — как живой слой баз. Пересбор — повторный проход,
  а не правка задним числом.
* Панель, MCP и установка этапом не менялись.
