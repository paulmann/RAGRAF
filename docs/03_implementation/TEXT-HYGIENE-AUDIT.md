# Чистота текста: где механизм BOM/CRLF вредил и что изменено

Дата: 31.10.2026. Вопрос владельца: «не вредил ли механизм автоматической
очистки CRLF и BOM, и если да, то в каких случаях». Ответ ниже — замер, а не
мнение: каждый случай воспроизведён в песочнице `%TEMP%\hygiene-sandbox`
прогоном настоящего инструмента `clean-bom-senior` (v3.0.0) с проверкой байтов
до и после.

## 1. Что было механизмом

Три части, и вред появлялся на стыке:

| часть | что делала | чем это грозило |
|---|---|---|
| правило проекта §6 (AGENTS.md) | «любой файл с кодом привести к `BOM=False`, `CRLF=False`» | правило про РЕЗУЛЬТАТ, а не про класс файла: под него попадала и запись, и данные |
| `clean-bom-senior` (sh/ps1) | нормализует **любой** явно переданный путь: CRLF→LF, BOM по «умной» политике | расширение и назначение файла не учитываются |
| `tools/check_bom_crlf.py` | проверка списка файлов наивным `b"\r\n" in data` | двоичные файлы числились «грязными», каталоги `archive/` и `community/` — обычными файлами |

## 2. Замеры: что именно меняется

### 2.1 Прогон инструмента по классам файлов (sh-версия, эталон)

| файл | было | стало | вердикт |
|---|---|---|---|
| `plain.txt` (CRLF) | CRLF | LF | правильно: обычный текст |
| `straight.bat` (CRLF) | 38 б | 34 б | **меняет исполняемый файл** |
| `table.csv` по RFC 4180 | 10 б | 8 б | **ломает формат: CRLF обязателен** |
| `keys.reg` | 96 б | 92 б | меняет файл реестра |
| `archive_copy.py` (запись с `sha256`) | `e9852244e883` | `a43f8c189b50` | **запись перестала быть копией** |
| `note.txt.bak-20261031` | 12 б | 11 б | **переписан бэкап: испорчено свидетельство** |
| `image.png` (двоичный, внутри `0D 0A`) | 16 б | 16 б | не тронут — инструмент распознал двоичный |
| `utf16.txt` | 28 б | 28 б | не тронут |
| `clean.txt` | 4 б | 4 б | не тронут, `mtime` сохранён |
| `cr_only.txt` (одинокий CR) | 4 б | 4 б | не тронут |
| `bom.ps1` (BOM + не-ASCII) | BOM + CRLF | BOM + LF | BOM сохранён намеренно — верно |
| `bom.bat` + `--no-rn-normalize` | BOM + CRLF | CRLF | BOM снят, CRLF сохранены — верно |

Вывод: сам инструмент аккуратен там, где решение принимает он (двоичные,
UTF-16, BOM-политика). Вред начинается там, где решение принимает вызывающий:
он передаёт путь, а инструмент обязан его нормализовать.

### 2.2 Обход каталога

`bash clean-bom-senior.sh <каталог>` берёт только свои расширения
(`php css js txt xml htm html`) — и переписывает всё подряд: в песочнице
изменены 6 файлов из 9, включая приманку `приманка.txt` и вложенный
`sub/deep.txt`. Файлы `.py`, `.csv`, `.bat`, `.reg` в этом режиме не тронуты —
не потому что защищены, а потому что не попали в список расширений. Это то же
поведение, которое 29.10.2026 переписало **727 существующих файлов** дерева
вместо одного нужного (вендорные `.tools/jdk`, `.ort_gpu_probe`, конфиги чужих
корпусов).

### 2.3 Исполнение LF-батника (проверка распространённого утверждения)

Правило проекта говорило: «cmd.exe LF-батник не исполняет вовсе (exit 255)».
Замер на этой машине (7 конструкций × 2 варианта переводов строк, `cmd.exe /c`):

| конструкция | LF | CRLF |
|---|---|---|
| `goto` + метка | exit 0, `both` | exit 0, `both` |
| `call :sub` | exit 0, `IN-SUB / AFTER` | то же |
| вложенный `for` в скобках | `1a 1b 2a 2b` | то же |
| `goto` внутри `if (...)` | exit 0 | то же |
| `set` внутри `if (...)` | `Y=` | `Y=` |
| `echo 100%%` | `100%` | `100%` |
| последняя строка без перевода | exit 3, `LAST` | то же |

Расхождений нет: **на этой машине LF-батник исполняется так же, как CRLF**.
Утверждение правила не воспроизвелось, и оно исправлено в документации: у
`.bat`/`.cmd`/`.reg`/`.csv`/`.tsv` переводы строк не меняются **не потому, что
LF «не работает», а потому что это формат исполняемого файла и данных**, а не
стиль текста. Опираться на поведение конкретного `cmd.exe` в правиле гигиены
нельзя.

### 2.4 Ложные срабатывания проверки

Наивное `b"\r\n" in data` считало «грязными» файлы живого дерева:
`assets/social-preview.png`, `catalog/secrets.sqlite`,
`workspace/rev-0099.cpg.bin/cpg.bin`. В них `0D 0A` — содержимое двоичного
формата. Инструмент их не трогал (2.1), а проверка сообщала о дефекте — и
следующий шаг «дочистить с `--force`» испортил бы файл.

### 2.5 Что НЕ навредило (проверено, чтобы не искать заново)

* жёсткие ссылки: инструмент пишет на месте, оба имени остались одним файлом
  (`st_ino` совпал, содержимое одинаковое) — ссылка не разорвана;
* уже чистый файл не перезаписывается: `mtime` не сдвинулся;
* записи `archive/**` в живом дереве целы: все 10 строк манифестов
  (`sha256`) совпали с файлами — до этой правки очистка по ним не прошла;
* скрытые правки: 1793 файла дерева содержат `0D 0A` или BOM, но 1777 из них
  — артефакты (`.zwork`, `stage-*`, `.work-*`, логи, копии). Рабочих файлов
  проекта с CRLF всего 16, и все — двоичные (png, sqlite, cpg.bin) или записи
  (`archive/**`, выводы тестов). Поэтому массовой беды в дереве RAGRAF сейчас
  нет — вред был бы причинён следующей массовой чисткой, а не прошлой.

## 3. Что изменено

| файл | изменение |
|---|---|
| `tools/text_hygiene.py` | **новый**: политика «что можно переписывать». Классификация по фактическим байтам (текст / двоичный / UTF-16 / пустой / ссылка / каталог) и причины защиты: `archive/**`, `community/**`, `*.bak*`, `*.orig-*`, `.zwork`/`stage-*`, расширения с функциональным CRLF. Очистка — только явными путями, каталоги отклоняются целиком. Для `.bat/.cmd/.reg` с BOM вызывается `--no-rn-normalize`, чтобы BOM снять, а CRLF сохранить |
| `tools/check_bom_crlf.py` | переписан на этот модуль: пять групп вместо «чисто/грязно», двоичные файлы больше не числятся дефектом, `--paths`/`--paths-from` вместо правки списка в коде |
| `tests/test_text_hygiene.py` | **новый** набор, 41 свойство: двоичные и UTF-16 не считаются грязными, CRLF функциональных расширений не меняется, записи не подаются инструменту, каталог отклоняется, чистый файл не переписывается, смешанные переводы строк названы, жёсткая ссылка не разрывается |
| `tools/release/manifest.toml` | класс `tools/text_hygiene.py` объявлен рабочим с причиной (иначе 45-я проверка чекера называет файл без класса) |
| `AGENTS.md`, `docs/AGENTS-context.md` | правило чистоты текста: классы, защищённые пути, порядок «сначала отчёт, потом очистка» |

## 3.1 Подробное правило (перенесено из AGENTS.md)

`tools/text_hygiene.py`: он смотрит фактические байты и называет причину.
Не переписываются: двоичные и UTF-16 (в них `0D 0A` — не перевод строки),
`.bat/.cmd/.reg` и данные RFC 4180 (`.csv`/`.tsv`), записи `archive/**` и
побайтовые копии `community/**` (их байты сверяются по `sha256`), копии
`*.bak*`/`*.orig-*`, машинные артефакты (`.zwork`, `stage-*`). Каталог как
аргумент отклоняется: обход дерева — это и есть механизм, который 29.10.2026
переписал 727 существующих файлов вместо одного. Замеры и случаи вреда —
`docs/03_implementation/TEXT-HYGIENE-AUDIT.md`.

## 4. Как проверить

```powershell
python tools\text_hygiene.py --paths src\ragraf\facade.py README.md   # отчёт, ничего не пишет
python tools\check_bom_crlf.py                                        # список этой задачи
python tests\test_text_hygiene.py                                     # 41 свойство
```

Замеры из раздела 2 воспроизводятся этим набором: он сам создаёт песочницу в
`%TEMP%`, прогоняет настоящий инструмент и сверяет байты до/после, а при
отсутствии Git Bash печатает `SKIP` с причиной, а не зелёный вердикт.

Очистка выполняется только после просмотра отчёта и только явными путями:

```powershell
python tools\text_hygiene.py --paths <файлы> --apply
```

## 5. Границы и что осталось

* Модуль не решает, «правильный» ли у файла стиль: он отвечает на вопрос
  «можно ли переписывать» и «что именно изменится»;
* BOM у не-ASCII `.txt`/`.ps1`/`.psm1`/`.reg` сохраняется намеренно (его читает
  Excel и Windows PowerShell 5.1) — это политика инструмента, и модуль её не
  дублирует, а не мешает ей;
* данные в кодировке cp1251 по-прежнему требуют `--force` инструмента и
  решения человека: `text_hygiene` называет такой файл двоичным и не трогает;
* глобальное правило §6 правил машины (в `AGENTS.md` пользователя) содержит
  утверждение про LF-батник, которое на этой машине не воспроизводится
  (2.3). Правило про результат это не отменяет, но обоснование уточнено здесь.
