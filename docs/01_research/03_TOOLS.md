## 2. Топ-3 варианта стека под наши ограничения

### Вариант A — «граф + вектор + лексика в embeddable-движках» (**рекомендуемый базовый**)

| Слой | Кандидат | Почему |
|---|---|---|
| Граф | **Kuzu 0.11.3** или **LadybugDB** (форк), альтернатива — **DuckDB PGQ** ⏳ | Cypher, встраивается в процесс, без службы и без админа |
| Вектор | **sqlite-vec** или **Qdrant local mode** / **LanceDB** | файл вместо сервера |
| Лексика | **SQLite FTS5** (уже есть) или **Tantivy** | BM25 без внешних сервисов |
| Символы | **SCIP** (`scip-php` ✅ + `scip-typescript` + `scip-python`) + **tree-sitter** | определения/ссылки/реализации машинно, а не эвристикой |

**Что даёт:** AST-производные связи, символы, вызовы, импорты, гибридный поиск, полностью локально, без служб.
**Чего не даёт:** CFG, DFG, межпроцедурного data-flow, taint-анализа, срезов по PDG.

### Вариант B — «граф в уже имеющемся MySQL»

| Слой | Кандидат | Комментарий |
|---|---|---|
| Лексика | **MySQL FULLTEXT (InnoDB)** | ноль новых сервисов, но **нет русского стемминга**, токены < 3 символов не индексируются |
| Граф | Kuzu/Ladybug файлом рядом | MySQL для графовых обходов не годится |
| Вектор | sqlite-vec/DuckDB VSS | рядом, файлом |

**Что даёт:** минимум новых зависимостей, единый «сервер», знакомая админская модель.
**Чего не даёт:** русского морфологического поиска (для кода это терпимо, для документации — хуже), гибридный поиск собирается руками.

### Вариант C — «символьная навигация через LSP» (быстрый старт)

**Serena (MCP)** + `mcp-language-server` + `ast-grep` + `ctags` + FTS5.
**Что даёт:** >40 языков, включая PHP/PowerShell/C#/TS/Markdown; навигация и правки «из коробки»; минимум своего кода.
**Чего не даёт:** это символы и навигация, **не граф кода** — нет ни data-flow, ни срезов, ни impact-анализа по зависимостям.

### Вариант D — «полный CPG через Joern» (максимум возможностей, вне текущих ограничений)

Joern + JDK 19: единственный проверенный инструмент, дающий **полный CPG** (AST+CFG+DFG+PDG) и CPGQL, причём **с поддержкой PHP (`php2cpg`)**, Python, JS и C#. Лицензия Apache-2.0.

| Что появляется | Что стоит |
|---|---|
| Межпроцедурный data-flow, taint, срезы по PDG — то, на чём построены лучшие результаты статьи | JVM (JDK 19) — установка с согласия владельца; Joern + JDK ≈ 0,5–1,5 ГБ |
| Готовый язык запросов CPGQL (но агенту его давать нельзя — см. ниже) | Скорость и качество на динамическом PHP неизвестны (⏳) |
| Совместимость с `codebadger` (MCP над Joern) — но тот требует ещё и Docker | Дополнительный слой: JVM в процессе индексации |

## 3. Что теряется без JVM — прямо

**Ни один вариант A/B/C не воспроизводит CPG.** Без Joern мы не получаем:
межпроцедурный поток данных · taint-анализ · срезы по PDG (то, что даёт в статье сжатие контекста) · запросы по CFG.
Взамен мы получаем AST-производные связи, символы через SCIP, вызовы, импорты, БД-схему, маршруты и гибридный поиск.

**Следствие для ТЗ:** если заказчик не разрешает JVM, требования формулируются как «impact analysis по структурным связям + символам + истории git», **без обещания data-flow**. Обещать срезы по PDG без Joern было бы недобросовестно.

## 6. Ключевые технические риски

1. **Лицензия CodeQL.** Для проприетарного внутреннего кода бесплатность не подтверждена: CLI бесплатен для public repos, для private нужен GitHub Code Security и принятие CodeQL Terms. Первоисточник лицензии не открыт ⏳ → **не закладывать CodeQL в обязательный стек**.
2. **PHP в Joern есть** (`php2cpg` в официальной таблице фронтендов) — вопреки распространённому мнению. Риск смещается на **качество CPG для динамического PHP**: `eval`, `include`, переменные-функции, magic-методы. Замеров нет ⏳.
3. **Kuzu заморожен** → зависимость от архивированного проекта. Выбор: остаться на 0.11.3 или перейти на LadybugDB (совместимость формата ⏳).
4. **Milvus Lite на Windows** исторически не поддерживался — до проверки считать недоступным ⏳.
5. **`claude-context` не offline** (нужен Milvus/Zilliz Cloud + ключ OpenAI) → противоречит цели «локальная база знаний».
6. **`vss` в DuckDB помечен experimental**, `sqlite-vec` — pre-v1 («expect breaking changes»). Оба могут менять API.
7. **Время эмбеддинга на CPU не измерено.** Оценку для корпуса 1–5 млн строк дать нельзя без замера — выносится в план замеров.
8. **Русская морфология.** Ни MySQL FULLTEXT, ни ngram-парсер русского стемминга не дают; для документации качество лексического поиска будет хуже, чем у BM25 со стеммером ⏳ (есть ли русский Snowball в `tantivy-py` — не проверено).
9. **Инкрементальность почти нигде не подтверждена.** Единственный проверенный механизм — tree-sitter (`ts_tree_edit` + reparse). У SCIP, Aider, SCIP-индексаторов — не подтверждено ⏳.

## 7. Вывод для выбора стека

1. **Базовый слой (без согласований):** tree-sitter + SCIP-индексаторы + SQLite FTS5 + embeddable граф (Kuzu/Ladybug) + локальные эмбеддинги через `fastembed`. Даёт AST-связи, символы, вызовы, схему БД, маршруты, гибридный поиск — и всё это **без JVM, без Docker, без админа**.
2. **Опциональный слой (требует согласия):** Joern + JDK 19 — добавляет CFG/DFG/PDG и срезы, то есть ровно то, чем статья объясняет свои лучшие результаты.
3. **Не берём:** CodeQL (лицензия), Docker-зависимые (`code-graph-rag`, `codebadger`), облачные (`claude-context`), pgvector (нет PostgreSQL и нужен админ), Neo4j (служба + админ), архивированные (`stack-graphs`), Kuzu как единственная опора (заморожен).
