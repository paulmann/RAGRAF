# Скорость и стабильность индексации (этап 12)

Замеры 31.10.2026, корпус `ragraf` (938 файлов, 21 тыс. чанков), машина с RTX 5080.
Каждое число получено прогоном, команда указана рядом. Ни одно утверждение здесь
не является оценкой: оценки помечены словом «оценка».

## 1. Что было измерено в начале

| Что | Значение | Чем измерено |
|---|---|---|
| быстрая переиндексация, всего | **35,6 с** (до правок) | `python tools/ragraf.py ensure .` |
| то же по стадиям | сумма 29,3 с | `query index_status`, блок стадий |
| необъяснённый остаток | ≈6,3 с | разница между суммой стадий и прогоном |
| стадия `lexvec` | **16,18 с** | `query index_status` |

Сумма стадий не покрывала прогон: запечатывание, ротация и открытие хранилищ
в профиль не попадали вовсе. Поэтому первым делом добавлены стадии `seal` и
`rotate` — иначе «где ушло время» отвечается догадкой.

## 2. Находка: соединение с виртуальной таблицей стоило 17 секунд

`reusable_vectors` соединял обычную таблицу `vec_meta` с виртуальной `vec_chunk`:

```sql
SELECT vm.text_hash, v.embedding FROM vec_meta vm
  JOIN vec_chunk v ON v.chunk_id = vm.chunk_id
 WHERE vm.model = ? AND vm.text_hash IN (...)
```

План, который выбирает SQLite, — `SCAN v VIRTUAL TABLE INDEX 1:2!___`: ограничение
по `chunk_id` в виртуальную таблицу **не передаётся**, и на КАЖДУЮ строку
`vec_meta` выполняется полный скан `vec_chunk`.

| Форма запроса | Время | План |
|---|---|---|
| соединение (как было) | **16,98 с** | `SCAN v VIRTUAL TABLE INDEX 1:2!___` |
| `EXISTS` с тем же условием | 16,98 с | тот же скан на каждую строку |
| нарезка по 900 id + `IN (...)` | 1,63 с | поиск по первичному ключу |
| скан `vec_chunk` целиком + пары из `vec_meta` + пересечение в Python | **0,17 с** | два скана |

Измерено `tools/`-пробой на живом хранилище (21 272 чанка против 41 356 строк
vec0). Замена сделана в `LexVecStore.reuse_index`; прежняя форма запрещена
свойством `tests/test_vector_reuse.py` (проверка исходника на строку соединения).

## 3. Находка: 100 % векторов уже были на месте

| Что | Значение |
|---|---|
| чанков активной ревизии | 21 272 |
| из них `chunk_id` уже с вектором в vec0 | **21 272 (100,0 %)** |
| уникальных текстов среди них | 14 478 |
| `chunk_id`, встречающихся больше чем в одной ревизии | 21 271 |

Вектор принадлежит `chunk_id`, а `chunk_id` адресует содержимое: неизменившийся
чанк получает тот же идентификатор. Значит прежняя безусловная запись
(`DELETE` + `INSERT` на 21 тыс. строк) **не меняла ни одного значения**.
Теперь пишется только то, чего в vec0 нет; для сдвинутых чанков (текст тот же,
идентификатор новый) вектор переносится запросом `INSERT … SELECT` — vec0 его
поддерживает (проба на песочнице: копия 5 строк из 5, `tests/test_vector_reuse.py`
сверяет перенесённый вектор побайтово).

## 4. Находка: уборка векторов не работала вовсе

`_purge_rev_data` удалял строки vec0 по `chunk_id` удаляемой ревизии. На этом
соединении расширение `vec0` **не загружалось**, `table_exists` отвечал `True`
(имя есть в `sqlite_master`), `DELETE` падал с `no such module: vec0`, а ошибка
глушилась `break`. Замер: **19 709 строк из 41 356 (48 %)** были недостижимы для
поиска и никем не убраны.

Там же была вторая ошибка смысла: удалялись векторы, которыми пользуются
ОСТАЛЬНЫЕ ревизии. Теперь удаляются только те, на которые не ссылается ни одна
ревизия (после удаления строк ревизии), а расширение загружается явно.
Замер после правки: сирот **0**, строк vec0 21 703 вместо 41 356.

## 5. Находка: текст токенизировался дважды

`add_chunks` считал `tokenize_for_fts(ch.text)` дважды (в `symbol_tokens` и
`code_tokens` попадало одно и то же значение). В профиле — 42 556 вызовов,
**4,68 с**; половина работы была лишней. Теперь один вызов на чанк.

## 6. Находка: проверка модели платилась на каждом прогоне

`embedder.status()` грузит модель ONNX (замер в чистом процессе: **1,57 с**),
и вызывался даже когда кодировать было нечего — все векторы переиспользовались.
Теперь проверка идёт только при непустом списке новых текстов.

## 7. Решение по ротации: пакет НЕ экономит

Прежняя политика удаляла данные одной ревизии на каждом прогоне. Проверены оба
варианта, которые предлагались.

| Вариант | Плата за прогон | Что видно в замере |
|---|---|---|
| удалять на каждом прогоне (`rotate_batch: 1`) | **4,45 с** | стадия `rotate`: 4,68 с при `items=1` |
| копить и удалять пачкой из трёх | 18,0 с на каждый третий | стадия `rotate`: 8,9 с при `items=2`, прогон 33,9 с |
| отложить до `ragraf compact` | 0 в прогоне | хранилище растёт на ≈0,6 ГБ за ревизию без предела |

Вывод: пачка **не амортизируется** — удаление N ревизий стоит N × 4,45 с, потому
что работа пропорциональна числу строк (29 запросов `DELETE` по ~100 тыс. строк:
81 тыс. рёбер, 21 тыс. чанков и их FTS-строки). Зато появляется прогон на 34 с.
Поэтому умолчание — `rotate_batch: 1` (удалять сразу, ровный график), а значение
больше единицы осталось настройкой для корпусов, где важно число прогонов, а не
длительность одного.

Цена удержания названа объёмом: одна ревизия корпуса ragraf — **≈0,6 ГБ**
(lexvec 443 МБ + graph 170 МБ). `retain_revs: 3` = 1,8 ГБ, порог предупреждения
о хранилище — 6 ГБ.

## 8. Решение по GPU: замер, а не ожидание

Замер `Embedder` (модель `paraphrase-multilingual-MiniLM-L12-v2`, 384 измерения):

| Путь | Подготовка | Кодирование |
|---|---|---|
| процессор (ONNX) | 1,57 с (загрузка модели) | **1,83 мс/текст** (512 текстов: 0,94 с) |
| карта (torch 2.11 + cu128, RTX 5080) | **17,8–29,9 с** (два прогона) | **0,23–0,27 мс/текст** |

Точка равенства = подготовка / (мс_проц − мс_карт): **11 113** текстов при
подготовке 17,8 с и **19 185** при 29,9 с.

Следствие для политики:

* быстрая переиндексация кодирует **0 текстов** (все переиспользованы), полная —
  около 14,5 тыс. уникальных. То есть объём работы лежит НИЖЕ точки равенства
  даже в благоприятном случае;
* поэтому `gpu_min_texts` для этого корпуса поднят с 1800 до **18 000**: ниже
  этого порога карта проигрывает по времени на измеренную величину, и занижать
  порог «чтобы карта работала» — значит платить 18–30 с за прогон;
* глобальное умолчание (1800) не тронуто: оно относится к машинам, где замер не
  делался, и меняется там по своему замеру.

Критерий «≤ 30 с» выполнен по числу прогона (`report.seconds` = 25,4 с).
Настенное время команды `ragraf ensure .` — **29,8–30,5 с**: перед решением о
переиндексации `ensure` трижды считает контрольную сумму корпуса (≈4,4 с на
938 файлах), и эта работа не входит в прогон. Она названа здесь как остаток,
а не спрятана.

**Остаток закрыт 01.11.2026 (этап 13).** Сверка корпуса сведена к одной, а
мёртвый дешёвый путь вылечен:

| Что | До | После |
|---|---|---|
| `ensure`, индекс актуален | 2,245 с (2 обхода корпуса) | **0,240 с** (1 дешёвый обход) |
| настенное время команды | 4,59 с | **0,74 с** |
| обходов с чтением на пересбор | 3 (сторож: до, внутри прогона, после) | **1** (+1 — сам индексатор) |
| отпечаток входа после доказанного равенства сумм | не обновлялся → дешёвый путь мёртв навсегда | **лечится** |

Замер — на одном и том же корпусе (944 файла): `ensure` в процессе 2,245 с до

свойства и что при этом поменялось в поведении сторожа —
`docs/03_implementation/USEFULNESS.md`, §6; проверки —
`tests/test_watch_single_scan.py`.

`docs/03_implementation/USEFULNESS.md`, §6.

## 11. Урок, который стоил файла

При правке `lexvec.py` файл был открыт на запись «на месте»
(`Path.write_text`), и отказ валидатора `newline` случился ПОСЛЕ обрезания файла:
`lexvec.py` стал 0 байт. Спас не бэкап, а индекс: в таблице `file` хранится
`sha256` каждого проиндексированного файла, а свежая копия дерева лежала в
`.zwork/ent-publish` (18:46 того же дня). Сверка `sha256` восстановленного файла
с записью ревизии дала совпадение байт в байт.

Правило на будущее (выполняется в `tools/`-правках этапа): содержимое пишется в
`<файл>.new`, проверяется разбором, и только потом заменяет оригинал через
`os.replace`; копия оригинала снимается ДО правки.
