# Издания pro и enterprise: что написано, что объявлено, что осталось

Документ текущего состояния. Отвечает на один вопрос: **по каждой возможности
платных изданий — есть ли код в сборке, и если нет, то что именно не написано.**
Числа и статусы берутся из `src/ragraf/edition_baseline.json` и проверяются
`edition.baseline_problems`; здесь они не перепечатываются «на память».

## 1. Зачем понадобился статус в данных

До этапа И9 раздел `missing` в ответе `python tools/ragraf.py edition` смешивал
два совершенно разных состояния:

* **«написано, но действует другое издание»** — код в сборке есть, лицензия не
  позволяет;
* **«объявлено, кода нет»** — возможность существует только записью в данных.

Причина была одна и та же: `возможность появляется в издании pro`. Читатель не
мог отличить готовую работу от обещания, а платное искали и не находили —
измерено на этапе И9: у enterprise в `missing` стояли пять pro-возможностей, из
которых четыре не имели ни одной операции в сборке.

Поэтому у каждой возможности появилось поле `status` из **закрытого списка**:

| `status` | Что означает | Обязательное поле |
|---|---|---|
| `shipped` | операции возможности есть в сборке | — |
| `declared` | объявлено как запланированное | `planned`: одной строкой, что именно не написано |

Опечатка в статусе, `declared` без `planned` и `shipped` с `planned` —
**отказ проверки данных** (`edition.baseline_problems`), а не «неизвестное
значение, считается объявленным». Иначе `shippd` тихо означал бы что угодно.

Статус не отменяет проверку состава: возможность попадает в список действующих,
только если ВСЕ её операции найдены в сборке. Поэтому `declared` видна в
`missing` с причиной, в которой назван статус, а не только издание.

## 2. Возможности платных изданий

| Возможность | Издание | Статус | Что сделано | Что осталось |
|---|---|---|---|---|
| `quality-loop` | pro | `shipped` | `src/ragraf/quality.py`: набор проверок индекса, запись прогона в добавляющую таблицу `quality_run`, сравнение двух прогонов; операции `quality_suite`, `quality_diff`, `quality_prune` (прореживание журнала прогонов: сухой прогон по умолчанию, копия до удаления, подтверждение); инструменты `ragraf_quality_suite`, `ragraf_quality_diff`, `ragraf_quality_prune`; проверка `tests/test_quality_loop.py` | — |
| `shared-index` | pro | `shipped` | `src/ragraf/shared_index.py`: чтение индекса команды по сети — `serve` отдаёт операции чтения по допуску, `query` возвращает тот же конверт, что локальный фасад, с честной свежестью; запись по сети не публикуется (граница этапа); операции `shared_index_status`, `shared_index_publish`, `shared_index_query`; проверка `tests/test_shared_index.py` (69 свойств) | — |
| `secret-broker` | pro | `declared` | хранилище секретов (`vault.py`, `vault_ops.py`) — это ДРУГАЯ возможность и она в Community | брокер как служба: выдача по запросу, срок, владелец, отзыв, плановая смена |
| `connectors` | pro | `declared` | ничего в сборке | контракт запуска для каждого вида внешней системы (адрес, права, повторы); без него «запуск» был бы заглушкой |
| `fleet` | pro | `declared` | ничего в сборке | канал управления установками и подписанный пакет настроек |
| `sso` | enterprise | `shipped` | `src/ragraf/sso.py`: OIDC authorization code + PKCE, роли только из групп отображения | SAML — отказ с причиной |
| `siem-export` | enterprise | `shipped` | `src/ragraf/siem.py`: syslog/HTTP, курсор доставки, только метаданные | — |
| `offline-license` | enterprise | `shipped` | `src/ragraf/license_offline.py`: заявка, выпуск, приёмка по подписи и отпечатку установки, перенос | — |
| `attestation` | enterprise | `shipped` | `src/ragraf/attest.py`: подписанный набор, проверка пересчётом хэшей из файлов | — |

Итог по изданиям: у **enterprise** действуют **11 возможностей** (пять базовых
Community + `quality-loop` + `shared-index` + четыре enterprise), в `missing` — три
запланированные pro (`secret-broker`, `connectors`, `fleet`). У **pro** действуют
**7** (пять базовых + `quality-loop` + `shared-index`), в `missing` — те же три pro
и четыре enterprise.

## 3. Почему четыре возможности не сделаны «заодно»

Их объединяет одно: **у каждой нет контракта, а не кода**. Написать их «пока
руки на клавиатуре» значило бы придумать контракт за владельца, и это было бы
хуже отсутствия:

* `shared-index` требует решения о доверии между установками. Публикация
  ревизии без проверки получателя — это раздача индекса кому угодно; проверка
  подписи требует ключей, которых в сборке нет.
* `secret-broker` требует политики срока и владельца секрета. Хранилище уже
  отвечает на вопрос «дай значение по праву», а брокер — на «выдай доступ на
  время и смени по расписанию»; это разные обязательства, и второе без политики
  становится способом обойти первое.
* `connectors` требует отдельного контракта на каждый внешний вид: адрес, права,
  повторы, предел. Одна общая заглушка `connector_run` возвращала бы `ok=true`,
  ничего не запуская, — то есть ровно тот класс ложного успеха, из-за которого
  в проекте появилось правило «зелёная проверка, ничего не осмотревшая, — провал».
* `fleet` требует канала управления установками. Управлять нечем: парка
  зарегистрированных установок в этой сборке нет, и «применение настроек»
  применяло бы их к нулю машин, отчитываясь об успехе.

Поэтому у всех четырёх `status=declared`, а в `planned` назван недостающий
контракт. Это видно и в ответе `edition` с лицензией, и без неё.

## 4. Что делает контур качества

Пять проверок, закрытый список и фиксированный порядок (`quality.CHECK_IDS`):

| Проверка | Что измеряет | Когда `problem` |
|---|---|---|
| `chunks_over_budget` | чанки длиннее предела (8000 токенов, `chunk_map.tokens`) | есть хоть один: выдача размывается |
| `signature_truncated` | функции с обрезанной сигнатурой в `node.props` | есть хоть одна: контракт параметров недостижим |
| `vector_available` | доступность `sqlite-vec` и число векторов | никогда (`warn`): честная деградация, не дефект |
| `capability_honest` | рёбра с источником графа свойств кода при `capability=full` | `full` без таких рёбер — завышенный режим |
| `parse_partial` | доля файлов с `parse_status` `partial`/`failed` (промилле) | никогда (`warn` при доле выше 200‰) |

Три свойства — часть контракта, а не украшение:

1. **Детерминизм.** В измерении нет времени и длительностей, доли считаются
   целыми промилле, порядок задан списком. Два прогона на неизменённом индексе
   дают одинаковый `digest` (sha256 канонической записи). Замер 25.10.2026 на
   rev-0266: `0e1944a1e86a578f…` в обоих прогонах.
2. **В журнал — только числа.** Добавляющая таблица `quality_run` (существующие
   таблицы и нумерация ревизий не затрагиваются) хранит ревизию, режим, счётчики
   и JSON измерения: имена проверок, числа, причины словами. Ни строк кода, ни
   путей файлов, ни содержимого чанков — прогон качества не должен становиться
   вторым индексом. Автоматической ротации нет: удаление старых записей —
   отдельное решение владельца, а не побочный эффект.
3. **Сравнение не выносит вердикт через ревизию.** Если прогоны сделаны на
   разных ревизиях, ответ несёт `through_revision: true` и `verdict: null`:
   правка кода законно меняет числа, и называть это деградацией индекса значило
   бы обвинять индекс за работу программиста.

Чего контур НЕ делает: не проверяет конвенции проекта (BOM, доктрину, числа в
документах — это чекер `tools/Invoke-ProjectDoctrine.ps1`), не измеряет качество
ранжирования и полноту ответов (для этого нужны запросы пользователя, а не
индекс). Обе границы названы в поле `limits` каждого ответа.

## 5. Проверки

```powershell
python tools\ragraf.py edition                 # Community: 5 возможностей
python tests\test_editions.py                  # 95 свойств, включая статусы
python tests\test_quality_loop.py              # 154 свойства
python tests\test_offline_attest.py            # 78 свойств, enterprise = 11 возможностей
pwsh -NoLogo -NoProfile -NonInteractive -File tools\Invoke-ProjectDoctrine.ps1
```

Чекер — **32 проверки**: `Test-EditionLayer` (27-я) запускает оба набора —
изданий и контура качества — и отдельно требует, чтобы каждый осмотрел не меньше
своего порога свойств. Ноль осмотренных свойств при успехе — провал, а не PASS.
