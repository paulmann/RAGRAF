# Документный граф: фундамент LLM-слоя (этап 1)

Дата: 1 ноября 2026 г. Область: RAGRAF (`C:/AutoClaw/RAGRAF`), этап 1 плана
`docs/00_plan/PLAN-AGENT-INTEGRATIONS.md` (§3.2, §3.3, §3.9).

## 1. Что входит в этап и что нет

Входит: клиент LLM (`src/ragraf/llm.py`), отпечаток слоя и схема фактов
(`src/ragraf/docgraph.py`), двенадцать настроек, две подкоманды `docgraph`, один набор
проверок.

**Не входит** (осознанно): извлечение сущностей и отношений, сводки тем, операции
чтения фасада и MCP, dual-level поиск, гейт изданий. Всё это этапы 2–5; на этом этапе
`docgraph build` без `--dry-run` отказывает кодом 2 и называет этап, в котором появится
извлечение. Молча ничего не делать значило бы выдать несобранный слой за собранный —
это тот класс дефекта, ради которого в продукте различаются «нет данных» и «не
собрано».

## 2. Клиент LLM: контракт

| Состояние | Признак | Что видит вызывающий |
|---|---|---|
| `configured` | `llm_enabled=true`, задана модель, задано имя секрета | вызов идёт, ключ выдаётся хранилищем при первом обращении |
| `local` | `llm_provider=local` | то же, ключ не требуется |
| `unavailable` | настройка неполная или провайдер отказал | код (`not_configured`, `no_key`, `auth`, `timeout`, `network`, `server`, `rate_limit`, `response`) и причина словами |

Отказ — исключение `LLMError` с кодом. Пустая строка в ответе означала бы «модель ничего
не сказала» и была бы неотличима от «спросить не удалось»; поэтому её нет ни в одном
пути.

Ключ: в настройке лежит ИМЯ записи (`llm_secret_name`), значение выдаёт
`Vault.reveal()` с причиной, каждая выдача попадает в аудит. Значение живёт в поле
клиента до конца его жизни: слой собирается тысячами обращений, и одно обращение к
хранилищу на прогон — это и меньше шума в журнале, и один вход в криптографию вместо
тысячи.

Температура по умолчанию 0. Таймаут ставится на сокет (жёсткий), попытки повторяются
только при временных отказах (`timeout`, `network`, `server`, `rate_limit`) и не
повторяются при отказах ключа и формата: повтор стоит денег и даёт тот же ответ.

## 3. Кэш ответов

Таблица `llm_cache(key, model, prompt_version, response, created_at)` в хранилище
лексики. Ключ — `sha256(нормализованный промпт + вход + модель + версия промпта)`,
разделитель — управляющий символ, который не встречается в тексте.

Нормализация промпта — только пробельная: хвостовые пробелы строк, пустые строки и
пробелы по краям текста. Других преобразований нет: любое «улучшение» текста инструкции
меняет ответ модели, и кэш начал бы отдавать результат другого вопроса.

Кэш адресуется содержимым, а НЕ ревизией: тот же чанк в следующей ревизии не
оплачивается второй раз. Поэтому у таблицы нет `rev_id`, и ротация её не чистит; предел
20 000 строк ограничивает рост, а факты слоя живут в других таблицах и чистку переживают.

## 4. Отпечаток слоя

`fingerprint(provider, model, prompt_version, temperature, extraction)` — `sha256` от
отсортированных частей; температура приводится к фиксированной точности (`0` и `0.0` —
одно значение). Провайдер входит в отпечаток, хотя план его не перечисляет: смена
провайдера меняет производителя фактов так же, как смена модели.

Запись идёт в два места:

* блок `docgraph` в `rev.json` рядом с `corpus_hash` — только если паспорт принадлежит
  этой ревизии (в чужой паспорт запись не идёт, и ответ это называет);
* `meta` журнала: `docgraph_fingerprint:<rev>` и `docgraph_state:<rev>` (разобранные
  части рядом с хэшем — «отпечаток изменился» без перечня непроверяемо).

Факт записи проверяется ПЕРЕЧИТЫВАНИЕМ, а не намерением — образец взят у живого слоя
баз (`src/ragraf/db_writer.py`), где расхождение «печатается вместо записывается» было
измеренным дефектом.

Смена отпечатка относительно предыдущей ревизии — запись `docgraph_fingerprint` в
`drift_entry` (append-only) и строка в `LEDGER.md`. Вид добавлен в отчёт архивации,
чтобы «что изменилось в знаниях» называло и смену входа слоя.

## 5. Схема фактов и правило адресуемости

Шесть таблиц в хранилище лексики: `entity`, `entity_mention`, `entity_relation`,
`theme`, `theme_member`, `theme_summary`. Все несут `rev_id`, поэтому попадают под
политику хранения автоматически.

* `entity_id = sha1(norm_name + '|' + kind)`, `theme_id = sha1(seed + '|' +
  отсортированные участники)`, `rel_id = sha1(src|dst|kind|chunk)` — одинаковый вход даёт
  одинаковый идентификатор на любой машине и в любой ревизии.
* Цитата хранится хэшем и смещениями, а не копией текста: слой не должен становиться
  вторым корпусом, который разойдётся с первым.
* **Нет упоминания — нет факта.** `add_entity` требует упоминаний, `add_relation` —
  адреса, `add_theme` — участников; пустой список даёт отказ с кодом
  (`mention_required`, `mention_address_incomplete`, `quote_required`,
  `members_required`). `check_integrity` ловит и обход API: сырой `INSERT` без
  упоминания — находка `entity_without_mention`.

## 6. Команды

```
python tools/ragraf.py -p config/ragraf.yaml docgraph status
python tools/ragraf.py -p config/ragraf.yaml docgraph build --dry-run
python tools/ragraf.py --json -p config/ragraf.yaml docgraph status
```

`status` отвечает при неработающем LLM (это состояние, а не ошибка): состояние
провайдера, отпечаток действующий и записанный, число документов/чанков/сущностей/
упоминаний/отношений/тем, вердикт целостности, причина и подсказки.

`build --dry-run` считает вход: чанки, вызовы, знаки и токены (оценка), сколько записей
уже лежит в кэше. Сети нет вовсе — поэтому команда полезна именно тогда, когда LLM ещё
не настроен и надо решить, настраивать ли.

## 7. Настройки

| Ключ | Смысл |
|---|---|
| `llm_enabled` | включатель LLM-прохода (отдельно от модели) |
| `llm_provider` | `openai` \| `local` (список закрытый) |
| `llm_model` | имя модели у провайдера |
| `llm_base_url` | адрес API; пусто — по умолчанию для провайдера |
| `llm_secret_name` | ИМЯ записи хранилища, не значение |
| `llm_prompt_version` | версия промпта: входит в отпечаток и в ключ кэша |
| `llm_timeout_seconds` | жёсткий предел ожидания ответа |
| `llm_max_attempts` | попытки при временном отказе |
| `llm_cache_enabled` | кэш ответов |
| `docgraph_max_chars` | знаков чанка в один запрос |
| `docgraph_max_entities` | предел сущностей из одного чанка |
| `docgraph_min_quote_chars` | минимальная длина цитаты упоминания |
