# Панель управления: как устроено оформление (замер 15.10.2026)

## Сборка стилей — локальная, без сети

Оформление собирается Tailwind CSS v4 и **коммитится** готовым файлом. Страница
при работе не тянет ничего извне: ни CDN, ни шрифтов, ни иконок.

```powershell
npm install                 # один раз: ставит tailwindcss и @tailwindcss/cli
npm run build:css           # admin/static/tailwind.src.css -> admin/static/style.css
npm run watch:css           # то же в режиме наблюдения при правке оформления
node tools/check_admin_frontend.mjs   # поведение страницы в браузерной модели
```

Источник (`admin/static/tailwind.src.css`) — единственное место, где живёт
палитра. В нём же выключен автопоиск классов (`source(none)`): без этого
Tailwind обходил бы `.venv`, `.tools` и `.ragraf`. Источники перечислены явно
(`app.js` и каркас страницы в `src/ragraf/admin_server.py`).

Автопоиск классов в v4 подхватывает новый класс автоматически; при выключенном
поиске новый класс должен появиться либо в исходнике, либо в перечисленных
файлах — иначе он не попадёт в сборку.

## Токены и темы

Цвета — только семантические (`--background`, `--card`, `--muted-foreground`,
`--primary`, `--ring`, `--ok/--warn/--bad`), как принято в shadcn. Светлая схема
в `:root`, тёмная — в `[data-theme="dark"]`; переключение идёт атрибутом на
`<html>`, поэтому в разметке нет `dark:`-переопределений.

Выбор темы хранится в `localStorage` (`ragraf-admin-theme`: `system` | `light` |
`dark`), при первом заходе берётся системная настройка, и пока выбор —
«как в системе», панель следит за сменой системной темы. Тема выставляется
скриптом в `<head>` до первой отрисовки, иначе на тёмной системе мелькает
светлый фон.

## Разделы и опрос состояния

Разделы (`Developments`, `Indexing`, `Index quality`, `Usage and effect`,
`Database sizes`, `Settings`, `Mode and clients`, `Access`, `Databases`) лежат в
DOM одновременно, переключается только видимость — переключение не требует
запроса. Выбранный раздел хранится в `localStorage` (`ragraf-admin-section`).

Поведение при опросе состояния (это была ЖАЛОБА владельца — «поля сбрасываются
каждую секунду»):

* страница не перерисовывается, пока фокус внутри поля формы;
* если перерисовка всё же произошла, введённые значения возвращаются
  (`snapshotFormValues` / `restoreFormValues`);
* повторный опрос идёт только пока сервер САМ сообщает, что собирает данные.
  Раньше условие включало и разработки без индекса — такая отметка остаётся
  неопределённой навсегда, и страница перечитывалась бесконечно.

Проверка поведения — `node tools/check_admin_frontend.mjs` (jsdom, 14 проверок);
она ловит и потерю значения, и лишние перерисовки за 4 секунды.
## Вход в панель: почему он не запоминался (замер 15.10.2026)

Жалоба владельца: «ввожу токен, панель пишет, что вошёл, но любая операция снова
показывает вход». Причина была двойная:

1. «Проверкой» входа служил запрос `GET /api/state`, а заголовок с токеном клиент
   отправлял **только вместе с телом запроса**. Страница состояния читается и без
   прав, поэтому успешным выглядел любой ввод; первая же запись получала 403, и
   раздел входа возвращался.
2. Панель печатает **новый** токен сессии при каждом запуске, а браузер хранил
   прежний и продолжал его предъявлять — вход «слетал» сам.

Что сделано:

* заголовок с токеном идёт с любым запросом, а не только с телом;
* права подтверждает сервер: `POST /api/auth/token` отвечает
  `{"ok": true, "authenticated": true, "kind": ..., "label": ...}` либо 403.
  Точка стоит выше общей проверки доступа (как вход и выход: иначе проверка
  требовала бы входа); ответ не содержит секретов;
* токен сохраняется в браузере **только после подтверждения сервером**; при
  запуске сохранённый токен перепроверяется, устаревший забывается, и владелец
  видит причину («токен не действует в этом запуске панели»);
* в шапке справа — надпись `Guest` или `Admin` с выпадающим меню: ввод токена,
  выход из системы, «забыть токен». Надпись перерисовывается только при смене
  состояния, чтобы не закрывать раскрытое меню на каждом опросе.

Проверка поведения — `node tools/check_admin_frontend.mjs`: неверное значение не
принимается и не сохраняется, верное подтверждается живым сервером (для этого
запуск панели делается с `python -u`, иначе баннер с токеном остаётся в буфере
вывода и значение не прочитать), надпись переключается Guest → Admin → Guest.
## Рабочий запуск панели: порт, токен, срок снимков (замер 15.10.2026)

Владелец: «нужен рабочий инструмент». Найдено и исправлено:

* `--port 11701` (через пробел) **молча игнорировался** — принималась только форма
  `--port=11701`. Теперь принимаются обе.
* Занятый порт больше не срывает запуск: панель берёт следующий свободный и
  печатает, какой именно. Проба порта идёт **соединением** (`connect_ex`), а сервер
  создаётся с `allow_reuse_address = False`: на Windows `SO_REUSEADDR` позволяет
  привязаться к уже занятому порту — замерено, что два экземпляра печатали один
  адрес, а слушал только один.
* Баннер запуска печатается с `flush=True`: при перенаправленном выводе строка с
  токеном оставалась в буфере, и токен нельзя было прочитать из журнала (именно на
  этом спотыкалась проверка `check_admin_frontend.mjs`, которой нужен живой вход).
* **Панель собирала сведения почти непрерывно.** Замер: полный обход разработок —
  около 100 секунд (почти всё время — одна разработка AutoClaw, 54 тыс. файлов), а
  срок снимка был 120 секунд; у разделов «Использование» и «Качество индекса»
  срока не было вовсе, поэтому чтение баз 27 разработок запускалось на **каждом**
  обращении к состоянию. Следствие: `collecting` был истинным почти всегда, а
  страница опрашивала состояние каждые 3 секунды.
  Теперь срок снимка 1800 секунд, у разделов — 600, а кнопка обновления запрашивает
  `/api/state?force=1` (сбор заново, без ожидания срока). Замер после правки:
  **0 замеров со сбором из 9 за 90 секунд** (прежде — почти все).
* Отказ точки входа (`/api/auth/login`, `/api/auth/logout`, `/api/auth/token`) больше
  не помечается как «права отобрали»: после неверного пароля страница не считает,
  что доступ потерян.
* Вход по паролю подтверждается у сервера, поэтому надпись в шапке меняется на
  `Admin` (раньше оставалась `Guest`, хотя запись уже была разрешена).

Проверки: `python tools/check_admin.py --token=…` — 39/0; `node
tools/check_admin_frontend.mjs` — 32/0 (включая «кнопка обновления запрашивает сбор
заново» и «опрос состояния не запускает цикл перерисовок», которая теперь
выполняется, а не пропускается); `python tools/check_admin_i18n.py` — 92/0;
`python tools/check_bom_crlf.py` — 39/39; чекер конвенций — 19/0 PASS.
## Значение доступа переживает перезапуск (замер 15.10.2026, вторая жалоба)

Владелец: «токен перестал приниматься», «окно Session token не реагирует на ввод
токена и нажатие Use token». Разбор дал две разные причины.

**1. Значение менялось при каждом запуске.** Токен создавался в памяти процесса
(`secrets.token_urlsafe(24)`), поэтому любой перезапуск панели — в том числе
служебный, во время правок, — делал сохранённый в браузере вход недействительным:
панель честно отвечала «токен не принят», а взять новый было неоткуда, кроме
консоли запуска. Теперь значение лежит в файле
`.ragraf/admin/session_key` и переиспользуется при запуске; в баннере печатается
и путь к файлу. Новое значение выпускается осознанно: `--new-token` (или удаление
файла). Проверка: отпечаток файла до и после перезапуска совпал, значение после
перезапуска принимается (`POST /api/auth/token` → 200); прежде без этого признака
«стойкость» проверить было нечем.

**2. Отказ из меню в шапке закрывал само меню.** Сообщение об отказе живёт внутри
выпадающего меню, а перерисовка надписи (`renderAccount`) перестраивала меню и
закрывала его вместе с сообщением — нажатие выглядело как «ничего не произошло».
Теперь при отказе меню не перестраивается: сообщение остаётся на экране, поле
ввода и кнопка никуда не деваются. Кнопка «Use token» в разделе входа на странице
дополнительно перерисовывает надпись в шапке в обоих случаях.

**Как это проверяется.** В `tools/check_admin_frontend.mjs` добавлены две проверки:
кнопка «Use token» на странице сообщает об отказе (прежде этот путь не проверялся
вовсе) и надпись в шапке переключается `Guest → Admin → Guest` на живом сервере.
Итог: 34/0. Живая проверка панели — 39/0, словари — 92/0 (проверка запрещает
кириллицу в китайском переводе: русский термин в нём пришлось заменить).

**Граница доверия.** Значение доступа теперь лежит на диске и переживает
перезапуск; каталог `.ragraf` исключён из индексации, панель слушает только
127.0.0.1. Кому этого мало — `--new-token` выпускает новое значение, а прежнее
перестаёт приниматься сразу.
## Служебная проверка затирала общий снимок (замер 15.10.2026)

Отказы «показаны размеры баз» и «собрана статистика по разработкам» в
`tools/check_admin.py` повторялись каждый раз после перезапуска панели, и причина
оказалась не в панели, а в проверке словаря: её раздел «контракт страницы» запускает
сбор **в своём процессе** с урезанным списком разработок, а сбор записывал снимок в
общий файл `catalog/admin_snapshot.json`. Замер: в файле оказалась **одна** запись
(ragraf) вместо 27, и панель после перезапуска показывала размеры баз одной
разработки. Это видел и владелец: пустые столбцы размеров без всякой причины.

Исправлено: запись снимков разрешена только процессу панели (флаг выставляется в
`main()`), служебные проверки считают в своём процессе, но общий файл не трогают.
Проверено замером: после прогона `check_admin_i18n.py` снимок сохраняет 27 записей,
`check_admin.py` даёт 39/0 сразу после перезапуска панели (прежде — отказ, пока не
пройдёт полный обход).

Заодно разделы «Использование» и «Качество индекса» получили снимок на диске
(`catalog/admin_detail.json`): прежде после каждого запуска оба раздела были пустыми
минуту, пока идёт сбор, — теперь показываются сразу.

## Режим работы: пропадал список и появилась инструкция (замер 15.10.2026)

Жалоба владельца: «попробовал сменить cli на mcp-stdio, и из выбора пропало всё,
кроме CLI, да и он не выбран». Причина: **ответы о режиме имели разную форму**.
Чтение (`GET /api/mode`) отдавало `mode` (строка) ВМЕСТЕ со `modes` (список), а
применение (`POST /api/mode`) — только строку. Страница присваивала себе ответ
целиком, поэтому после применения у неё исчезал список режимов: оставался запасной
`['cli']`, и ни одно значение не было выбрано. Проверено запросом: до правки
`POST` отдавал ключи `mode, ok, probe`, после — `mode, modes, ok, probe` (четыре
режима, как и у чтения).

Исправлено: ответ о режиме строится одной функцией `mode_payload()` для чтения и
для применения; страница дополнительно переживает строку вместо объекта (страховка
на случай старого ответа).

**Инструкция по подключению.** Владелец просил показывать под выбором режима, что
именно настраивать в AutoClaw и HARNESS. Блок строится из данных сервера, а не из
текста страницы, поэтому не может разойтись с фактическими значениями:

* AutoClaw — шаги формы «Add tool», команда запуска сервиса (`tools/ragraf-mcp-http.py`
  с портом) и напоминание про значение доступа в поле Bearer token;
* HARNESS — только те варианты клиента, что отвечают выбранному каналу: `stdio`
  для `mcp-stdio`, `streamable-http` для `mcp-http`, оба для `both`, с готовой
  конфигурацией и путём к файлу профиля;
* `cli` — команда вида `python tools/ragraf.py -p <конфиг> <команда>` и прямое
  указание, что настраивать ничего не нужно;
* если выбран `mcp-stdio`, а AutoClaw подключается по HTTP, панель это говорит
  прямо (предупреждение под значениями формы) — иначе владелец настроит клиент и
  не поймёт, почему он молчит.

Блок обновляется СРАЗУ при выборе режима, до применения. Проверки в
`tools/check_admin_frontend.mjs`: список из четырёх значений, выбранное значение,
наличие инструкции для AutoClaw и HARNESS, смена инструкции при переключении
`mcp-http`/`mcp-stdio`/`cli`, предупреждение про HTTP только когда оно уместно, и
проверка формы ответа у ЖИВОГО сервера. Итог — 46/0.
## Обе формы подключения AutoClaw и живой индикатор связи (замер 15.10.2026)

Запрос владельца: «а если я хочу через Local program, а не Online service? Добавь
обе инструкции и информацию, видит сервис AutoClaw или нет: до коннекта — красным,
потом жёлтое, зелёное на успешный коннект».

**Обе формы.** `client_setup.autoclaw_values()` отдаёт `variants`: `Online service`
(URL `http://127.0.0.1:8765/mcp`, поле Bearer token, команда подъёма сервиса) и
`Local program` (Command/Arguments/Working directory — процесс запускает сам
AutoClaw, ни порт, ни значение доступа не нужны). Панель показывает обе формы
под выбором режима; прежние ключи `how`/`fields`/`before` оставлены как были, их
читают проверки проекта.

**Следы обращений.** Новый модуль `src/ragraf/contact.py` записывает каждое
обращение к MCP-серверу — `initialize`, `tools/list`, `tools/call` — в общий файл
`.ragraf/admin/mcp_contacts.json`. Хук стоит в `McpServer.handle()`, поэтому
покрыты ОБА канала: HTTP-сервис и stdio-процесс, который запускает клиент.

**Различение клиента.** Сервис поднимается с `--agent AutoClaw`, поэтому хранятся
два имени: `agent` (параметр запуска) и `client_info` (имя из `clientInfo` запроса
`initialize`, которое клиент обязан сообщить по протоколу). Признаком подключения
служит `client_info`, если он есть: иначе любой клиент, пришедший на сервис,
выглядел бы как AutoClaw. Проверено живым прогоном: обращение с `clientInfo.name =
SomeOtherTool` зелёного не даёт, а с `AutoClaw` — даёт.

**Три состояния в панели.** Красное — обращений не видно; жёлтое — HTTP-сервис
поднят (проба соединением по порту), но обращений от клиента нет либо последнее
было больше пяти минут назад; зелёное — обращение было, показаны имя клиента,
сколько назад и последний инструмент. Состояние связи показывается и в блоке
AutoClaw, и в блоке HARNESS.

**Замеры живьём (15.10.2026).** Сервис не поднят, следов нет → `service_running:
false`, красное. Сервис поднят, обращений нет → `service_running: true`, следов 0,
жёлтое. Обращение с `clientInfo.name = AutoClaw` (реальный MCP-запрос на
`/mcp`) → след `AutoClaw`, `client_info: AutoClaw`, источник `client`, 2 вызова,
последний `tools/list` → зелёное. Локальный запуск (`tools/ragraf-mcp.py` через
stdio с тем же `clientInfo`) → след `AutoClaw (Local program)`, источник `client`.

Проверки теста поведения: 52/0, включая красное/жёлтое/зелёное состояние, показ
обеих форм подключения и отказ считать чужим именем клиента подключением AutoClaw.
## Параметры из ENV и почему панель не видела AutoClaw (замер 15.10.2026)

Замечания владельца: «В инструкции Working directory, но в AutoClaw такого поля нет —
там передача параметров через ENV»; «AutoClaw говорит, что успешно присоединился, а
панель говорит: обращений от AutoClaw не видно».

**1. Рабочего каталога в форме нет.** У типа `Local program` поля «Working directory»
действительно нет, зато есть «Environment variables (optional, one KEY=value per line)».
Добавлена поддержка переменных окружения для того, что раньше задавал только
рабочий каталог: `RAGRAF_PROJECT` (и `RAGRAF_CONFIG`) подставляется в `--project` —
и в stdio-сервере (`tools/ragraf-mcp.py`), и в HTTP-сервисе. Имена агента брались из
ENV и раньше (`RAGRAF_AGENT`, `RAGRAF_AGENT_KIND`).
Замер: запуск из каталога `C:\` БЕЗ `--project`, только с `RAGRAF_PROJECT` → сервер
напечатал «проект C:\AutoClaw\RAGRAF\config\ragraf.yaml», ответил на `initialize` и
на `tools/call`. Инструкция в панели теперь показывает: Launch command, Arguments
(путь к `ragraf-mcp.py`), Environment variables тремя строками — и не показывает
поля, которого в форме нет. Значения с переносами строк выводятся отдельными
строками (`<br>` после экранирования): иначе три переменные склеивались в одну.

**2. Связь БЫЛА, а панель её не видела.** В следах лежала запись
`agent: AutoClaw`, `client_info: zwork`, канал `stdio`, 2 вызова — но панель искала
строку «autoclaw» только в поле `client_info`, а MCP-клиент AutoClaw представляется
именем **`zwork`**. Отсюда красное «обращений не видно» при работающем подключении
(процессы клиента были живы).

Исправлено: сопоставление идёт по ДВУМ именам записи, но по-разному для каналов.
`client_info` (имя, которым представился сам клиент) значимо всегда; `agent` —
только для stdio, где этот параметр задаёт сам клиент своей командной строкой. Для
записей канала http берётся лишь `client_info`: там `--agent` задаётся один раз при
запуске сервиса, и по нему чужой клиент выглядел бы как AutoClaw. Слово `zwork`
добавлено в список по замеру. Выводы считает СЕРВЕР (`contact.links`), страница их
только показывает — правило сопоставления должно быть одно.

**3. Окно «связь есть» — 15 минут.** Клиент MCP обращается по потребности, и
молчание в несколько минут не означает разрыв. Состояния: обращение за последние
15 минут — зелёное; было раньше — жёлтое с возрастом («обращений не было N назад:
возможно, связь потеряна»); не было никогда — красное; сервис поднят без обращений
— жёлтое.

Замер после правки: панель разрешает `autoclaw → AutoClaw / zwork`, то есть
подключение владельца показано зелёным. Проверки теста поведения: 56/0, включая
сверку рисунка индикатора с ответом сервера на том же прогоне, наличие переменных
окружения и отсутствие поля «рабочий каталог».
