# Верификация утверждений статьи-источника

**Источник:** «Агент не справляется с аудитом кода? Просто добавь графы» — Радда Юрьева, Positive Technologies, <https://habr.com/ru/companies/pt/articles/1084780/>
**Метод:** каждое числовое утверждение сверялось с первоисточником (arXiv / материалы конференций / репозитории). Пересказ статьи сам по себе доказательством не считается.
**Статус:** волна 2 из 2 — проверка завершена. Непроверенным осталось одно место (проценты сжатия LLMxCPG) — оно помечено явно.

## 2. Что статья исказила — систематические смещения

1. **Единицы измерения.** 184 CVE против 184 GitHub Advisory (и 408 vulnerability entries). Для оценки объёма данных разница принципиальна.
2. **Класс уязвимостей.** ALIBI работал только с разыменованием нулевого указателя (125 случаев), статья обобщила до «уязвимостей».
3. **Даты.** CLEAR — 17 июля, а не «август».
4. **Вторичное подано как первичное.** Ключевое число 22,58% и «> 56%» фейлов у VulnGym воспроизводятся только в **AI-обзоре** (alphaXiv), а не в тексте статьи и не в датасете: README проекта содержит «Baseline evaluation results — Coming soon». Формально это не ошибка, но читатель не может проверить число по первоисточнику, о чём статья не оговаривает.
5. **Ошибка масштаба.** «9 агентских конфигураций» не подтверждается: подтверждаемый список скаффолдов — три (Claude Code, OpenHands, MiniSWE).
6. **Несуществующая ссылка.** LeanGuard не находится ни поиском по arXiv, ни веб-поиском — после двух целенаправленных попыток.
7. **Проценты без источника.** Агрегированные 68–70% / 90,93%, «8000 токенов» и «≈0,6 на свежих уязвимостях» у LLMxCPG **остались неподтверждёнными** (бюджет чтения PDF исчерпан дважды). Подтверждён только качественный пример 85 → 18 строк.
8. **Одиночный результат как закон.** «Только граф лучше, чем граф + код» опирается на одну работу (107 кейсов, C/C++, 5 CWE, один протокол рассуждений, одна команда). Сам автор работы признаёт исключения — см. §3.

**Вывод о добросовестности.** Итог двух волн по 19 проверявшимся положениям: **подтверждено 10**, **частично 2**, **опровергнуто 1** (для репозитория), **не подтверждено 1** (число VulnGym-разбивки), **не найдено 1** (LeanGuard), **осталось не проверенным 1** (проценты сжатия LLMxCPG). Там, где статью можно проверить полностью, она **точна дословно**: «Words Speak Louder Than Code» (все четыре числа), CLEAR (оба процента и состав агентов), идентификаторы шести работ, оценки качества граф-представлений RepBench, пороги LLMxCPG. Ошибки концентрируются в трёх местах: **вторичное подано как первичное** (VulnGym), **ошибка масштаба** («9 конфигураций») и **одна несуществующая ссылка** (LeanGuard).

**Практическое следствие для RAGRAF.** Общий вектор статьи — граф как слой структуры, LLM как слой интерпретации, фиксированные операции вместо свободного языка запросов — подтверждён на первоисточниках. Конкретные проценты переносить в ТЗ нельзя: они получены на C/C++ и памяти-безопасности, а не на прикладном коде на PHP/Python/JS. Ссылку на LeanGuard использовать не следует.

## 3. Противоречия, которые нельзя замалчивать

| Противоречие | Суть | Что это значит для нас |
|---|---|---|
| «Только граф» против «граф + код» | RepBench: graph-only > source+graph. Но это 107 кейсов на C/C++, один протокол, и сам автор отмечает случаи, где source+graph не хуже | Не фиксировать правило «никогда не давать исходник». Проверять на нашем корпусе (метрика M4) и давать исходник там, где он нужен (например, генерация патча) |
| «Меньше контекста, больше структуры» против «больше контекста» (long-context) | Прямого сравнения граф-индекса с long-context-индексом в выборке нет | Выбор не доказан; нужен собственный замер M3, а не ссылка на статью |
| Повышение полноты против роста шума | Классический компромисс SAST: полнота даётся шумом, точность — дороже | Отсюда обязательная пометка достоверности и провенанса у каждого факта: агент сам решает, насколько доверять |
| Обфускация vs extract-method | Граф устойчив к переименованию, но ломается на выносе кода в функцию | extract-method — ежедневная операция при рефакторинге → это не экзотический риск, а основной источник «плывущего» индекса |

## 4. Границы применимости к нашему кейсу

Все подтверждённые числа получены на **поиске уязвимостей**, преимущественно на **C/C++** и memory-safety-классах:

| Параметр | Подтверждённые работы | Наш кейс | Следствие |
|---|---|---|---|
| Задача | найти уязвимость | найти, где менять; что сломается; как сделать одинаково | Переносится механика (граф + срез + LLM-интерпретатор), но **не метрики** |
| Языки | C/C++ (VulnGym — 71,2% бизнес-логики, но без опубликованного baseline) | PHP, Python, JS/TS, C#, PowerShell, SQL | Прямых измерений для наших языков нет — нужен свой стенд |
| Режим | разовый аудит зафиксированного коммита | непрерывная разработка, индекс живёт месяцами | **Требование дрейфа индекса в литературе не покрыто** — это наша инженерная работа, а не перенос результата |
| Провенанс | требования не формализованы | обязателен для каждого факта | Вводим как собственное НФТ |
| Текстовые каналы влияния | ALIBI: комментарии — вектор атаки, спасает только изоляция | комментарии/докблоки/история — тоже данные | Хранить текстовые поля отдельно от структурных фактов |
