# Вход в ТЗ: требования, вытекающие из исследования

Документ — мост между Этапом 1 и Этапом 2. Каждое требование здесь опирается на **проверенный** факт (первоисточник, замер или официальная документация), а не на пересказ статьи. Формулировки готовы к переносу в ТЗ Этапа 2; нумерация предварительная.

---

## 2. Требования, готовые к переносу в ТЗ

### Функциональные (уточнённые)

- **FR-1** Граф кода: узлы и типизированные рёбра с языковой разметкой (AST-производные: `contains`, `defines`, `imports`, `extends`, `implements`, `calls`, `instantiates`).
- **FR-2** Векторный + лексический индексы, гибридное ранжирование (лексика обязательна: точные имена, пути, SQL-литералы).
- **FR-3** Внешние контракты в графе: таблицы/колонки/внешние ключи, HTTP-маршруты и обработчики, формы, CLI-точки входа, документы Markdown.
- **FR-4** Фиксированные операции фасада: `search`, `symbol`, `references`, `callers`, `callees`, `impact`, `slice`, `repo_map`, `schema`, `table_usage`, `routes`, `index_status`, `drift_report`, `drift_ack`, `live_read`. Свободного языка запросов нет.
- **FR-5** Навигация отвечает `path:line` и диапазоном строк — «где файл» и «где строка» одним запросом.
- **FR-6** Основной формат ответа — компактный структурный контекст (подграф/срез), а не файл целиком.
- **FR-7** Каждый факт сопровождается `evidence` (`path:line`), `confidence` и `index_rev`.
- **FR-8** Инкрементальная переиндексация гранулярна по изменённому участку; рёбра помечаются категорией стоимости пересчёта.
- **FR-9** Ledger: append-only журнал дельт, ключ `(path, old_hash, new_hash)`; запись **только** через фасад, не агентом напрямую.
- **FR-10** Провенанс обязателен: источник-экстрактор с версией, `path:line`, `index_rev`.
- **FR-11** Пороги — конфигурируемые, с процедурой калибровки на ~20 примерах.
- **FR-12** Разделение слоёв: структурные факты ≠ свободный текст. Текст помечается и не подаётся как истина.
- **FR-13** Нейтральность формулировок в ответах фасада.
- **FR-14** Дедупликация и выбраковка: у факта есть признак «полезен / нейтрален / вреден по обратной связи».
- **FR-15** Явный ответ «не найдено по индексу» + предложение `live_read`, а не приблизительная выдача.
- **FR-16** Инкрементальный разбор через tree-sitter (`Tree.edit`); полный разбор — только при `reindex --commit`.
- **FR-17** Конфигурация исключений (вендорные каталоги, `.log`, `_bak`, `node_modules`, артефакты агента) — обязательна.
- **FR-18** Переиндексация по явной команде; результат — новый `INDEX_REV`; прежняя ревизия сохраняется.
- **FR-19** Архивация ledger при переиндексации в человекочитаемый отчёт «что изменилось в знаниях».
- **FR-20** Отчёт покрытия: разобрано / не разобрано, потерянные связи, эвристические рёбра.

### Нефункциональные

- **NFR-1** Без прав администратора; установка — только в пользовательские каталоги.
- **NFR-2** Полная индексация ~160 тыс. строк ≤ 15 мин; инкрементальная — секунды.
- **NFR-3** Секреты: значения не индексируются; секретоносные пути исключаются списком.
- **NFR-4** Детерминированность: одинаковый вход → идентичный `INDEX_REV`.
- **NFR-5** Индекс удаляется и пересобирается одной командой; артефакты не размазаны по проекту.
- **NFR-6** PowerShell 7.6+ / Python 3.13 по правилам проекта (utf8NoBOM, без BOM/CRLF в поставляемых файлах, `#Requires`, без WinPS-compat).
- **NFR-7** Никакого свободного доступа к графу извне фасада — только чтение операций.

## 3. Что ТЗ обязано честно ограничить

1. **Без JVM нет CFG/DFG/PDG** и срезов по потоку данных. Требования формулируются как «impact analysis по структурным связям, символам и истории», **без обещания data-flow**. Это ограничение вписывается в ТЗ явно, а не выясняется в реализации.
2. **Все подтверждённые в литературе числа получены на C/C++ и на поиске уязвимостей.** Для PHP/Python/JS измерений нет → наши метрики M1–M4 снимаются на нашем корпусе, а чужие проценты в ТЗ не переносятся.
3. **Проценты сжатия 68–70% и 90,93% не подтверждены** — как ориентир можно использовать только эмпирический факт «сжатие возможно», но не цифру.
4. **Ссылку на LeanGuard использовать нельзя** — работа по этому названию не находится.
5. **Устаревание индекса в литературе не измерено** → M5 (свежесть) мы определяем и измеряем сами.
6. **Пороги: без калибровки использовать нельзя** — разброс в 3 раза между корпусами.

## 4. Ограничения выбранного стека (следствие замеров)

| Что | Статус |
|---|---|
| `sqlite-vec` — вектор в том же файле, что лексика | **доступно**; версия pre-v1 («expect breaking changes») → обернуть в свой слой, чтобы замена не ломала ТЗ |
| SQLite FTS5 (BM25) | **доступно**, встроено |
| `fastembed` (ONNX, без torch) | **доступно**; `bge-m3` и `gte-multilingual` в нём **отсутствуют**; мультиязычный e5 — только `-large` (2,24 ГБ); русскоязычный минимум — `paraphrase-multilingual-MiniLM-L12-v2` (~0,22 ГБ, 384) |
| Граф: таблицы смежности в SQLite / рекурсивные CTE | **доступно**, ноль зависимостей |
| Граф: Cypher — `real-ladybug` (форк Kuzu) | **колесо есть**; совместимость с форматом Kuzu **не подтверждена**; `ladybugdb` на PyPI не существует (пакет `real-ladybug`) |
| `kuzu` 0.11.3 | колесо есть, но репозиторий **архивирован** → как единственная опора рискованно |
| DuckDB `vss` | **experimental**, ANN-индекс держится в RAM целиком, инкрементальных обновлений нет |
| DuckPGQ | **community-расширение**, «research project and a work in progress» → не фундамент |
| Milvus Lite | **Windows не поддерживается** → исключён |
| Qdrant (local mode) | доступно, но режим заявлен как «для разработки и прототипов» |
| Скорость эмбеддингов на CPU | **не измерена** (в документации замеров нет) → первый прогон обязан её замерить |
| CodeQL | лицензия не подтверждена для проприетарного кода → **не в стеке** |
| `code-graph-rag`, `codebadger` | требуют Docker → исключены |

## 5. Открытые технические вопросы к Этапу 2

1. Граф: собственные таблицы в SQLite или `real-ladybug`? Решается замером на пилоте.
2. Эмбеддинг-модель: русскоязычный минимум (0,22 ГБ) или мультиязычный `e5-large` (2,24 ГБ)? Влияет на скорость и качество M3.
3. Чанкинг кода: по символам (функция/метод) — очевидно; нужен ли дополнительный слой «скользящее окно» внутри крупных функций (у пилота есть файлы на 9 тыс. строк).
4. Индексировать ли документацию в тот же граф или отдельным слоем с связью `documented_by`.
5. Сколько ревизий индекса хранить и в каком формате (полные копии vs дельты).
